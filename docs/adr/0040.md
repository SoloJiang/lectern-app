# ADR 0040：依赖层这一阶段只支持 pnpm 的布局；链接可以落在同一 worktree 已发现的另一个依赖根里；身份取自 pnpm 记下的安装状态

- 状态：已接受
- 日期：2026-10-21
- 修订：[ADR 0033](0033.md)（「依赖根的读取限制」中「符号链接只在同一生态的同一个根内解析」；「键」中 npm / pnpm / yarn 的身份「lockfile 的 `integrity`」；依赖层覆盖的 TS / JS 布局；「只读声明和源码的扩展名」）

## 背景

[ADR 0033](0033.md) 让依赖层为当前子项目的直接依赖建声明闭包的索引，读取限制里有一条：符号链接只在同一生态的同一个根内解析，目标离开这个根就按读不到处理。code_intel 的设计审阅发现两处与实际的安装布局不合：

- pnpm 工作区：子项目 `packages/app/node_modules/react` 是指向工作区根 `node_modules/.pnpm/react@19.0.0/node_modules/react` 的链接。`packages/app/node_modules` 和根目录的 `node_modules` 是 Node 查找链上的两个根，按「同一个根」的规则，工作区里每个子项目的依赖都读不到。
- npm 的身份：`package-lock.json` 记的是应当安装的内容。`git pull` 或切换分支之后、`npm install` 之前，lockfile 已经是新的，`node_modules` 还是旧的；按新的 `integrity` 记下旧的内容，之后就一直沿用。

2026-10-21 产品负责人决定：依赖都通过 pnpm 管理。这一阶段的依赖层以 pnpm 的布局为准，npm 和 yarn 的布局以后再做。

pnpm 的布局（[pnpm 文档](https://pnpm.io/symlinked-node-modules-structure)）：包装在虚拟存储 `node_modules/.pnpm/<名字>@<版本>[_<peer>]/node_modules/<名字>` 里，目录名带着已安装的名字、版本和 peer（名字里的 `/` 写作 `+`，peer 长时是哈希）；每个子项目的 `node_modules/<名字>` 是指向它的链接；工作区里虚拟存储默认在工作区根的 `node_modules/.pnpm`。pnpm 每次安装之后按实际装好的树写 `node_modules/.pnpm/lock.yaml`，格式与 `pnpm-lock.yaml` 相同；`packages:` 里每个包的 `resolution.integrity` 是 tarball 的哈希。

## 决策

**范围**

- 这一阶段的 TS / JS 依赖层和跳转时依赖的按需解析只在 pnpm 的布局上运行：子项目的 Node 查找链上有一个含 `.pnpm` 目录的 `node_modules`。没有的项目（npm、yarn 安装）没有依赖层，也不按需解析依赖；依赖里的定义不出现，项目自己的结果和完整性不受影响。这是写明的已知限制。
- 读取规则（依赖根怎样打开、链接怎样解析、读哪些文件、上限）不依赖 pnpm 的布局；以后加入 npm 的平铺布局只需要另一种身份来源，不改安全模型。Cargo、Go、Python 和 ADR 0033 的其余部分不变。

**链接的解析（修订 ADR 0033 的「同一个根」）**

- 关键约束：链接按词法解析，目标必须落在同一个 worktree 已发现的某个依赖根之内（子项目 Node 查找链上经 worktree 根的 `SafeRoot::open_dir` 打开的 `node_modules`，打开时路径的任何一级都不是符号链接）；之后经目标所在根的 `SafeRoot` 读，读取时不跟随任何符号链接，其余各级不得是符号链接。目标不在任何已发现的根里（`$HOME`、worktree 之外、没有作为根打开的目录、另一个 worktree 的根）就按读不到处理。
- 所以安全性质不变：依赖层读的每个文件都在某个按 ADR 0033 第一条打开的根之内，不读这些根之外的任何东西。
- 根按 worktree 登记，切换当前 worktree 后另一个 worktree 的根不再被读；根被删掉重建时按登记的路径重新打开（由 code_intel 的设计负责）。

**身份（修订 ADR 0033「键」里 npm / pnpm / yarn 的一条）**

- 一个包的身份是（虚拟存储的目录名、`integrity`、已安装的 `package.json` 的 stat）。`integrity` 先取 `node_modules/.pnpm/lock.yaml`（已安装的状态），没有时取工作区里的 `pnpm-lock.yaml`；按已安装的目录名里的名字和版本找键，所以 lockfile 已经改成另一个版本、还没安装时找不到这个键，走后备，不会把还没安装的内容的 `integrity` 当作身份。
- 取不到 `integrity` 时的后备是（目录名、包清单的 OID、stat），然后照常走 ADR 0033 的 stat 表。后备只会让身份更容易「变了」、多读文件，不会给出错的身份。
- 关键约束：不新增依赖（ADR 0033），所以不用 YAML 解析器。lockfile 按行流式扫描，只认一个写明的语法子集（`lockfileVersion` 的主版本 6 或 9、`packages:` 段、第 2 列的项、`resolution` 的两种写法），文件和单行都有上限；超出子集时这一项（或整个文件）走后备，从不在子集之外猜。子集和上限写在 code_intel 的设计里。
- 只读的文件（修订 ADR 0033 第四条）：在声明和源码的扩展名之外，加上虚拟存储所在的根里的 `.pnpm/lock.yaml` 这一个文件，按完整的相对路径匹配。`pnpm-lock.yaml` 是受跟踪的工作区文件，不经依赖根读。
- 失效：`pnpm-lock.yaml`、`pnpm-workspace.yaml` 和清单是受跟踪的文件，fs_watch 照常交付；`.pnpm/lock.yaml` 在被忽略的目录里，在打开项目、上述文件变化和依赖读取失败时检查。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 保持「同一个根」，pnpm 工作区不支持 | 产品负责人决定依赖都通过 pnpm 管理，工作区是 pnpm 的常见用法 |
| 允许链接指向 worktree 里任何目录 | 被审阅的 agent 可以在 worktree 里放任何文件；只认已经按规则打开的依赖根，范围最小 |
| 引入 YAML 解析器读 lockfile | ADR 0033 不新增依赖；只需要每个包的一个字段，流式的行扫描足够，超出子集时有不出错的后备 |
| 身份只取 `pnpm-lock.yaml` | 与 npm 的 `package-lock.json` 同样的问题：安装之前 lockfile 已经变了 |
| 这一阶段同时支持 npm 和 yarn | 产品决定以 pnpm 为准；npm 的身份要另一种来源（`node_modules/.package-lock.json` 或安装状态的 stat），yarn 有两种 lockfile 格式，留到以后 |

- `code_intel`：「依赖层」按本 ADR 写（pnpm 的发现、目录名、两个 lockfile 的扫描与语法子集、链接落在已发现的根里、按 worktree 登记的根），测试 `deps_link_into_a_discovered_root_is_read`、`deps_link_outside_the_discovered_roots_is_rejected`、`deps_lock_scan_*`、`deps_npm_layout_is_out_of_scope`；见 [code_intel 设计「依赖层」](../design/code_intel.md#依赖层)。
- `bench`：`code_intel/deps_*` 和 `app/index_100k` 的夹具是 pnpm 的布局（[bench 设计「预算表」](../design/bench.md#预算表)）。

## 已知限制

- npm、yarn 安装的项目没有依赖层和依赖的按需解析。
- `virtual-store-dir` 配到 `node_modules` 之外时，链接的目标不在已发现的根里，依赖读不到。
- 只在 `node_modules` 里重装、受跟踪的文件都没改时，`.pnpm/lock.yaml` 的变化在下次打开项目或依赖读取失败时才发现。
- lockfile 的扫描只认版本 6 和 9；pnpm 以后的格式在支持之前走后备。
