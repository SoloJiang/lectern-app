# ADR 0040：依赖根里的符号链接可以落在同一 worktree 已发现的另一个依赖根里

- 状态：已接受
- 日期：2026-10-21
- 修订：[ADR 0033](0033.md)（「依赖根的读取限制」中「符号链接只在同一生态的同一个根内解析」一条）

## 背景

[ADR 0033](0033.md) 让依赖层为当前子项目的直接依赖建声明闭包的索引，读取限制里有一条：符号链接只在同一生态的同一个根内解析（pnpm 的 `node_modules/x` → `node_modules/.pnpm/…`），目标离开这个根就按读不到处理。

code_intel 的设计审阅发现这条与 pnpm 工作区不合。工作区里，子项目 `packages/app/node_modules/react` 是指向工作区根 `node_modules/.pnpm/react@19.0.0/node_modules/react` 的链接：pnpm 默认把虚拟存储放在工作区根的 `node_modules/.pnpm`，每个子项目的 `node_modules/<名字>` 都指向那里（[pnpm 文档](https://pnpm.io/symlinked-node-modules-structure)）。`packages/app/node_modules` 和根目录的 `node_modules` 是 Node 查找链上的两个根，按「同一个根」的规则，工作区里每个子项目的依赖都读不到，而工作区是 pnpm 的常见用法。

## 决策

- 关键约束：链接按词法解析（相对链接所在的目录，得到相对 worktree 根的路径），目标必须落在同一个 worktree 已发现的某个依赖根之内。已发现的根是子项目 Node 查找链上经 worktree 根的 `SafeRoot::open_dir` 打开的 `node_modules`，打开时路径的任何一级都不是符号链接（ADR 0033 第一条）。之后经目标所在根的 `SafeRoot` 读，读取时不跟随任何符号链接，其余各级不得是符号链接（[ADR 0028](0028.md)）。
- 目标不在任何已发现的根里（`$HOME`、worktree 之外、worktree 里没有作为根打开的目录、另一个 worktree 的根）就按读不到处理，与原规则相同。
- 所以安全性质不变：依赖层读的每个文件都在某个按 ADR 0033 第一条打开的根之内，不读这些根之外的任何东西。被审阅的 agent 能改写 worktree，但它能让链接指向的位置只有本来就允许读的根。
- 根按 worktree 登记：切换当前 worktree 之后，另一个 worktree 的根不再被读，也不是链接的合法目标。根被删掉重建（`npm ci`、删掉重装 `node_modules`）时按登记的路径重新验证、重新打开，具体规则由 code_intel 的设计负责。
- ADR 0033 的其余部分不变：身份（npm 的 lockfile `integrity`，`pnpm-lock.yaml` 和 `yarn.lock` 的项目取清单的后备）、只读的扩展名、限额、存储和分层。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 保持「同一个根」 | pnpm 工作区的每个子项目都读不到依赖 |
| 允许链接指向 worktree 里任何目录 | 被审阅的 agent 可以在 worktree 里放任何文件；只认已经按规则打开的依赖根，范围最小 |
| 为每个链接目标另开一个根 | 多出的根不在 Node 的查找链上，要另一套打开和计数的规则；落在已发现的根里已经覆盖 pnpm 的默认布局 |

## 影响

- `code_intel`：「依赖层」的链接解析按本 ADR 写，根按（worktree、目录）登记并重新验证；测试 `deps_link_into_a_discovered_root_is_read`（工作区子项目的链接指向根目录的 `.pnpm`，经那个根读到）和 `deps_link_outside_the_discovered_roots_is_rejected`（指向已发现的根之外的链接不读，`SafeRoot` 的读取记录里没有那些路径）；见 [code_intel 设计「依赖层」](../design/code_intel.md#依赖层)。
- [ADR 0033](0033.md) 的状态行与索引注明被本 ADR 修订。

## 已知限制

- pnpm 的 `virtual-store-dir` 配到 `node_modules` 之外时，链接的目标不在已发现的根里，依赖读不到。
