# ADR 0033：依赖源码按需解析、空闲时只索引直接依赖；后台工作可以在交互时让路

- 状态：已接受，「依赖根的读取限制」中符号链接只在同一个根内解析一条已被 [ADR 0040](0040.md) 修订（链接可以落在同一 worktree 已发现的另一个依赖根里）；「两类只存内存的批量工作」中空闲预取「排在第 3 层之前」已被 [ADR 0041](0041.md) 修订（至多等每个批量线程正在运行的一批和一个窗口任务，名义约 400 ms，p95 ≤ 500 ms）
- 日期：2026-10-18
- 修订：[ADR 0029](0029.md)（「已知限制」中暂停开关只供测量一条；四条条件之外增加两类只存内存的批量工作）

## 背景

产品要求：跳转用到的依赖文件（如 node_modules）可以异步解析，解析要充分利用空闲时间。建索引不区分电源，见 [ADR 0032](0032.md)，本 ADR 不涉及电源。

现有规则：被忽略的目录不进文件列表、不建索引、不监听（[技术调研「排除的功能」](../design/tech-research.md#排除的功能)）；导航第 3 层「依赖源码」按需（[ADR 0007](0007.md)）；可暂停的后台工作在批量线程上运行，kernel 有一个只供测量使用的全局暂停开关（[ADR 0029](0029.md)）。

[大文件与渲染调研](../research/large-files-rendering.md)第 1、2 节实测（Linux 容器）：

- 一个 21 个直接依赖的 Vite + React + TS 项目，`node_modules` 有 244 个包、10,053 个文件、116 MiB；直接依赖从类型入口出发、沿相对 import 走到的声明文件（声明闭包）合计约 5 MiB、250 个文件。Next.js 项目的 `node_modules` 有 337 MiB，声明闭包 3.8 MiB。
- 读文件加求 blob OID（sha1dc）约 430–570 MiB/s；`lstat` 每个文件 1.9–3.9 µs。
- 主线程每帧 2 ms 的工作，另有 1 个普通优先级的解析线程时 p99 从 5.1 ms 变成 6.5 ms；3 个线程占满这台 4 vCPU 的共享虚拟机时出现过一次 114 ms。生产配置是 utility QoS、`clamp(核数 / 4, 1, 3)` 个批量线程，没有在 M 系列上测过。

## 决策

**依赖源码**

- 依赖目录（`node_modules`、Cargo 的 registry 源码、Go 模块缓存、项目里的 Python 虚拟环境）不整体索引、不列出、不监听，规则不变。
- 按需：跳转的 import 解析（`code_intel` 的解析扩展点，TS 由 #19 实现）把裸模块名解析到依赖根里的声明文件时，当场读取和抽取，持有 `BusyGuard`、在 `Interactive` 上运行，计入查询的预算。
- 空闲时：当前子项目清单里的直接依赖，从声明入口出发、沿相对 import、re-export 和 `/// <reference path>` 走到的文件，作为批量层的「依赖层」建索引，排在第 4 层之后、第 5 层之前，所以不占用 [ADR 0031](0031.md) 为 `app/index_100k` 留的余量。它满足 ADR 0029 的四条条件，持有 `BackgroundGuard`。依赖的依赖不建索引，只按需解析。
- 限额：每个包的闭包最多 4,000 个文件、16 MiB，单个文件最多 1 MiB；每个项目的依赖层最多读 64 MiB 源码。
- 存储：抽取结果写进项目分库的新命名空间 `code_intel.deps`，与项目文件的 `code_intel.tags` 分开计 LRU 和配额。`code_intel.deps` 的配额 32 MiB，从 `code_intel` 原来的 256 MiB 里划出（`code_intel.tags` 改为 224 MiB），两者合计仍是 256 MiB，hunk 缓存至少保留 256 MiB 的约定不变。依赖的单元只淘汰依赖的单元。包的（相对路径、OID）表作为同一命名空间里的条目存放。
- 键：被忽略的文件没有 index 的 OID，按 git 的 blob 格式对内容求哈希（与文件夹项目相同，ADR 0030），单元的键与项目文件相同（OID、语言、grammar 版本、查询版本）。包的身份决定是否重读：lockfile 的 `integrity`、`Cargo.lock` 的 `checksum` 或 git 提交、`go.sum` 的哈希、`*.dist-info/RECORD` 的 OID，都没有时取包清单的 OID。身份不变时不读、不 stat；身份变了或取不到时，按（设备号、inode、大小、修改时间、状态改变时间）的 stat 表跳过没变的文件。跳转打开目标文件时按读到的字节重新求 OID，与记下的不同就当场重新抽取。
- 失效：受跟踪的 lockfile 和清单的变化（`fs_watch` 照常交付）、打开项目时的身份检查、跳转时的读取核对。依赖目录本身仍不监听。
- 放在核心的 `code_intel` 里，不做成插件：不新增依赖，TS / JS 是核心语言（ADR 0018）。Java 的 `-sources.jar` 要 zip 解码器，按 ADR 0007 和 #26 决定归属，键、身份、配额、读取限制和分层沿用本 ADR。

**依赖根的读取限制（关键约束）**

威胁模型与 AGENTS.md「Review guidelines」相同：被审阅的 agent 和它启动的进程可以任意改写工作区，包括把 `node_modules` 或 `.venv` 换成指向 `$HOME` 的符号链接、在 `package.json` 里写 `"types": "../../.ssh/id_ed25519"`、在依赖目录里建指向别处的链接。依赖层不能因此读到允许范围之外的文件。

- 工作区之内的依赖根（`node_modules`、`.venv`、`vendor/`）从工作区根的 `SafeRoot` 以不跟随符号链接的方式打开（新增的 `SafeRoot::open_dir`，路径的任何一级是符号链接都失败），不按路径另开 `SafeRoot`。
- 工作区之外只允许依赖缓存里的源码子树，路径由 Lectern 自己进程的环境得到（项目文件里写的路径不算，不为取路径运行外部命令）：`$CARGO_HOME/registry/src`、`$CARGO_HOME/git/checkouts`、`$GOMODCACHE` 里 `cache/` 之外的部分、`~/.m2/repository`、`~/.gradle/caches/modules-2/files-2.1`。不打开 `$CARGO_HOME`、`~/.m2`、`~/.gradle` 本身，所以 `credentials.toml`、`settings.xml`、`gradle.properties` 不在任何根里。
- 包内的路径（`types`、`exports`、import）按词法相对包目录解析，结果离开这个依赖根就丢弃。符号链接只在同一生态的同一个根内解析（pnpm 的 `node_modules/x` → `node_modules/.pnpm/…`），目标离开这个根就按读不到处理；解析后的路径仍经这个根的 `SafeRoot` 读取，其余各级不得是符号链接（[ADR 0028](0028.md)）。
- 只读声明和源码的扩展名：TS 的 `.d.ts`、`.d.mts`、`.d.cts`、`.ts`、`.tsx` 和 `package.json`；Rust 的 `.rs` 和 `Cargo.toml`；Go 的 `.go` 和 `go.mod`；Python 的 `.py`、`.pyi` 和 `RECORD`。其他文件不读。

**交互时让路**

- 交互静止：300 ms 内没有键盘、鼠标按键、滚轮（含惯性）和拖拽，没有运行中的 `ui` 动效，executor 没有排队或在途的 `Interactive` 任务。由 `app` 在 UI 线程上判断。
- kernel 在测量用的暂停开关之外增加一个全局的让路开关。打开时，第 4 层、依赖层、第 5 层和下文两类只存内存的批量工作让路；第 3 层（当前子项目）不让路。让路的工作：
  - 在途的那个文件在下一个分片边界停下、保留状态，不放弃：解析用可恢复的分片解析（调研实测恢复后的树与一次解析相同），一次遍历抽取在节点计数的检查点停下。不能恢复的抽取（语言包的 tree-sitter-tags）放弃这一项，交互静止后重做。
  - 之后只在保活时段里前进：全局同一时刻最多一个时段，每个最长 50 ms，相邻两个时段的开始至少相隔 500 ms；时段里只做一个文件，超过 256 KiB 的文件等交互静止。所以开关打开期间，无论有几个批量线程，批量层合计最多用一个核的 10%，连续滚动时第 4、5 层仍在前进。
  - 不改变「静止」和后台工作状态的报告，`Kernel::pause` 的语义和 bench 的采样不变。
- 默认关闭：让路开关和交互静止的判断随实现进入代码，但 `app` 只在 macOS 上的 `app/scroll_frames_indexing`（批量层有工作时滚动，预算与 `app/scroll_frames` 相同）不让路就超标时才启用它，启用的条件由这个基准校准。基准不让路就通过时，开关保持关闭。
- 索引覆盖的预算（ADR 0030）和测量方式不变；另加只记录的 `app/index_100k_interaction`（建索引期间按脚本滚动）。

**两类只存内存的批量工作**

它们不满足 ADR 0029 第二条（结果按 OID 写入 `cache`），作为有上限的例外：持有 `BackgroundGuard`、只在批量线程上运行、受让路开关约束，结果只进 `file_reader` 已有的 8 MB 高亮与文本 LRU，暂停、取消或退出最多丢掉在途的一项，丢了在用到时现算。

- 空闲预取：交互静止时预先算出审阅集合的下一个未看文件、抽屉里第一个候选的文件、跳转唯一候选的目标文件的高亮区间，每次进入交互静止最多 4 个文件，排在第 3 层之前。
- 打开的大文件的整文件高亮：[ADR 0034](0034.md) 档位 B、C 里可见窗口前后各一个之外的窗口，每个文件同时最多一个任务。

首帧之前不做任何一项：没有打开的项目就没有依赖层、预取和打开的文件（ADR 0017）。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 整体索引 `node_modules` | 实测是直接依赖声明闭包的 24 倍，99% 不会被跳到；还要监听被忽略的目录 |
| 监听依赖目录 | 与「不监听被忽略的目录」冲突；`npm install` 一次写上万个文件；lockfile 已经反映了几乎全部变化 |
| 依赖层排在第 3 层之后 | 占用 `app/index_100k` 的余量；跳转进依赖已由按需解析覆盖 |
| 依赖的单元与项目文件共用 `code_intel.tags` | 单元没有来源字段，32 MiB 的上限无法计数；10 万文件的仓库本来就超过配额，依赖会挤掉项目自己的单元 |
| 交互时用测量用的暂停开关 | 它放弃在途的文件，连续滚动会让一个大文件反复重做；还会改变 bench 读到的后台状态 |
| 让路时完全停下 | 连续交互时第 4、5 层可以无限期不前进 |
| 让路时每个线程每 500 ms 跑一个普通批次 | 批次只在文件边界结束，一个文件可以跑到 250 ms 的截止时间，3 个批量线程时约占每 500 ms 的一半 |

## 已知限制

- lockfile 被忽略或不存在的项目，只在打开项目和跳转时发现依赖的变化。
- 手工改过的依赖文件，在被跳转打开之前，索引里的位置可能过期。
- Python 只支持项目目录里的虚拟环境，不支持全局的 site-packages；`$GOMODCACHE` 等缓存路径被设成符号链接时按用户的配置跟随，这些路径不在被审阅的 agent 可写的范围里。
- 让路对帧时间的效果只在 Linux 虚拟机上间接测过，是否需要启用由 macOS 上的基准决定。
