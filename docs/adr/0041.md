# ADR 0041：语法高亮放在非插件的领域库 `syntax`，核心高亮语言补上 JSON、YAML、TOML、Markdown 的 grammar

- 状态：已接受
- 日期：2026-10-21
- 修订：[ADR 0033](0033.md)（「两类只存内存的批量工作」中空闲预取「排在第 3 层之前」：改为至多等每个批量线程正在运行的一批和一个窗口任务）

## 背景

[ADR 0034](0034.md) 规定高亮的计算放在领域层、视图只读快照，「具体放在哪个 crate 由 `file_reader` 的设计文档决定」。使用方有三个：`file_reader`（完整文件阅读与编辑，[#10](https://github.com/SoloJiang/lectern-app/issues/10)）、`review_view`（diff 两侧按窗口的高亮）、`code_intel`（与高亮共用 grammar 和 tree-sitter 版本，[code_intel 设计「对其他 crate 的要求」](../design/code_intel.md#对其他-crate-的要求)）。`code_intel` 和 `file_reader` 都是插件 crate，插件之间不能直接依赖，视图也不能依赖插件 crate（架构规则 7，[ADR 0025](0025.md)）。

[ADR 0018](0018.md) 的核心（随安装包）包括 TypeScript / JavaScript、Rust、Java、Python、Go、JSON、YAML、TOML、Markdown 的语法高亮。工作区现在只有 `code_intel` 用的前六种 grammar（[ADR 0030](0030.md)，`=` 锁定在 `[workspace.dependencies]`）。

[#42](https://github.com/SoloJiang/lectern-app/issues/42) 指出 tree-sitter 的进度回调打断不了手写的 external scanner：scanner 卡在循环里时，首屏 8 ms 的截止时间不是真正的上限。code_intel 设计要求高亮方对 scanner 的处理同样作用于 `code_intel`。

## 决策

**`syntax` crate**

- 新建 `lectern-syntax`：领域层、普通的库 crate，不实现 `Plugin`，不依赖 GPUI。它负责高亮的语言表与查询、首屏窗口与安全位置的规则、整文件与按窗口的解析、着色区间、文本存储与行索引、行检查点（`syntax.lines`）、8 MiB 的高亮与文本 LRU、[ADR 0033](0033.md) 的两类只存内存的批量工作（空闲预取、大文件的整文件高亮），以及编辑模式的增量高亮。
- 依赖方向：`file_reader`、`review_view` 和 `code_intel` 都可以依赖它（视图依赖领域库；插件依赖非插件的库），它不依赖任何插件 crate。IO 只经 `platform`（读）和 `git`（对象库、blob 哈希），派生数据按 OID 进 `cache`。
- 高亮用 tree-sitter 0.27.1 的 `Query` 与 `QueryCursor::set_byte_range`，不引入 `tree-sitter-highlight`，不做语言注入。查询文件随 crate 存放，查询版本进缓存键，规则与 ADR 0030 的抽取键相同。
- 编辑模式的 gpui-component `InputHighlighter` 适配器在 `file_reader`；它把缓冲区复制成快照交给 `syntax`，`syntax` 不依赖 ropey 和 gpui-component。

**新增的 grammar**

| crate | 版本 | 说明 |
|---|---|---|
| `tree-sitter-json` | `=0.24.8` | ADR 0034 的实测用的同一版本 |
| `tree-sitter-yaml` | `=0.7.2` | 带 external scanner |
| `tree-sitter-toml-ng` | `=0.7.0` | 带 external scanner |
| `tree-sitter-md` | `=0.5.3`，不开 `parser` feature | 只用块级 grammar，它带 external scanner；`parser` 会带进 tree-sitter 0.26 |

四个都是 MIT，正常依赖只有 `tree-sitter-language`（已在 Cargo.lock）和构建期的 `cc`。版本取 ABI 落在 tree-sitter 0.27.1 支持范围内的版本，与现有 grammar 一样在 `[workspace.dependencies]` 用 `=` 锁定，由测试对照 Cargo.lock 和 ABI 范围；升级单独提 PR。体积计入 ADR 0018 的 80 MB，由 [#38](https://github.com/SoloJiang/lectern-app/issues/38) 测量。

**external scanner 的处理（关键约束）**

- 解析和高亮查询只在 executor 的线程上运行，UI 线程从不等它：首屏窗口过了 8 ms 就先画没有高亮的文本（ADR 0034），所以卡住的 scanner 不会卡住界面。
- 只有正在某个线程上运行的解析调用登记在 `syntax` 的进程级健康表里（语言、grammar 版本、这次调用的预算、这个线程的 CPU 时钟）。登记在进入 tree-sitter（或 tree-sitter-tags）之前、在调用的线程上进行，调用以任何结果返回（完成、分片用完、让路停下、`code_intel` 的 `Parked`、取消）时注销；停下等待期间不在表里，续做时以剩余的预算重新登记，不沿用最初的截止时刻。所以分片、让路和暂停不会被当成卡住。
- 判定用线程的 CPU 时间（`platform` 提供，macOS 的 `thread_info`、Linux 的 `pthread_getcpuclockid`）：一次调用自登记以来用掉的 CPU 时间超过它的预算加 1 s，下一次为同一 grammar 版本登记时就把这个版本在本次运行中停用，之后这种语言只显示纯文本，`code_intel` 也不再为它提交抽取和解析。线程在 utility QoS 下被并发的构建挤掉时 CPU 时间不增长，不会误判；读不到 CPU 时钟时按墙上时间、宽限 10 s。被占住的线程等 scanner 自己返回，不强行终止。
- 只适用于静态链接、经过审查的核心 grammar（ADR 0018 要求 scanner 只做纯计算）。语言包的 grammar 按 #39 / #40 的设计处理，加载器给出的 grammar 同样登记在这张表里。

**批量线程上的先后（修订 ADR 0033 的「排在第 3 层之前」）**

`executor` 的 `Batch` 队列先进先出。`code_intel` 每个批量线程上有一个长期任务，它已经在每个批次边界调用 `yield_now()`、重新入队（`code_intel` 的批量循环，第 7 步已合并），所以排在队列里的其他 `Batch` 任务至多等每个线程正在运行的一批。决定：

- `syntax` 的批量工作都用普通的 `Batch`，不给 `executor` 加新的优先级。空闲预取同一时刻至多一个任务、一个任务一个文件（≤ 1 MiB 的整文件或第一屏的窗口）；大文件的批量窗口同一时刻至多一个任务、一个任务至多一个窗口、50 ms 的解析，之后重新入队。
- 等待的上限（关键约束）：队列和线程上至多有 N 个 `code_intel` 任务（N 是批量线程数）、一个窗口任务和一个预取任务。一批是抽取的循环（开始 50 ms 之后的第一个文件边界结束，那个文件至多到后台的 250 ms 截止时间，看门狗每 10 ms 检查一次）加一次提交（至多一次 `canonical_oids` 的 index 解析，10 万文件约 22 ms，和一个写事务），约 350 ms。预取入队后至多等每个线程上的一批加一个窗口任务（≤ 50 ms），名义约 400 ms；`syntax/prefetch_wait` 在真实的 `code_intel` 建索引时测量，按 p95 ≤ 500 ms 判定，最大值只记录。`code_intel` 重新入队时可以带着它停下的项（含超过 256 KiB 的一项的 `LargeSlot`），任务数不变；让路的等待方至多阻塞 N − 1 个批量线程，持有者总有一个线程可用（`syntax` 的批量任务从不等 `LargeSlot`），论证在 file_reader 设计「批量线程上的先后」。
- 这是对 [ADR 0033](0033.md)「空闲预取……排在第 3 层之前」的修订：预取不插到已经入队的第 3 层批次前面，改为「至多等每个批量线程正在运行的一批和一个窗口任务（名义约 400 ms，p95 ≤ 500 ms）」，期间第 3 层至多前进这一批。理由：预取在交互静止（300 ms 没有输入）时才发出，算的是用户下一步可能要看的文件，晚几百毫秒开始通常仍在下一个动作之前；严格的先后要给 `executor` 加一级优先级（下表），这一点等待不值得。

**放弃的方案**

| 方案 | 原因 |
|---|---|
| 高亮放在 `code_intel` | 它是插件 crate，`file_reader`、`review_view` 不能依赖它；它的常驻份额也不含高亮 |
| 高亮放在 `file_reader` | `review_view` 要依赖另一个视图插件；领域逻辑放在依赖 GPUI 的 crate 里，Linux CI 测不到 |
| 引入 `tree-sitter-highlight` | 它按整棵树和注入层工作，窗口、截止时间和按行存放的区间都要另写；多一个依赖 |
| 只带 `code_intel` 的六种 grammar | 与 ADR 0018 的核心语言不一致，审阅里常见的 `package.json`、CI 配置、`Cargo.toml`、README 没有高亮 |
| 为 scanner 单开看门狗线程，或把解析放到独立进程 | 界面不等解析，提交时检查已经能阻止更多线程被占住；独立进程超出一帧的预算（ADR 0018） |
| 按墙上时间、从最初的截止时刻判定卡住 | 分片、让路和暂停的调用会被算成卡住；批量线程是 utility QoS，被并发的构建挤掉时墙上时间照走，正常滚动或编译时会把一种语言误停用整个运行 |
| `executor` 加一级批量线程先取的 `Priority::BatchFront`，给预取用 | 严格做到「排在第 3 层之前」，但只省下至多一批（约 350 ms，含提交）的等待；要改已实现的 `executor` 接口和调度，多一种优先级要测；窗口链若也用它，每个窗口都插到 `Batch` 之前，64 MiB 的文件会让第 3 层停十几秒 |

## 影响

- 新 crate `crates/syntax`（`AGENTS.md`、`CLAUDE.md` 软链接），设计在 [file_reader 设计](../design/file_reader.md)；[cargo-workspace 设计](../design/cargo-workspace.md)的 crate 表随 crate 的第一个 PR 加一行。
- 根 `Cargo.toml` 加四个 grammar，`just deny` 覆盖。
- [cache 设计「命名空间」](../design/cache.md#命名空间)：`syntax.lines` 的使用方是 `syntax`。
- [code_intel 设计](../design/code_intel.md)：「不做」里的高亮一条和「对其他 crate 的要求」的高亮方一条指向 `syntax`；一个 PR 补测试，固定批量循环在批次边界重新入队（预取的前提，行为已实现），之后的一个 PR 让抽取和解析登记在健康表里。
- `executor` 不改。`platform`：线程的 CPU 时钟。
- [ADR 0033](0033.md) 的状态行和索引注明「排在第 3 层之前」被本 ADR 修订。
- [技术调研](../design/tech-research.md)的 crate 表加 `syntax`。

## 已知限制

- 卡住的 scanner 会一直占着一个 executor 线程，直到它返回。
- Markdown 只高亮块级结构；行内元素和注入的语言不高亮。
