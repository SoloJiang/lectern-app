# ADR 0026：会话日志按追加前缀增量解析，解析结果以会话和已解析前缀为键缓存

- 状态：已接受
- 日期：2026-10-17

## 背景

`agents` 要从 Claude Code 和 Codex 的会话日志里交出轮次结构、工具调用事件和原始用量（[ADR 0014](0014.md)、[ADR 0020](0020.md)），设计见 [agents 设计](../design/agents.md)。三个约束决定了读取方式：

- 日志很大，并且一直在增长。本机一个连续工作了两天的 Claude Code 会话有 56 MB、约 1600 次工具调用；「打开一个会话的 Diff < 50 ms」（[性能预算](../design/tech-research.md#性能预算)）不允许打开时重新解析整个文件，空闲内存预算（[ADR 0017](0017.md)）不允许整文件读入内存。
- 架构规则 5 要求派生数据以 git blob OID 为键缓存，目的是内容不变就不重算、内容变了一定失效。会话日志在 git 之外，没有 blob OID。
- Codex 把冷的会话文件压缩为 `.jsonl.zst`（`codex-rs/rollout/src/compression.rs`），ADR 0014 要求两种都读。

技术调研的草案写的是「`serde_json::Value` 加适配器」和直接用 `notify` 监听，本 ADR 取代这两点。

## 决策

**增量读取**

- 两种 agent 都只追加写日志。读取只消费到最后一个换行，记下游标：解压后的字节偏移、偏移之前的 256 字节原样副本、解析器的状态。下次从偏移继续读，先比较这 256 字节；不同就当作文件被改写，从头读并告诉消费方重置。
- 游标由消费方保存，本 crate 不替消费方记进度：`usage` 把游标和记录写进同一个事务，重启后从自己的游标继续。
- 每次读取的字节上限是软上限：只要游标之后有完整的行，至少消费一行；超过 16 MB 的行不进内存、跳过并计数，游标越过它。所以每次读取要么到了末尾，要么游标前进。
- 偏移按解压后的内容计，文件被压缩成 `.zst` 之后游标照样有效。

**压缩会话的随机读取**

- Codex 把整个冷文件压成一个 zstd 帧，没有可以定位的帧边界。顺序读取照样流式解码；需要按偏移读一行时（打开会话、读正文），第一次把它完整解压成应用缓存目录下的只读副本，之后在副本上按偏移读。
- 副本以（来源 ID、会话 ID、压缩文件的设备号、inode、大小、修改时间）为键，全部副本合计上限 1 GB，按最后访问时间做字节 LRU，可以随时删除重建；内存里不保留副本内容。压缩文件的会话摘要以（文件身份、适配器版本、摘要格式版本）为键存进 `cache`，启动时不再解压。
- 发现不等待整份解压：没有缓存摘要的压缩文件先用开头和 `stat` 生成摘要并发布，取自末尾的字段标为待定，由后台任务补齐后再发布。
- 放弃：记录帧边界（只有一个帧）；把被引用的每一行正文存进轮次索引（大小接近原文件，还要进 SQLite 和内存）。

**缓存键**

- 轮次索引这类从日志派生的数据，以（来源 ID、会话 ID、适配器版本、索引格式版本）为键存进 `cache`，值里带生成它时的游标。读取时用游标的前缀比较判断是否仍有效：有效就只解析游标之后追加的部分，无效就整份重建。
- 这是架构规则 5 在 git 之外的对应做法：判断依据是已解析部分的内容（偏移加末尾字节），不是文件的修改时间或大小。规则 5 对 git 内容的要求不变。

**解析与依赖**

- 每行用 `serde_json` 反序列化到只声明用到字段的结构，字符串借用原行；不先转成 `serde_json::Value`：`Value` 为每个字段分配内存，而工具结果里常有整份文件内容。字段缺失、类型不认识的记录跳过并计数，不报错退出。
- `.jsonl.zst` 用 [ruzstd](https://crates.io/crates/ruzstd) 解码（MIT，纯 Rust 流式解码器）。
- 时间戳是固定格式的 RFC 3339 UTC，手写解析，不引入 `chrono` 或 `time`。
- 目录监听走 `fs_watch` 的接口（macOS 后端在 `platform`），不在 `agents` 里直接用 `notify`。

放弃的方案：

- 每次启动、每次打开都重新解析：大会话超出 50 ms 预算，并且每次启动都要把全部历史重读一遍。
- 按文件的修改时间和大小判断缓存是否有效：改写后大小可能不变，修改时间可能被同步工具改动，判断不了内容。
- 对整个已解析前缀求哈希：每次追加都要重读整个文件，失去增量读取的意义。
- `zstd` crate：绑定 C 库，需要 C 编译链，体积更大；这里只需要解码冷文件，速度不是瓶颈。

## 影响

- `agents`：游标、适配器和缓存键的细节在 [agents 设计](../design/agents.md)。
- `cache`：提供不属于任何仓库的应用级分库存会话的轮次索引和压缩会话的摘要（`crates/cache/AGENTS.md`）。
- `app`：把 `platform` 提供的应用缓存目录下的 `agents/decoded/` 交给 `agents` 存解压副本。
- `fs_watch`：提供不按 git index 过滤的递归目录监听（`crates/fs_watch/AGENTS.md`）。
- `usage`：按 `agents` 交出的游标续读，和记录在同一个事务里落盘。
- `bench`：解析吞吐、追加读取、带缓存打开大会话的基准（[#7](https://github.com/SoloJiang/lectern-app/issues/7)）。
- [技术调研「Agent 项目发现」](../design/tech-research.md#1-agent-项目发现)的草案说明随本 ADR 修改。

## 已知限制

- 文件中间被改写、末尾 256 字节恰好不变时发现不了；两种 agent 都只追加写，不专门处理。
- `.zst` 不能从中间开始解压，顺序续读压缩文件要从头解压到游标；只有冷文件被压缩，很少续读。
- 第一次打开一个压缩会话要解压整个文件，超出「打开一个会话的 Diff < 50 ms」，界面显示骨架或进度；副本建好之后的打开在预算内。
