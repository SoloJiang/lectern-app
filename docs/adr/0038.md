# ADR 0038：工作区比较在一次调用内用至多 4 个作用域线程并行 stat

- 状态：已接受
- 日期：2026-10-20

## 背景

[git 设计「数据流与线程」](../design/git.md#数据流与线程)规定本 crate 的函数在调用方的后台任务线程上运行、不建线程。10 万个跟踪文件的干净比较（`git/changes_clean_100k`，< 2 s）在 macOS CI 上约 3.7 s，按阶段（[#133](https://github.com/SoloJiang/lectern-app/pull/133)）：读基准树 1.84 s、每个跟踪路径一次 `SafeRoot::stat` 1.15 s、未跟踪遍历 645 ms；index 解析、分类都在 20 ms 以下。fs_watch 重建过滤器（`git/filter_100k`，< 400 ms）在 macOS 上 678–766 ms，其中目录遍历一项 473 ms。

读基准树由 index 的 cache-tree 跳过（git 设计「工作区比较」），不需要线程。剩下的两项是逐个路径、逐个目录的系统调用：macOS 上一次 stat 约 11 µs，一次列目录约 13 µs。git 的 `core.preloadIndex` 出于同样的原因用多个线程做 stat。

## 决策

- 工作区比较对每个跟踪路径的 stat 一遍可以在一次调用内用 `std::thread::scope` 起线程，连同调用线程至多 `min(CPU 数, 4)` 个，调用返回前全部 join。不跨调用保留线程，不建线程池。
- 关键约束：
  - 结果按输入顺序合并，改动集与串行时完全相同，与调度无关。
  - 只把只读的 `SafeRoot::stat` 放到其他线程。gix 句柄、index 和比较的判定仍在调用线程上（gix 句柄不是 `Send`，[ADR 0024](0024.md) 不变）。
  - 规模小时串行：每个线程至少 2048 个路径。
  - 取消标志在每个线程上检查；panic 传回调用线程。
- 未跟踪遍历的目录列举（比较和 fs_watch 过滤器共用）仍串行。试过在其他线程上预先列出遍历已经决定进入的目录：Linux 上 10 万文件的遍历从 279 ms 变成 584 ms，过滤器从 266 ms 变成 574 ms。每个目录的列举只有几微秒，跨线程交接（锁、唤醒、按路径查表）的开销比它大。遍历要降下来，得减少要列的目录（如 git 的 untracked cache 按目录的 mtime 跳过），另行决定。
- 放弃：
  - 经 `executor` 提交：`git` 不依赖 `executor`；调用方本身就在一个工作线程上等待，嵌套提交的任务会排在别的任务后面，在工作线程占满时还可能互相等待。
  - rayon 一类的全局线程池：新依赖，线程常驻，违反「无常驻运行时」和空闲内存预算。
  - 打开 gix 的 `parallel`：ADR 0024 关闭它，是为了句柄不跨线程、不常驻线程。

[ADR 0029](0029.md) 的批量线程组管可暂停的长时间后台工作；比较是调用方任务的一部分，它的线程随调用结束，两者不冲突。

## 影响

- `git`：`parallel.rs`（有序的分块并行）用于 stat 一遍；git 设计「数据流与线程」「工作区比较」「性能」随同修改。
- 其他 crate 的接口不变。

## 已知限制

- 作用域线程不设 QoS（设置 QoS 是 macOS 的系统调用，只能在 `platform`，架构规则 6），macOS 上它们按系统默认的 QoS 运行，不一定继承调用线程的 QoS。
- 调用期间至多多出 3 个线程（每个 2 MiB 虚拟栈），与同时运行的其他 CPU 密集工作争用核心。
