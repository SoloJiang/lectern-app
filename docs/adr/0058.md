# ADR 0058：`terminal/input` 的预算由 ≤ 2 µs 改为 ≤ 6 µs，因为唤醒一个睡着的线程的系统调用要 3 µs 以上

- 状态：已接受
- 日期：2026-10-31
- 修订：[terminal 设计「性能」](../design/terminal.md#性能)（`terminal/input` 的预算）

## 背景

[terminal 设计](../design/terminal.md)给 `terminal/input` 的份额是中位数 ≤ 2 µs：主线程上的一次 `Terminals::input`，即把输入放进队列、向终端线程的唤醒 socket 写一个字节。这个数在设计阶段没有测过。第 3 步实现了被测的代码，按设计的做法（终端线程 `poll` 主端 fd 和唤醒 socket，空闲时无限期阻塞），本机（Apple M5 Pro、macOS 27.0.1）的实测：

- `terminal/input`：中位数 3.6–3.9 µs（多次运行；安静时有过两次 1.5、1.7 µs，之后没有再出现）。
- 其中主要是唤醒的代价，不是本 crate 的其他工作。对照（一个线程睡在 `poll` 上，另一个线程写一个字节，每次之间睡 200 µs 让它重新睡下）：socketpair 中位数 3.1–3.8 µs（p95 5.3–7.3 µs），pipe 2.3–2.8 µs，`kqueue` 的 `EVFILT_USER` 触发 1.9–2.0 µs。没有线程在等时，同一次 socket 写只要 0.33 µs。入队、查表、`Arc` 克隆合起来不到 1 µs。

这一项不是 [ADR 0055](0055.md) 的放宽：0055 针对「没有改动被测代码的 PR 上反复超标的份额预算」，而这个 PR 引入了被测的代码，数字是物理上的唤醒代价，不是噪声。

## 决策

- `terminal/input` 的预算由中位数 ≤ 2 µs 改为中位数 ≤ 6 µs。实测最差约 3.9 µs，6 µs 留约 50% 的余量，托管 runner 上虚拟化的唤醒更慢。
- 保持设计的做法：终端线程 `poll` 主端 fd 和唤醒 socket。放弃的方案：
  - 唤醒改用 pipe：约 2.5 µs，仍然超过 2 µs，只省 1 µs。
  - 改用 `kqueue` 加 `EVFILT_USER`：约 1.9 µs，加上入队的不到 1 µs 仍不保证 ≤ 2 µs，而且要改设计里「数据流与线程」的 `poll` 循环和唤醒 socket。
  - 让终端线程在输入之后自旋一小段时间，使连续的输入不必唤醒：只对连续输入有效，每次打字停顿之后的第一个输入仍要唤醒，而且空闲时烧 CPU（性能是第一约束）。
- 这个数在 CI 上要复核：托管 runner 是虚拟机，睡着的线程的唤醒延迟可能更大。复核的结果超过 6 µs 时，按实测另写 ADR，不再用 0055。

## 影响

- `lectern-bench` 的 `budgets.rs`：`terminal/input` 的 `Limit::TimeAtMost`。
- [terminal 设计](../design/terminal.md)「性能」的基准表、「实际验证」「与设计的差异」；[bench 设计](../design/bench.md)的预算表。
- 帧、回显和启动的预算不变（`terminal/echo_latency` 实测中位数 80–160 µs，含同样的一次唤醒）。

## 已知限制

- 6 µs 是在一台机器上测的；睡着的线程落在哪个核、核是否在深度空闲，会让同一台机器上的数在 1.5 µs 到 3.9 µs 之间变化。
