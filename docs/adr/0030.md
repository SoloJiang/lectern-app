# ADR 0030：代码导航用 frizbee 模糊匹配、tree-sitter-tags 抽取符号，导航延迟列为顶层预算

- 状态：已接受，「符号抽取」已被 [ADR 0031](0031.md) 修订；「内存与磁盘的目标份额」里 10 万文件形状的份额之和改为对照 [ADR 0035](0035.md) 的 `app/idle_100k`（< 120 MB），已被它修订
- 日期：2026-10-17

## 背景

产品要求浏览文件和代码跳转足够快。[代码导航调研](../research/code-navigation.md)比较了模糊匹配和符号索引的实现，给出了各交互的延迟目标。依赖选型和顶层预算的改动都要写 ADR（AGENTS.md「禁止事项」、[bench 设计「预算表」](../design/bench.md#预算表)）。

约束：

- 后台线程只由 `executor` 管理（[executor 设计](../design/executor.md)）。唯一的例外是 `git` 工作区比较的 stat 一遍，见 [ADR 0038](0038.md)；它与下文放弃的 `match_list_parallel`、`nucleo` 的区别也写在那里。
- 只允许宽松许可证，`cargo-deny` 拒绝 GPL（架构规则 8）；不引入 WASM 宿主（架构规则 3）。
- 派生数据以 blob OID 为键缓存（架构规则 5），存进 `cache` 的 SQLite（[ADR 0027](0027.md)）。
- 安装包 ≤ 80 MB（[ADR 0018](0018.md)），打开 monorepo 空闲 < 100 MB（[ADR 0017](0017.md)）。

调研的实测（Linux 容器，Xeon 2.1 GHz，只用于比较方案的量级）：

- 14 万条路径：frizbee 0.13.0 单线程 0.8–6.1 ms、4 线程 0.6–3.8 ms，nucleo-matcher 单线程 6.7–26.0 ms；98 万条路径 frizbee 4 线程 3.5–23.1 ms。
- tree-sitter 0.27.1 加 tree-sitter-tags 0.27.1 抽取 Rust 单线程约 4.3 MB/s；SQLite B-tree 按名字精确或前缀查找 < 0.1 ms。

## 决策

**模糊匹配：frizbee `=0.13.0`**

- MIT，没有运行时依赖；可选的 `serde` 不开。根 `Cargo.toml` 的 `[workspace.dependencies]` 精确锁定，升级单独提 PR，跑完匹配的快照测试和 ⌘K 基准后合并。
- 只调用单线程的匹配接口。并行由 Lectern 在 `executor` 上分片：每片一个 `Interactive` 任务，片与片之间检查取消标志，各片取前 k 个后归并。不得调用 `match_list_parallel`，它每次调用都新开操作系统线程。
- frizbee 直接匹配 UTF-8 字节，不做 Unicode 规范化，所以查询和路径进入匹配器前统一成 NFC。
- 匹配、分层和排序属于 ⌘K（[#102](https://github.com/SoloJiang/lectern-app/issues/102)），放在 `code_intel` 还是单独的 crate 由它的设计文档决定。

**符号抽取：tree-sitter-tags `=0.27.1`**

- MIT。它依赖 tree-sitter `^0.27.1`，所以 Lectern 的 tree-sitter 也锁在 0.27.1，两者一起升级；可加载的 grammar 的 ABI 范围随 tree-sitter 版本确定（ADR 0018）。不开 tree-sitter 的 `wasm` feature。新增的传递依赖只有 `tree-sitter-language`（MIT）和 `streaming-iterator`（MIT OR Apache-2.0），`regex`、`memchr`、`thiserror` 已在 Cargo.lock 里。
- 每种语言的 tags 查询随 grammar 分发：核心语言随安装包，语言包里的作为 ADR 0018 的声明式查询文件。
- 抽取结果的键是（blob OID、语言、grammar 版本、查询版本），结果只取决于键里的输入。语言由路径决定：同一份内容放在 `.js` 和 `.ts` 下 OID 相同，解析器和查询不同，所以键里要有语言；grammar 或查询升级后旧结果不再命中。Java 解析器的结果按（blob OID、解析器版本）缓存。文件夹项目没有 git，按 git 的 blob 格式对内容求哈希作为 OID。
- 结果存进 `cache` 仓库分库（文件夹项目用文件夹分库）的自定义表，按名字查找用 SQLite 的 B-tree 索引。⌘K 的符号模糊搜索对去重后的名字数组使用同一个 frizbee。

**不采用的方案**

| 方案 | 原因 |
|---|---|
| Zed `fuzzy` | GPL-3.0-or-later，架构规则 8 不允许，也不得照抄 |
| 高层 `nucleo` | 自带 rayon 线程池，违反「后台线程只由 executor 管理」 |
| `nucleo-matcher` | MPL-2.0 允许使用，Unicode 处理更完整；实测慢 3–4 倍，最后一次发布在 2024-02。作为 frizbee 出问题时的备选 |
| `fst` | 精确和前缀查找 SQLite 已在 0.1 ms 内，模糊查找 frizbee 更快；`fst` 不可修改，增量更新要另做分段合并 |
| SQLite FTS5 trigram | 名字的子串搜索由模糊匹配覆盖；少于 3 个字符的查询用不上；实测让索引文件从 6.1 MB 涨到 11.2 MB |
| 文件内容的三元组索引 | 约为语料的 3.5 倍，不属于审阅闭环的核心；全文搜索按需扫描文件 |
| ctags 表 | 整份重写，没有增量格式，一份表对应一个目录树，与 blob 键不符 |

实测的 SQLite 查找或 frizbee 匹配超出下面的预算时，再评估 `fst` 和 FTS5，写新 ADR。

**延迟预算**

以下预算加入[技术调研「性能预算」](../design/tech-research.md#性能预算)，属于顶层预算。测量条件与现有端到端基准相同：M 系列 Mac，系统文件缓存已热，cloudprint 形状的夹具，另加 10 万文件、20 万条路径和 100 万条路径的合成仓库。分档的预算在档位的上界测量：「20 万条以内」用 20 万条的夹具。「一帧」与「打开文件到首屏高亮」同口径，按 < 16 ms 判定。

| 交互 | 预算 | 基准 |
|---|---|---|
| 打开 ⌘K 到面板和空查询列表显示 | < 16 ms | `app/palette_open` |
| ⌘K 每次按键到结果更新 | 20 万条路径以内 ≤ 16 ms；更大的仓库 ≤ 50 ms，期间保留上一轮结果 | `app/palette_key_200k`、`app/palette_key_1m` |
| 打开 Files（目录表已建好） | < 16 ms；文件列表未就绪时按 100 ms 规则显示骨架 | `app/files_open` |
| 展开目录（子项 2,000 个以内） | < 16 ms | `app/files_expand` |
| 跳转到定义：同文件或索引命中 | 候选列表 ≤ 50 ms；只有一个候选时，目标文件首屏高亮 ≤ 100 ms | `app/goto_candidates`、`app/goto_single` |
| 跳转到定义：索引尚未覆盖 | 第一批结果 ≤ 300 ms；限时搜索 1 s 后停止，从请求到搜索结束（找完或到时停止）、最后一批结果画出 ≤ 1.1 s，其中 0.1 s 是取消和绘制的余量 | `app/goto_unindexed`、`app/goto_unindexed_done` |
| 查找引用、调用方 | 第一批 ≤ 200 ms；10 万文件的仓库全部结果 ≤ 2 s，陆续追加 | `app/references_first`、`app/references_100k` |
| 后退、前进（最近访问的位置） | < 16 ms | `app/nav_back` |
| 索引覆盖范围（后台，接电源） | 审阅集合：打开项目后 ≤ 2 s；当前子项目 ≤ 10 s；10 万文件的整个仓库 ≤ 2 分钟 | `app/index_review_set`、`app/index_subproject`、`app/index_100k` |

索引覆盖范围是由吞吐推出的估算，在 M 系列上实测后校准；改数字仍要写 ADR。bench 预算表加入以上条目，`Tier::Top`、状态为计划中，由 #102（⌘K）、[#10](https://github.com/SoloJiang/lectern-app/issues/10)（Files 与后退、前进）、#17（`code_intel`）和 [#20](https://github.com/SoloJiang/lectern-app/issues/20)（上下文抽屉的查找引用）的实现 PR 加入基准并改为生效。

**内存与磁盘的目标份额**

调研估算的份额作为目标，由 `code_intel` 和 `cache` 的设计文档定为 `Tier::Share` 预算，并说明 monorepo 100 MB 下各份额之和仍在预算内：

- `code_intel` 空闲常驻：cloudprint 形状 ≤ 10 MB，10 万文件 ≤ 20 MB。其中「blob → 路径」映射 1–3 MB；⌘K 名字表 4–8 MB，⌘K 关闭 30 秒后释放；高亮与文本的 LRU 上限 8 MB。
- 目录表约 1 MB（10 万文件），计入 `project`。
- 磁盘上的符号表：cloudprint 形状约 1 MB，10 万文件约 200–250 MB，在 `cache` 的仓库分库内单独计份额，不挤占 hunk 缓存。

## 影响

- 根 `Cargo.toml`：frizbee、tree-sitter、tree-sitter-tags 由第一个用到它们的实现 PR 加入；`just deny` 覆盖新增的传递依赖；体积计入 ADR 0018，由 [#38](https://github.com/SoloJiang/lectern-app/issues/38) 的安装包检查测量。
- [技术调研](../design/tech-research.md)：「性能预算」加入延迟预算；「技术选型」加一行；「代码导航与编辑」第 1 层的可用时机改为分层的覆盖目标。
- `bench`：预算表加入上面的计划中条目；⌘K、Files、跳转和后退的端到端基准要在探针里增加对应的 `OpenTarget` 和 `Milestone`，并生成 20 万条和 100 万条路径的合成仓库，随各实现 PR 加入。`app/goto_unindexed_done` 的里程碑是限时搜索结束：找完全部候选文件或到时停止，且最后一批结果已画出；夹具里未索引的文件要多到 1 s 内搜不完，才能测到停止。
- `code_intel`（[#17](https://github.com/SoloJiang/lectern-app/issues/17)）、⌘K（#102）、Files（#10）和 [cache 设计](../design/cache.md)：匹配、抽取、存储和份额按本 ADR 编写。
- 后台索引与静止的关系见 [ADR 0029](0029.md)。

## 已知限制

- NFC 统一之后，frizbee 对 `İ`、`ß` 这类字符的大小写折叠仍有缺口。
- tags 查询按名字连接引用和定义，没有作用域解析，常见名字更容易跳错；消歧规则见调研第 6 节，由 `code_intel` 的设计文档负责。
- 预算来自 Linux 容器上的实测和估算，M 系列上的校准在实现阶段进行。
