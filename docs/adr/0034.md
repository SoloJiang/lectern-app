# ADR 0034：大文件按窗口解析与高亮，不保留整棵语法树，阅读视图只排版可见行

- 状态：已接受
- 日期：2026-10-18
- 修订：[ADR 0018](0018.md)（「执行时间有上限」一条里 UI 路径上的解析）；[技术调研「技术选型」](../design/tech-research.md#技术选型)的「文本存储：gpui-component Editor」和[「编辑范围」](../design/tech-research.md#编辑范围第三层)的「基于 gpui-component 的 Editor」

## 背景

产品要求打开单个大文件也要很快，并检查渲染侧的瓶颈。现有预算：打开文件到首屏高亮 < 16 ms，滚动与输入稳定 120 fps（[性能预算](../design/tech-research.md#性能预算)），两条都对任何大小的文件成立。

[大文件与渲染调研](../research/large-files-rendering.md)在 Linux 容器（Xeon 2.1 GHz）上用 tree-sitter 0.27.1 实测：

- 整文件解析是线性的，TS 约 6 MiB/s、Rust 4–6 MiB/s、JSON 15–20 MiB/s、压缩成一行的 JS 约 3 MiB/s。1 MiB 的 TS 要 165 ms，64 MiB 要 11–18 s。
- 语法树占输入的 14–41 倍，压缩 JS 47–83 倍：4 MiB 的 TS 是 134 MiB，64 MiB 是 2.1 GiB。
- 解析可以分片：进度回调中止的解析在下一次调用时接着做，得到的树与一次解析完全相同（18 个文件、3 种片长全部相同），分片的额外开销在测量噪声以内。
- 窗口单独解析：文件开头 16 KiB 的窗口 0.7–4.9 ms，高亮与整文件解析逐字节一致；文件中部从启发式的安全位置开始的 14–25 KiB 窗口平均 0.6–6 ms，40 个随机位置里 85–100% 完全一致。整个文件按 64 KiB 的窗口逐个解析再丢弃、下一个窗口从前一个窗口的语法树确认的语句边界开始，总耗时与整文件解析相同，一致率合成文件 100%、真实文件 98.9–100%，同时存在的语法树不超过约 5 MiB。

[gpui-component 0.7.3](https://github.com/longbridge/gpui-component/tree/v0.7.3) 的编辑器（`InputState` 的代码模式）读源码得到（GPUI 在 Linux 上不能构建，未运行）：文本是 ropey 的 Rope；超过 256 KiB 的文件在 150 ms 防抖之后才在后台解析整个文件，之前没有高亮；软换行在 UI 线程上逐行测量整个文件；超过 10,000 字节的行不高亮，但每帧仍把整行复制成字符串再排版；高亮要开它的 `tree-sitter` feature，它依赖 tree-sitter 0.26.13，与 Lectern 锁定的 0.27.1 是两份。GPUI 的坐标是 f32，超过 2^24 像素（行高 18 pt 时约 93 万行）之后滚动位置不再精确到像素。

## 决策

**解析与高亮**

- 不在 UI 线程上解析（AGENTS.md「禁止事项」），也不保留打开文件的整棵语法树。高亮的结果是按行存放的着色区间，进入已有的 8 MB 高亮与文本 LRU；语法树在算出区间后释放。编辑模式例外，见下文。
- 首屏：从可见区域之前的安全位置开始，取覆盖可见行的窗口（不超过 16 KiB 加上可见部分）单独解析，算出可见行的区间后交给视图。窗口解析带 8 ms 截止时间：超时时这一帧先画出没有高亮的文本，解析完成后再上色。安全位置由每种语言的轻量规则给出：第 0 列开始的语句、一行很长时的 `;` 或 `}` 之后、JSON 字符串之外的成员开头（窗口两端补齐括号）。
- 首屏之后按文件大小分三档：
  - 不超过 1 MiB，且没有超过 4 KiB 的行：整文件解析，按 8 ms 一片在 `Interactive` 上运行、片与片之间可以让给别的交互任务，完成后用整文件的区间替换首屏的。
  - 1–16 MiB，或有超过 4 KiB 的行：从文件开头按约 64 KiB 的窗口顺序解析，每个窗口只采用到它自己的语法树里最后一个完整节点为止的部分，下一个窗口从那里开始；算出区间后立即释放语法树。每个窗口的解析同样按 8 ms 分片。
  - 超过 16 MiB：只为可见区域附近的窗口算区间，随滚动按需计算，不算整个文件。
- 不高亮（降级为纯文本）的情况：二进制或不是 UTF-8；一个 64 KiB 的窗口解析超过 128 ms（不到 0.5 MiB/s，按病态输入处理）连续两次，这个文件本次打开不再高亮。文本照常显示、可以滚动和搜索。
- 抽取打开文件的符号（`code_intel` 第 1 层）用同样的窗口：可见窗口先抽取，结果陆续交出；打开文件的上限从 4 MiB 提高到 16 MiB。后台的上限 1 MiB 不变。

**文本存储**

- 不超过 16 MiB 的文件：先用有界的范围读取（[#103](https://github.com/SoloJiang/lectern-app/issues/103)）读首屏，再在后台读完整个文件，存成不可变的分块和行索引。
- 超过 16 MiB：不整份读入，按 64 KiB 的页经范围读取按需读，页的 LRU 不超过 8 MiB；行索引每 1024 行记一个检查点，在后台一遍扫描建好。
- 超过 4 KiB 的行一律折成显示行，按字符的格数（不测量字形）折到视口宽度，只为可见的行计算。

**渲染**

- 阅读视图（`file_reader` 的完整文件、`review_view` 的展示行）是自绘的固定行高列表：只为可见的显示行排版和绘制，滚动位置按（首行序号、行内偏移）保存，不用整份内容的像素高度；每行排版按（内容 OID、行号、宽度）的哈希缓存（GPUI 的 `shape_line_by_hash`）；渲染函数里不做与文件大小成正比的工作。
- gpui-component 的 `InputState` 只用于编辑模式，编辑的文件不超过 1 MiB；高亮经 gpui-component 的 `InputHighlighter` 接口接入 Lectern 自己基于 tree-sitter 0.27.1 的实现。不开 gpui-component 的 `tree-sitter` feature。
- 不做 minimap。

**预算**

预算数字不变，补充测量方式：`app/open_file` 另在 4 MiB、64 MiB 和压缩成一行的 4 MiB 文件上测量，同样 < 16 ms（降级的文件按首屏文本计时）；`app/scroll_frames` 另在 64 MiB 和压缩文件上测量，同样每帧工作时间 ≤ 8.3 ms、不掉帧。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 整文件解析后保留语法树，按需查询高亮 | 4 MiB 的 TS 就占 134 MiB，超出空闲内存预算的量级 |
| 用 gpui-component 的编辑器阅读所有文件 | 大文件首屏没有高亮，软换行和长行在 UI 线程上做与文件大小成正比的工作；高亮会带进第二份 tree-sitter |
| 只在可见区域显示高亮、其余不算 | 跳转和滚动到远处时每次都要等解析；窗口逐个算完后整文件都有高亮，代价与整文件解析相同 |
| 固定的字节上限之上一律不高亮 | 实测窗口解析与文件大小无关，64 MiB 的文件里首屏窗口同样只要几毫秒 |

## 影响

- `file_reader`（[#10](https://github.com/SoloJiang/lectern-app/issues/10)）、`review_view`：设计文档按本 ADR 编写阅读视图、档位和测试；高亮的计算放在领域层，视图只读快照（架构规则 4），具体放在哪个 crate 由 `file_reader` 的设计文档决定。
- `code_intel`：打开文件的抽取改为按窗口、上限 16 MiB，查询时的 `ParsedFile` 对超过 1 MiB 的当前文本只解析查询位置所在的窗口；改动清单见调研「设计文档的修改」。
- `platform`：范围读取（#103）是前置条件。
- `bench`：增加上面的测量；`code_intel` 增加窗口抽取的份额。
- [技术调研](../design/tech-research.md)：「技术选型」的文本存储、「编辑范围」、「代码与 Diff 查看」按本 ADR 修改。

## 已知限制

- 首屏窗口的起点是启发式的，落在多行注释或模板字符串里时首屏高亮出错（实测 40 个位置里最多 15% 不完全一致），直到整文件的区间算完后改正；按树切的窗口在一个包住整个文件的函数里仍有个别窗口出错（`typescript.js` 最差窗口 34%）。
- 窗口单独解析，跨窗口的作用域（如一个超过 64 KiB 的类）里的符号抽取可能缺少所在作用域。
- 折成显示行按字符格数计算，比例字体的回退字形（如 emoji）会让一行的实际宽度与估算不同。
- 解析速度和内存比例来自 Linux 容器和合成文件，M 系列上由 bench 校准；GPUI 部分只读了源码，由 macOS 上的 `#[gpui::test]` 和 UI 探针验证。
