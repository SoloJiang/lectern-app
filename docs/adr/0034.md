# ADR 0034：大文件按窗口解析与高亮，不保留整棵语法树，阅读视图只排版可见行

- 状态：已接受，「解析与高亮」中「阅读时不保留打开文件的整棵语法树」对跳转用的当前文本（128 KiB 以内）已被 [ADR 0037](0037.md) 修订；「预算」的保证对没有人持有、超过 1 MiB 的对象库内容已被 [ADR 0042](0042.md) 修订
- 日期：2026-10-18
- 修订：[ADR 0018](0018.md)（「执行时间有上限」一条里 UI 路径上的解析）；[技术调研「技术选型」](../design/tech-research.md#技术选型)的「文本存储：gpui-component Editor」和[「编辑范围」](../design/tech-research.md#编辑范围第三层)的「基于 gpui-component 的 Editor」

## 背景

产品要求打开单个大文件也要很快，并检查渲染侧的瓶颈。现有预算：打开文件到首屏高亮 < 16 ms，滚动与输入稳定 120 fps（[性能预算](../design/tech-research.md#性能预算)）。

[大文件与渲染调研](../research/large-files-rendering.md)在 Linux 容器（Xeon 2.1 GHz）上用 tree-sitter 0.27.1 实测：

- 整文件解析是线性的，TS 约 6 MiB/s、Rust 4–6 MiB/s、JSON 15–20 MiB/s、压缩成一行的 JS 约 3 MiB/s。1 MiB 的 TS 要 165 ms，64 MiB 要 11–18 s。
- 语法树占输入的 14–41 倍，压缩 JS 47–83 倍：4 MiB 的 TS 是 134 MiB，64 MiB 是 2.1 GiB。
- 解析可以分片：进度回调中止的解析在下一次调用时接着做，得到的树与一次解析完全相同（18 个文件、3 种片长全部相同），分片的额外开销在测量噪声以内。
- 窗口单独解析：文件开头 16 KiB 的窗口 0.7–4.9 ms，高亮与整文件解析逐字节一致；文件中部从启发式的安全位置开始的窗口（实测 14–25 KiB）平均 0.6–6 ms、最差 15 ms，40 个随机位置里 85–100% 完全一致。整个文件按 64 KiB 的窗口逐个解析再丢弃、下一个窗口从前一个窗口的语法树确认的语句边界开始，总耗时与整文件解析相同，一致率合成文件 100%、真实文件 98.9–100%，同时存在的语法树不超过约 5 MiB。
- 按行号定位：64 MiB 的文件找换行建行索引 37–45 ms，还要先读完整个文件。

[gpui-component 0.7.3](https://github.com/longbridge/gpui-component/tree/v0.7.3) 的编辑器（`InputState` 的代码模式）读源码得到（GPUI 在 Linux 上不能构建，未运行）：文本是 ropey 的 Rope；超过 256 KiB 的文件在 150 ms 防抖之后才在后台解析整个文件，之前没有高亮；设置文本时软换行在 UI 线程上逐行测量整个文件；超过 10,000 字节的行不高亮，但每帧仍把整行复制成字符串再排版；高亮要开它的 `tree-sitter` feature，它依赖 tree-sitter 0.26.13，与 Lectern 锁定的 0.27.1 是两份。GPUI 的坐标是 f32，超过 2^24 像素（行高 18 pt 时约 93 万行）之后滚动位置不再精确到像素。

## 决策

**解析与高亮**

- 不在 UI 线程上解析（AGENTS.md「禁止事项」），阅读时不保留打开文件的整棵语法树。高亮的结果是按行存放的着色区间，进入已有的 8 MB 高亮与文本 LRU；语法树在算出区间后释放。
- 首屏：从可见区域之前约 8 KiB 处的安全位置（往前至多再找 4 KiB）开始、到可见区域之后 4 KiB 结束的窗口单独解析，算出可见行的区间后交给视图；窗口不超过 16 KiB 加上可见部分（实测 14–25 KiB，一行很长的文件的可见部分按 8 KiB 计）。窗口解析带 8 ms 截止时间：超时时这一帧先画出没有高亮的文本，解析完成后再上色。安全位置由每种语言的轻量规则给出：第 0 列开始的语句、一行很长时的 `;` 或 `}` 之后、JSON 里形如 `,"键":` 的成员开头（窗口两端补齐括号）。
- 首屏路径上的准备工作都有界（关键约束）：选安全位置只看目标之前至多 64 KiB、之后至多 64 KiB 的字节，不用行索引，不从文件开头扫描（例如不为判断是否在 JSON 字符串里而从头做词法扫描）；目标所在的行从目标往前找换行（至多 4 KiB，找不到按长行处理）；编码和二进制只看窗口本身和文件头 8 KiB；长行只看可见的行；行号栏在行检查点或后台扫描之前按估计显示。64 KiB 之内找不到安全位置时，首屏先画纯文本，起点和行检查点在后台算出后再上色。实测（选起点、补括号、解析、可见部分的查询都在计时内）：选起点最多 0.07 ms；16 和 64 MiB 的一行 JSON 合计平均 1.7–2.0 ms、最多 3.4 ms，与 1 MiB 的相同；16 和 64 MiB 的一行压缩 JS 合计平均 7.8–11.6 ms、最多 20 ms，超过 8 ms 截止时间的那部分先画文本；真实的 `babel.min.js` 40 个位置里 3 个在 64 KiB 内找不到起点。
- 首屏之后按档位计算整个文件。多秒的计算不持有 `BusyGuard`、不占 `Interactive`：

| 档位 | 条件 | 首屏之后 | 守卫与线程 |
|---|---|---|---|
| A | ≤ 1 MiB，且没有超过 4 KiB 的行 | 整文件解析，8 ms 一片，完成后用整文件的区间替换首屏的 | `BusyGuard`、`Interactive`（1 MiB 约 165 ms） |
| B | 1–16 MiB，或有超过 4 KiB 的行 | 从文件开头按约 64 KiB 的窗口顺序解析，每个窗口只采用到它自己的语法树里最后一个完整节点为止的部分，下一个窗口从那里开始；记下每个窗口的起点，区间只为可见附近的窗口留在 LRU 里 | 可见窗口和前后各一个：`BusyGuard`、`Interactive`；其余：`BackgroundGuard`、批量线程，按 [ADR 0033](0033.md) 的只存内存的一类 |
| C | > 16 MiB | 只为可见区域附近的窗口算区间，随滚动按需计算；窗口起点的顺序计算同档位 B 的「其余」 | 同档位 B |

- 降级为纯文本：二进制或不是 UTF-8；一个 64 KiB 的窗口解析超过 128 ms（不到 0.5 MiB/s，按病态输入处理）连续两次，这个文件本次打开不再高亮。文本照常显示、可以滚动和搜索。

**打开文件的符号抽取**

- `code_intel` 第 1 层对超过 1 MiB 的打开文件按同样的窗口顺序抽取，每个窗口完成后立即作为一个单元写入 `cache`，键是（OID、语言、grammar 版本、查询版本、窗口起点），单元里记下窗口的终点。所以暂停、取消或退出只丢掉在途的窗口，恢复时从最后一个已写入窗口的终点继续，满足 ADR 0029 的第二条。窗口链覆盖到文件末尾时这个文件算作已入索引。
- 可见窗口先单独抽取一次，结果只在内存里用于同文件跳转（第一屏的符号先到）；它和前后各一个窗口在 `Interactive` 上，其余窗口在批量层最前面、持有 `BackgroundGuard`。
- 打开文件的上限从 4 MiB 提高到 16 MiB；后台的上限 1 MiB 不变。

**文本存储与定位**

- 不超过 16 MiB 的文件：先用有界的范围读取（[#103](https://github.com/SoloJiang/lectern-app/issues/103)）读首屏，再在后台读完整个文件，存成不可变的分块和行索引。超过 16 MiB：按 64 KiB 的页经范围读取按需读，页的 LRU 不超过 8 MiB。
- 打开到文件中部时按字节偏移定位：知道偏移的一方必须给出偏移。`code_intel` 的 `Location` 增加定义起点的字节偏移；`git` 的 hunk 和展示行带两侧的字节偏移；保存的阅读位置同时存行号和字节偏移。
- 只有行号时（如 agent 输出里的 `file:line`）用按 blob OID 缓存的行检查点：每 64 KiB 记下该处的行号，在后台第一次扫描整个文件时算出、写入 `cache`（64 MiB 的文件约 4 KiB）。
- 超过 4 KiB 的行一律折成显示行，按字符的格数（不测量字形）折到视口宽度，只为可见的行计算。4 KiB 是估计值，由 macOS 上 Core Text 排一行的实测校准。

**渲染**

- 阅读视图（`file_reader` 的完整文件、`review_view` 的展示行）是自绘的固定行高列表：只为可见的显示行排版和绘制，滚动位置按（首行序号、行内偏移）保存，不用整份内容的像素高度；每行排版按（内容 OID、行号、宽度）的哈希缓存（GPUI 的 `shape_line_by_hash`）；渲染函数里不做与文件大小成正比的工作。
- 不做 minimap。

**编辑模式**

- 只有档位 A 的文件可以进入编辑（≤ 1 MiB、没有超过 4 KiB 的行），用 gpui-component 的 `InputState`；高亮经它的 `InputHighlighter` 接口接入 Lectern 自己基于 tree-sitter 0.27.1 的实现，不开 gpui-component 的 `tree-sitter` feature。
- 编辑期间保留一棵语法树供增量解析，在上限处是 34–41 MiB；退出编辑模式时释放，不计入空闲内存（ADR 0017 的采样不在编辑模式下进行）。
- 进入编辑时 `InputState` 在 UI 线程上逐行建换行信息：编辑模式默认不开软换行，这一步在上限处是 3.6 万行的一次遍历（同类遍历实测约 2 ms）；开软换行时每行一次文本测量，只对 ≤ 256 KiB 的文件允许。1 MiB 的上限由 macOS 上的 `app/enter_edit` 校准，超标时降低上限。

**预算**

打开文件到首屏高亮 < 16 ms 在以下条件下对任何大小的文件成立：目标位置以字节偏移给出，或这个 blob 的行检查点已在缓存里，或目标在文件开头。只给行号、又没有检查点的第一次打开要扫描到那一行（64 MiB 的文件几十毫秒），之后有了检查点。降级的文件按首屏文本计时；首屏窗口超过 8 ms 截止时间时，首屏先画文本。

测量方式补充：`app/open_file` 另在 4 MiB、64 MiB、压缩成一行的 4 MiB 文件，以及 4 MiB 的 `package-lock.json` 中部的一个 hunk 上测量，预算相同；`app/scroll_frames` 另在 64 MiB 和压缩文件上测量；新增 `app/enter_edit`（上限处的文件从 ⌘E 到可以输入，中位数 ≤ 100 ms，即交互规范里不显示加载态的上限）和编辑模式下的 `app/scroll_frames` 场景。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 整文件解析后保留语法树，按需查询高亮 | 4 MiB 的 TS 就占 134 MiB，超出空闲内存预算的量级 |
| 用 gpui-component 的编辑器阅读所有文件 | 大文件首屏没有高亮，软换行和长行在 UI 线程上做与文件大小成正比的工作；高亮会带进第二份 tree-sitter |
| 不做顺序计算，每个窗口都从启发式的安全位置开始 | 启发式的起点在真实文件上有 0–15% 的位置出错；顺序计算给出每个窗口经语法树确认的起点（每个 8 字节），滚到任何位置都能按这个起点重算出与顺序计算相同的区间。它不给出整个文件的区间：档位 B 的 16 MiB 文件的区间约 29 MiB，放不进 8 MB 的 LRU |
| 打开文件的窗口抽取全部完成后才写入 | 违反 ADR 0029 第二条：暂停或退出会丢掉已完成的窗口 |

## 已知限制

- 首屏窗口的起点是启发式的，落在多行注释或模板字符串里时首屏高亮出错（实测 40 个位置里最多 16% 不完全一致），直到顺序计算到达这里后改正；按树切的窗口在一个包住整个文件的函数里仍有个别窗口出错（`typescript.js` 最差窗口 34%）。
- 窗口单独解析，跨越整个窗口的作用域（如一个超过 64 KiB 的类）里的符号抽取可能缺少所在作用域。
- 折成显示行按字符格数计算，比例字体的回退字形（如 emoji）会让一行的实际宽度与估算不同。
- 解析速度和内存比例来自 Linux 容器和合成文件，1 MiB、4 KiB、16 MiB、8 ms、128 ms 都在 M 系列上校准；GPUI 部分只读了源码，由 macOS 上的 `#[gpui::test]` 和 UI 探针验证。
