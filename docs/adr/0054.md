# ADR 0054：托管 runner 上反复超标的两项份额预算暂时放宽，`git/changes_clean_100k` < 3 s，`code_intel/extract_throughput` ≥ 3 MB/s

- 状态：已接受
- 日期：2026-10-28
- 修订：[ADR 0031](0031.md)（「预算保持 4 MB/s」改为 3 MB/s）

## 背景

两项 `Tier::Share` 的份额预算在只改文档的 PR 上反复超标，代码没有变化，同一台托管的 runner（Apple M1 (Virtual)，3 核，macOS 15.7.9），见 [#286](https://github.com/SoloJiang/lectern-app/issues/286)：

| 预算 | 原来的值 | 超标的运行 | 通过的运行 |
|---|---|---|---|
| `git/changes_clean_100k` 中位数 | < 2 s | 2.43、2.54 s（#280），2.50、2.31 s（#284） | 0.66、0.76、1.25、1.06 s |
| `code_intel/extract_throughput` 中位数 | ≥ 4 MB/s | 3.84 MB/s（#281，88b7ba7） | 同一份抽取代码多次通过；ADR 0031 记录过 3.11–3.19 MB/s 的运行 |

`git/changes_clean_100k` 多出的时间在 `phase_stat`（363 ms → 999 ms）和 `phase_untracked`（551 ms → 1.54 s），即文件系统的 stat 和目录遍历，不在比较的逻辑里。每次超标都要人工重跑，挡住了合并。

产品负责人的决定（2026-10-28）：两项先放宽，先完成产品能力，波动的原因以后再查。

## 决策

- `git/changes_clean_100k`：中位数 < 2 s 改为 < 3 s。超标的四次最大 2.54 s，3 s 留约 18% 的余量。
- `code_intel/extract_throughput`：中位数 ≥ 4 MB/s 改为 ≥ 3 MB/s。ADR 0031 记录的最低一次是 3.11 MB/s。
- 其余不变：样本数、采样规则、判定方式，两项各自的分阶段记录项，以及全部顶层预算（冷启动、空闲内存、`app/index_100k` ≤ 2 分钟等）。
- 这是暂时的放宽：[#286](https://github.com/SoloJiang/lectern-app/issues/286) 查清原因（托管 runner 的 I/O 波动、夹具刚建好时的冷缓存、分片里的位置），或自托管的实体 Mac 开始判定（[ADR 0052](0052.md)）之后，按实测改回原来的值或另写 ADR。

放弃的方案：

- 每次超标都重跑：已经做了五次，每次挡住合并一到两个小时。
- 只在判定机器上判定这两项：判定机器还没有接入。

## 影响

- `lectern-bench` 的 `budgets.rs`：两项的 `Limit`。
- `docs/design/bench.md`、`docs/design/git.md`、`docs/design/code_intel.md` 里写这两个数的地方。
- ADR 0031 的状态行和索引。

## 已知限制

- ADR 0031 的推导（800 MB、2 个批量线程、每线程 4 MB/s，约 100 s）在 3 MB/s 下约 133 s，超过 `app/index_100k` 的 2 分钟。顶层预算不变：`app/index_100k` 实现之后（[#17](https://github.com/SoloJiang/lectern-app/issues/17)）由它自己判定，份额放宽不会让顶层超标被放过。
- 放宽期间，抽取或工作区比较在 2–3 s、3–4 MB/s 之间的真实退化不会被 CI 发现，只能从报告里的数字看出。
