# ADR 0067：帧时间的预算在托管 runner 上判定主线程部分的 p95，整帧的最大值由判定机器判定

- 状态：已接受
- 日期：2026-11-23
- 修订：[ADR 0052](0052.md)（决策第 3 条的范围：帧时间的预算原由托管 runner 判定）

## 背景

帧时间的预算（[性能预算](../design/tech-research.md#性能预算)「滚动与输入」）在 bench 里是两个条件：每帧工作时间 `completed − requested` 的最大值 ≤ 8.3 ms，相邻帧间隔都 ≤ 1.5 个刷新周期。ADR 0052 把它留给 GitHub 托管的 runner 判定。

帧记录接通之后（[#393](https://github.com/SoloJiang/lectern-app/issues/393)，[#401](https://github.com/SoloJiang/lectern-app/pull/401)），`app/scroll_frames` 和 `app/scroll_frames_indexing` 第一次在托管 runner（Apple 虚拟机，Metal 设备是 "Apple Paravirtual device"，60 Hz 的虚拟显示器）上有了数据。同一个提交（417b3fec）运行 3 次，每个场景每次 1220 帧：

- 整帧的工作时间最大值 31–76 ms，帧间隔最大 1.5–3.0 个刷新周期，每次都超标。其中等 drawable（`nextDrawable` 的调用到返回）的 p95 是 5–16 ms、最大 31 ms；从帧源回调到帧开始的 p95 约 16.7 ms（一个刷新周期）；GPU 的最大值 4–38 ms。这三段都不是 Lectern 的代码在运行。
- 主线程部分（帧开始到调用 `nextDrawable`，加上拿到 drawable 到 `commit`）：

  | 场景 | 中位数 | p95 | 每次运行里超过 8.3 ms 的帧 |
  |---|---|---|---|
  | 64 MiB 的源码，阅读 | 2.5–3.2 ms | 4.4–4.9 ms | 3、2、4（最大 23.6 ms） |
  | 编辑模式 | 3.2–3.8 ms | 5.6–6.5 ms | 11、8、11 |
  | 索引期间滚动 | 1.7–2.2 ms | 3.8–5.2 ms | 11、22、11 |
  | 压缩成一行的 4 MiB 文件 | 5.3–6.1 ms | 约 10.5 ms | 248、241、343 |

  第一个场景是对照：p95 不到 5 ms，但每次运行都有 2–4 帧随机超过 8.3 ms，位置每次不同。所以主线程部分的最大值在这台机器上也会随机超标；最后一个场景是产品自己的开销，任何统计量下都超标。

托管 runner 能分辨的是 Lectern 主线程上的工作变慢，分辨不了整帧是否按时显示，也给不出可靠的最大值。

## 决策

1. 帧时间的预算（预算表里按 8.3 ms 判定帧的每一条，现在是 `app/scroll_frames`、`app/scroll_frames_indexing`、`app/input_frames`、`app/terminal_output_frames`、`app/animation_frames`、`app/home_frames`、`review_view/scroll_5000`）分成两部分判定：
   - **托管 runner：主线程部分的 p95 ≤ 8.3 ms。** 一帧的主线程部分是 `(drawable_asked − started) + (committed − drawable_got)`：从帧开始（`workspace` 的帧回调）到调用 `nextDrawable`，加上拿到 drawable 到 `commit`。它不含帧源回调到帧开始的等待、等 drawable 和 GPU。一条预算有几个场景时，每个场景各自取 p95，都要 ≤ 8.3 ms。报告同时写中位数、p99、最大值和超过 8.3 ms 的帧数，只记录。
   - **判定机器（ADR 0052 的实体 Mac）：原来的两个条件不变。** 整帧工作时间 `completed − requested` 的最大值 ≤ 8.3 ms，相邻帧间隔都 ≤ 1.5 个刷新周期（`review_view/scroll_5000` 是整帧工作时间的 p95 ≤ 8.3 ms）。这些条目成为判定机器的条目：托管 runner 上只记录，`Judge (physical Mac)` 运行并判定它们。
2. 关键约束：
   - 8.3 ms 这个数字不变，产品的目标仍是整帧在 120 Hz 下按时显示（「稳定 120 fps」）。托管 runner 上的 p95 是回归检查，不是这个目标的验收；验收是判定机器上的最大值。
   - 托管 runner 的条目里，一帧缺少四个时刻中的任何一个是错误，不是跳过这一帧：缺了时刻的记录不能判定。
   - 滚轮、按键等输入的处理要落在帧开始之后（基准在帧回调之后分发事件），否则它的开销不在主线程部分里。
   - 两部分用同一批记录：一次运行、一组帧，两个结果。
   - 不为了让托管 runner 通过而去掉场景或缩小夹具。超标的场景（现在是压缩成一行的文件）修到通过，按 [ADR 0055](0055.md) 的规则处理。
3. p95 而不是最大值或 p99，由产品负责人 2026-11-23 决定：对照场景每次运行有 2–4 帧随机超标，最大值必然随机失败；p99 允许 1220 帧里 12 帧，编辑模式（8–11）贴着线，索引期间（11–22）三次里超过一次。p95 允许 5% 的帧（1220 帧里 61 帧），三个开销正常的场景有余量，压缩成一行的场景仍然超标。
4. 放弃的方案：

   | 方案 | 原因 |
   |---|---|
   | 托管 runner 照旧判定整帧的最大值和间隔 | 每次都超标，超出的部分是虚拟机的 drawable 等待、帧源和 GPU |
   | 托管 runner 判定主线程部分的最大值 | 对照场景每次运行都有随机的超标帧 |
   | 托管 runner 判定主线程部分的 p99 | 两个场景在噪声范围内贴线，会随机失败 |
   | 托管 runner 上只记录，全部交给判定机器 | 判定机器不在 PR 上运行，现在还没有注册；主线程上的回归要到合并之后才看到，或者一直看不到 |
   | 放宽 8.3 ms | 数字来自 120 Hz 的帧周期，虚拟机慢不是产品变慢 |
   | 用线程的 CPU 时间代替墙上时间 | 虚拟机里的客户机看不到宿主机的抢占，尖峰可能仍在；多一组时刻；没有实测 |

## 影响

- `bench`：帧时间的条目标为判定机器的条目；每条增加一个托管 runner 判定的主线程部分的结果，来自同一批记录；缺时刻的帧是错误。随 [#401](https://github.com/SoloJiang/lectern-app/pull/401) 实现，条目的名字、报告的格式和预算表在 [bench 设计](../design/bench.md)。
- `platform`：帧记录带 `drawable_asked`、`drawable_got`、`committed` 三个时刻（只在 `bench-hooks` 里，ADR 0048），随 #401；设计在 [platform 设计「帧的时刻」](../design/platform.md#帧的时刻)。
- CI：`Judge (physical Mac)` 的命令加上帧时间的条目；`Benchmarks (macOS arm64)` 判定主线程部分。随 #401 改 `ci.yml` 和 [CI 设计「判定机器」](../design/ci.md#判定机器)。
- 其余帧时间的条目（输入、终端输出、动画、项目主页、审阅视图）还是计划中，生效时按本 ADR 分成两部分。
- ADR 0052 的状态行、索引、[性能预算](../design/tech-research.md#性能预算)表同步改正。

## 已知限制

- 判定机器注册之前（仓库变量 `LECTERN_JUDGE_RUNNER` 不是 `true`），整帧的最大值和帧间隔没有机器判定，只有托管 runner 的记录。
- p95 不反映最慢的 5% 的帧：偶发的长帧（例如一次滚动的头几帧）在托管 runner 上不会失败，只出现在报告的最大值和超标帧数里，要靠判定机器发现。
- 主线程部分不含 GPU 和等 drawable：画得太多导致 GPU 变慢、或者提交方式导致等 drawable 变长，托管 runner 看不到。
- 托管 runner 比目标硬件慢，主线程部分在那里通过不说明在实体机上有多少余量，在那里超标也可能在实体机上不超标；仍按托管 runner 的结果判定，因为它是 PR 上唯一的机器。
- 判定机器不在 PR 上运行（ADR 0052）：整帧的退化在合并之后 `main` 的运行上才看到，除非合并之前手动触发。
