# ADR 0042：对象库内容的首屏先用已经在内存里的那一份；没有人持有、超过 1 MiB 的不在 16 ms 的保证里

- 状态：已接受
- 日期：2026-10-21
- 修订：[ADR 0034](0034.md)（「预算」：首屏 < 16 ms 对任何大小的文件成立的条件）

## 背景

[ADR 0034](0034.md)「预算」规定：目标位置以字节偏移给出、或这个 blob 的行检查点已在缓存里、或目标在文件开头时，打开文件到首屏高亮 < 16 ms 对任何大小的文件成立。它的做法是首屏只经有界的范围读取读目标附近的一段（[platform 设计「范围读取」](../design/platform.md#范围读取)）。

完整文件阅读还要打开对象库里的内容（`TextOrigin::Object`）：Diff 的旧一侧经 ⇧⌘O 或 hunk 打开，以及从旧一侧发起的跳转候选（[file_reader 设计](../design/file_reader.md)「定位」）。对象库的内容不能按区间读：松散对象是整份 zlib 压缩的，包里的对象可能是增量，要先还原整条增量链；`git` 的 `Repo::blob` 整份取出（[git 设计](../design/git.md)，gix 只在 `git` 里用，[ADR 0024](0024.md)）。所以对象库内容的首屏要等解压，耗时随大小增长。没有在 M 系列上实测；按 zlib 的解压速度（每秒几百 MiB）估计，1 MiB 约 2–4 ms，4 MiB 约 10–30 ms（含增量还原），超过 16 ms 的一帧。

## 决策

- 先用已经在内存里的那一份：审阅视图显示一个文件的 diff 时本来就持有两侧的文本（`ChangeSet::texts`），它经 `Reader::share_object` 把文本登记给阅读视图，阅读视图只记 `Weak`，不多占内存。打开这个 OID 的对象库内容时，内容还活着就直接用，首屏不做 IO，16 ms 照常成立。现有的入口（Diff 的旧一侧、从旧一侧发起的跳转候选）打开时 diff 都还显示着，都落在这一类。
- 没有人持有时，≤ 1 MiB 的在首屏任务里解压，仍在 16 ms 之内（`syntax/first_screen/object_1mib` 判定 ≤ 8 ms 的份额）。
- 没有人持有、超过 1 MiB 的（Diff 关闭之后经后退、前进回到对象库内容）要等整份解压，**不在 16 ms 的保证里**；超过 16 MiB 的不打开。`syntax/first_screen/object_cold`（4 MiB）只记录。
- `app/open_file` 增加对象库的场景：从 diff 的旧一侧打开 4 MiB blob 中部的一个 hunk（内容已登记），预算 < 16 ms 不变。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 把解压后的对象库内容另存一份在内存里（按 OID 的 LRU） | 一份可达 16 MiB，超过已有的 8 MiB 高亮与文本 LRU，要新的内存份额（[ADR 0035](0035.md)）；它只服务 Diff 关闭之后的后退、前进 |
| 把解压后的内容写进 `cache` | 是对象库的重复副本；单个值上限 8 MiB（cache 设计）；首屏仍要读几 MiB |
| 流式解压、只解到目标处 | 包里的增量对象要先还原整条链，开头和中部的代价相同；gix 的接口整份返回 |

## 影响

- `file_reader` / `syntax`（[file_reader 设计](../design/file_reader.md)「定位」「性能」）：`Reader::share_object`、`OBJECT_INLINE = 1 MiB`、上面的基准。
- `review_view`：显示 diff 时为两侧文本登记，写进它的设计文档。
- [bench 设计「预算表」](../design/bench.md#预算表)：`app/open_file` 的场景加上对象库。
- ADR 0034 的状态行和索引注明「预算」被本 ADR 修订。

## 已知限制

- 估计的解压耗时没有在 M 系列上测过，由 `syntax/first_screen/object_cold` 记录；1 MiB 的界限超标时在 file_reader 设计里降低 `OBJECT_INLINE`。
