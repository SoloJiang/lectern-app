# ADR 0052：drawable 没有 `presentedTime` 时，首帧的时刻取显示回调运行的时刻，结果注明来源；首帧要真正显示的预算由自托管的实体 Mac 判定

- 状态：已接受
- 日期：2026-10-26
- 修订：[ADR 0048](0048.md)（首帧的钩子只取 `presentedTime` 大于 0 的 drawable）；[ADR 0017](0017.md)（冷启动的终点只能是 `presentedTime`；超过预算由 CI 的托管 runner 判定）；[bench 设计「未决问题」](../design/bench.md#未决问题)第 1 条（判定用的机器，原为选项 A）

## 背景

ADR 0017 把冷启动的终点定为第一个 `MTLDrawable` 的 `presentedTime`，经 `addPresentedHandler` 读取。ADR 0048 的首帧钩子（`platform::frame::on_first_presented`）因此跳过 `presentedTime` 为 0 的 drawable，等第一个大于 0 的。

bench 第 4 步（[#269](https://github.com/SoloJiang/lectern-app/pull/269)）在 CI 的 Benchmarks 任务上运行 `baseline/empty_window_cold_start`，探针一直收不到首帧回调，基线没有样本。#269 上临时的诊断提交（之后用 revert 提交去掉）在 GitHub 托管的 `macos-15-arm64` runner 上测得：

- 机器：Metal 设备是 "Apple Paravirtual device"（Anka 虚拟机），一个 1024 × 768 的显示器，没有睡眠。会话在控制台上（`kCGSSessionOnConsoleKey` 为 1），已登录，没有锁屏。窗口可见（`occlusionState` 为 0x2002）。
- 不经方法替换，在一个可见窗口的 `CAMetalLayer` 上按三条显示路径各画 120 帧：命令缓冲的 `presentDrawable:` 加 `commit`；`presentsWithTransaction` 加 `[drawable present]`；`presentDrawable:atTime:`。每条路径的 120 个显示回调都运行了，`presentedTime` 都是 0。
- 经 GPUI 的空窗口：第一次绘制时窗口还没有显示，第二次绘制时已经显示。启动后 1.1 s 的读数里，第一个 drawable 的显示回调已经运行，`presentedTime` 为 0；第二个的回调到 8.4 s 还没有运行。连续重画时，2.2 s 的读数里取了 109 个 drawable，只有 1 个回调运行过；3.2 s 时才追上（172 个里 170 个）。
- 本机屏幕锁定时结果相同：每个 `presentedTime` 都是 0。

所以这台机器从不给 `presentedTime`，与方法替换无关。按 ADR 0048，首帧回调永远不到，`baseline/empty_window_cold_start` 和 `app/cold_start` 在当时判定用的机器（托管 runner，[bench 设计「未决问题」](../design/bench.md#未决问题)第 1 条的选项 A）上没有样本。

加上决策 1 的回退之后，#269 在托管 runner 上的 CI 运行（提交 63e68c7）得到：

- `baseline/empty_window_cold_start`：20 个样本 111.27–224.56 ms，中位数 157 ms，20 个都超过 20 ms，来源都是 `handler`。
- `baseline/empty_window_idle`：14.4、13.6、16.3 MB，3 次的来源都是 `handler`。

这台机器上的回调会落后于显示几秒（上面 2.2 s 的读数），这些数字里有多少是虚拟机的回调延迟、多少是启动本身，从结果里分不出来。按 ADR 0017 的规则，`app/cold_start` 在托管 runner 上会一直超标，而 ADR 0017 不允许为此放宽预算。托管 runner 不能判定冷启动。

GitHub 建议自托管 runner 只用于私有仓库：公开仓库的 fork 可以开一个 PR，让工作流在 runner 上运行它的代码。本仓库是公开的。

## 决策

1. 显示回调读到的 `presentedTime` 不大于 0 时（0、负数、NaN），首帧的时刻是这个回调运行的时刻：回调里读 `CACurrentMediaTime()`，换算到系统时钟的方法不变（[platform 设计「时钟」](../design/platform.md#时钟)）。`presentedTime` 大于 0 时仍用它。最先运行的那个显示回调决定首帧，之后的不再交付。
2. 每个结果都带来源：`presented`（`presentedTime`）或 `handler`（回调运行的时刻）。`platform` 交给首帧回调的值、探针发给运行器的 `FirstFrame`、bench 的输出和报告都写明来源。
3. 首帧要真正显示的预算由一台自托管的实体 M 系列 Mac 判定（选项 B，产品负责人 2026-10-26），托管 runner 上只记录。预算和判定规则不变（ADR 0017）。关键约束：
   - 机器：实体的 M 系列 Mac，不是虚拟机（托管 runner 就是虚拟机），接着显示器或 HDMI 假负载。它作为本仓库的自托管 runner 注册，标签 `[self-hosted, macOS, ARM64, lectern-judge]`。
   - 范围：测量的时间止于首帧的预算，现在是 `app/cold_start`（判定）、`app/cold_start_purged` 和 `baseline/empty_window_cold_start`（只记录）。空窗口的两条基线（含 `baseline/empty_window_idle`）以判定机器的结果为 ADR 0017 的基线。其余预算仍由托管 runner 判定：端到端基准的里程碑取下一帧回调的时刻（[workspace 设计「已知限制」](../design/workspace.md#已知限制)），帧时间里的 `presented` 只报告，内存不取首帧的时刻。
   - 开关：bench 运行器读环境变量 `LECTERN_BENCH_JUDGE`。值为 `1` 时是判定机器，上面的条目照常判定。没有设置时，这些条目只记录（不判定、不重跑），报告写明原因，托管 runner 就是这种情况。其他值，在不判定的运行里（冒烟、不是 Apple 芯片）设为 `1`，以及设为 `1` 而判定机器的条目一条都没有运行（都被过滤、都是计划中或都跳过），都让运行器以退出码 2 失败，判定任务不会在没有判定时通过。
   - 判定机器上来源为 `handler` 的首帧是错误，不是通过，也不是只记录：实体机应当给出 `presentedTime`，`handler` 说明机器没有准备好（锁屏、显示器关闭或没有接）。
   - 什么时候运行：判定任务在 push 到 `main` 时运行，也可以由有写权限的人在本仓库的一个分支上手动触发（`workflow_dispatch`）。它不在 `pull_request` 上运行（决策 4），所以不是必需检查：`main` 上判定失败时修复或回退那次合并；改动首帧之前的代码的 PR，合并之前在它的分支上手动触发一次。runner 注册之前，它只在仓库变量 `LECTERN_JUDGE_RUNNER` 为 `true` 时运行，否则跳过。
4. 安全（仓库是公开的），以下全部要满足：
   - runner 只运行已经在 `main` 上的代码，或有写权限的人选定的本仓库分支（`workflow_dispatch`），不自动运行 PR 的代码：判定任务不在 `pull_request` 上运行，也不用 `pull_request_target`。不用 environment 的必需审批代替：个人仓库没有 runner 组，GitHub 不能限制哪些工作流用这台 runner；审批只约束引用了这个 environment 的任务，PR 改掉自己的工作流文件就绕过它。
   - 写权限只给仓库所有者：有写权限的人可以改工作流，让任何分支在这台机器上运行。
   - 仓库设置里，fork 的 PR 的工作流对所有外部贡献者都要批准（「Require approval for all external contributors」）。fork 的 PR 运行的是 PR 里的工作流文件，可以加上一个用这台 runner 的任务，所以改了 `.github/` 的 fork PR 不批准运行。
   - 不用任何 secret；`GITHUB_TOKEN` 只有 `contents: read`；checkout 不保存凭据；任务用的 action 固定到提交的 SHA。
   - 任务不下载工具：工具链和 `just` 由管理员预先装在专用用户只能读、不能写的目录里。任务的 `HOME`、`CARGO_HOME`、`TMPDIR` 都在每个任务清空的 `RUNNER_TEMP` 下。
   - runner 以一个专用的 macOS 标准用户运行，这个用户没有别的凭据（SSH 密钥、git 凭据、别的服务的钥匙串项、云账号）。runner 是这个用户的 LaunchAgent，在它的图形会话里运行。这个用户的主目录不跨任务信任（任务可以按绝对路径写它），定期删除这个用户、重新注册 runner；能在专用用户之外自动重新注册时，用一次性的 runner（`--ephemeral` 或 JIT）。
   - 每个任务开始和结束时清空工作区，不跨任务保留构建产物或缓存。结束时结束这个任务启动、还在运行的全部进程，按进程 ID 挑选，不按名字或路径：任务开始之前没有、现在属于专用用户的进程，runner 自己的进程除外。
   - 机器不睡眠，显示器常亮；专用用户自动登录，或一直保持登录、不锁屏。
5. 为什么回退不违反 ADR 0017、0048 不接受「`present` 的调用时刻」的理由：那些时刻在 drawable 交给系统之前或同时。显示回调登记在 drawable 上，只能在 drawable 交给 Core Animation 之后运行，所以它的时刻不早于 `present`，不会把还没有交出的帧算作已经显示。它不是显示时刻，结果的来源说明这一点。
6. 放弃的方案：

   | 方案 | 原因 |
   |---|---|
   | 照旧等第一个 `presentedTime` 大于 0 的 drawable | 托管 runner 和锁屏的机器永远等不到，基线没有样本 |
   | `on_next_frame` 或 `present` 的调用时刻 | 早于显示回调；ADR 0017、0048 不接受的理由仍成立 |
   | 在托管 runner 上按回调的时刻判定（选项 A 加回退） | 20 个样本都超过 20 ms，来源都是 `handler`，分不出虚拟机的回调延迟；冷启动会一直超标，又不能放宽预算 |
   | 判定机器上来源为 `handler` 的样本照常判定或只记录 | 会把不是显示时刻的数字当作判定结果和基线 |
   | 全部基准都改在判定机器上运行 | 其余预算不依赖显示，托管 runner 已经判定它们；判定任务每次从头构建，只运行需要显示的条目更短 |
   | 在判定机器上用 macOS 虚拟机隔离每个任务 | 托管 runner 就是虚拟机，不给 `presentedTime` |
   | 在本仓库分支的 `pull_request` 上自动判定 | runner 会运行每个 PR 的代码；PR 合并之前能判定，但持久的实体机上的风险更大 |
   | 同上，再加 environment 的必需审批 | 审批写在 PR 自己的工作流文件里，删掉就绕过；每次运行要人点一次 |

## 影响

- `platform`：`frame::on_first_presented` 的回调改为接受 `PresentedAt { time, source }`，新增 `TimeSource`（`Presented`、`Handler`）。行为只在 `bench-hooks` 里有，发布构建不变（ADR 0048）。`frame::record`（B2，尚未实现）的 `FrameTimes::presented` 按同一规则带来源。设计在 [platform 设计「帧的时刻」](../design/platform.md#帧的时刻)。
- `bench`：探针的 `FirstFrame` 带来源，冷启动和空窗口基线的输出写每个样本的来源。预算表标出决策 3 范围里的条目，运行器读 `LECTERN_BENCH_JUDGE`，进程调度在判定机器上把 `handler` 当作错误。都随 bench 第 4 步（#269），设计在 [bench 设计](../design/bench.md)。`wire` 的 `FrameTimes`、`Milestone` 现在不变，B2 和 bench 第 5 步加入它们的使用方时一起带上来源。
- CI：`ci.yml` 增加 `workflow_dispatch` 和判定任务 `Judge (physical Mac)`，`Benchmarks (macOS arm64)` 不变，决策 3 范围里的条目在那里只记录。任务、条件和机器的准备在 [CI 设计「判定机器」](../design/ci.md#判定机器)。产品负责人提供机器、预装工具、注册 runner、设置仓库变量。
- runner 注册之前，`app/cold_start`（bench 第 5 步）没有机器判定，空窗口的基线只有托管 runner 的记录。之后 PR 上也不自动判定冷启动，只在 `main` 上和手动触发时判定。
- ADR 0017 的测量方式和「影响」、ADR 0048 的决策第 1 条、两者的状态行、bench 设计「未决问题」第 1 条、索引同步改正。

## 已知限制

- 来源为 `handler` 的时刻不是显示时刻：它不早于 drawable 交给系统，与真正显示的先后不确定。托管 runner 上的冷启动记录是「进程创建到第一个运行的显示回调」，回调落后于显示（实测 2 s 以上），数字只会偏大。
- GPUI 的第一个 drawable 在窗口显示之前画出。在给 `presentedTime` 的实体机上，它的回调也可能带 0 先到，结果为 `handler`，按决策 3 判定任务每次都出错。还没有在没有锁屏的实体 Mac 上验证；注册之后的检查（[CI 设计「判定机器」](../design/ci.md#判定机器)）会看到它，那时要产品负责人重新决定，不是改配置。
- 本机屏幕锁定时，来源为 `handler` 的空窗口冷启动是 78–86 ms（#269，[bench 设计「实际验证」](../design/bench.md#实际验证)第 4 步）。实体机给 `presentedTime` 时的数字还不知道，由判定机器的第一次运行给出；空窗口本身就接近或超过 20 ms 时，按 ADR 0017「影响」记录数据，交给产品负责人决定。
- 公开仓库的残余风险：GitHub 不能限制哪些工作流用这台 runner，靠的是写权限只给仓库所有者、fork 的运行由人批准。误批一个改了工作流的 fork PR，它的代码就以专用用户在判定机器上运行。没有凭据、只读的工具、每次清空的工作区和临时目录限制了它能拿到和留下的东西，不能阻止它运行，也不能阻止它按绝对路径写专用用户的主目录（所以定期重建）；机器最好放在不能访问其他内网主机的网络里。
- 结束进程只覆盖本任务启动的进程：任务开始之前已经在运行的不在范围里。清理没有运行过的任务（runner 进程被结束、机器断电，或者误批的、没有这一步的工作流）留下的进程，会在之后的任务期间继续运行，要靠定期重建专用用户和重启机器结束。结束的范围也包括任务期间按需启动的、属于专用用户的系统代理，launchd 在需要时重新启动它们。
- PR 合并之前不自动判定冷启动：退化在合并之后 `main` 的运行上才看到，除非合并之前手动触发。
- 只有一台判定机器。它离线时 `main` 上的判定任务排队，不阻止合并；把仓库变量改为 `false` 可以停止排队，这期间冷启动没有判定。
- 锁屏的本机也得到 `handler`，它的数字不是 ADR 0017 要的基线。
