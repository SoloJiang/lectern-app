# ADR 0069：产品能力完成之前，基准任务不卡合并；超标记进 #440，最后统一优化

- 状态：已接受
- 日期：2026-11-25
- 修订：[ADR 0055](0055.md)（分项预算超标时按实测放宽的规则）

## 背景

ADR 0055 规定：分项预算在 CI 上超标、而且 PR 没有改动被测代码时，按实测放宽，每次写一行 ADR。这样仍要等基准跑完才能合并。macOS 托管 runner 经常排不上，一组 PR 的基准要排几个小时；主线上每次推送都会取消上一次推送的运行（`cancel-in-progress`），合并频繁时主线上的基准几乎跑不完。

#432 只改 `tools/automation/Cargo.lock`，`app/open_project` 的中位数是 128 ms 和 133 ms，预算 < 100 ms，合并被挡住。产品负责人的决定（2026-11-25）：「可以适当放开指标卡口，先确保功能完全交付，最后来一起系统性优化」。

## 决策

- 产品能力完成之前，合并只看功能检查：`Checks (Linux, GPUI-free crates)` 和 `Build and test (macOS arm64)` 通过、没有合并冲突。`Benchmarks*` 任务（分片、构建、`Benchmarks (macOS arm64)`）不卡合并，也不等它们跑完。
- 超标不再按 ADR 0055 逐项放宽预算，`budgets.rs` 的值不变。超标的条目记进 [#440](https://github.com/SoloJiang/lectern-app/issues/440)：PR 或提交、条目、实测值、预算。
- 测量的来源：一批合并之后，在主线的提交上建一个 `perf/snapshot-<提交>` 分支，用 `workflow_dispatch` 跑一次 CI。它的并发组与主线不同，后面的合并不会取消它。这次运行里超标的条目记进 #440。
- 顶层预算仍然守住：空闲内存 60 MB（`app/idle_*`）、安装包 80 MB（`app/bundle_size`、`app/dmg_size`）在快照运行里超标时，先查原因，把数字告诉产品负责人，查清之前不再合并可能影响它的 PR。冷启动 20 ms 照旧只在实体 Mac 上判定（[ADR 0052](0052.md)）。
- 功能检查失败照旧挡住合并。不缩小夹具，不为了让基准变绿去改被测代码。
- 产品能力完成之后做一次系统性的性能优化：按 #440 的条目逐项查原因，在实体 Mac 上核对；预算的值要改的，另写 ADR。

放弃的方案：

- 照旧按 ADR 0055 放宽并等基准跑完：每批 PR 挡几个小时，放宽的值也只反映托管 runner 的噪声。
- 删掉基准任务：最后的优化要靠这些数据，任务继续在每个 PR 上运行。

## 影响

- `AGENTS.md`「合并规则」第 2 条。
- `docs/design/ci.md`「任务」：必需检查的说明。
- ADR 0055 的状态行和索引。
- 自审记录写明基准不卡这次合并。

## 已知限制

- PR 上基准任务的结果可能在合并后才出来，甚至被取消；#440 以快照运行为准。
- 两次快照之间合并的多个 PR，超标时分不清是哪一个引入的，要在最后的优化里二分。
