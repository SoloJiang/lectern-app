# ADR 0048：测量构建用 Objective-C 运行时的方法替换取得帧的时刻，只在 `platform` 的 `bench-hooks` feature 里，发布构建不含

- 状态：已接受，管线创建方法的替换已被 [ADR 0049](0049.md) 去掉
- 日期：2026-10-25

## 背景

`bench` 要两类时刻（[bench 设计「需要其他 crate 提供的接口」](../design/bench.md#需要其他-crate-提供的接口)）：

- 冷启动的终点：第一个 drawable 的 `presentedTime`，经 `addPresentedHandler` 读取（[ADR 0017](0017.md)）。
- 滚动、输入、动画的每一帧：帧源要求这一帧的时刻（`requested`）、主线程开始处理的时刻（`started`）、命令缓冲完成的时刻（`completed`）和显示的时刻（`presented`）。

锁定的 gpui-pre 0.3.9（[ADR 0016](0016.md)）不暴露 drawable、命令缓冲和管线描述符。读源码得到的事实：

- `MetalRenderer::draw` 在主线程上依次调用 `-[CAMetalLayer nextDrawable]`、在自己的命令队列上建一个命令缓冲，然后提交。display link 发起的帧用 `presentDrawable:` 加 `commit`；`displayLayer:` 发起的帧（窗口第一次显示、变为前台窗口）用 `commit`、`waitUntilScheduled` 加 `[drawable present]`。两条路径都先经过 `nextDrawable`。
- 帧源是 CVDisplayLink 的 C 回调，经 dispatch source 合并后在主线程上处理。它不是 Objective-C 方法，替换不到。
- 主线程上的帧处理函数先执行 `Window::on_next_frame` 登记的回调，再做布局和绘制。这是公开接口。
- GPUI 的 `profiler` feature 记录帧信号和绘制的开始时刻，但它要 `hdrhistogram`（Cargo.lock 里没有），给被测进程的每个任务加计时，帧日志最多 16 MiB，也没有 `presentedTime` 和 GPU 的完成时刻。

Objective-C 运行时的 `class_getInstanceMethod` 加 `method_setImplementation` 可以替换一个类的方法实现，作用于这个类的所有实例，不改 GPUI 的源码。

## 决策

1. 测量构建用方法替换取得帧的时刻。只替换系统框架的类，不替换 GPUI 自己的类和函数：
   - `-[CAMetalLayer nextDrawable]`：在返回的 drawable 上登记 `addPresentedHandler:`，得到首帧和每一帧的 `presentedTime`。
   - 命令缓冲的具体类的 `-commit`：只在记录期间，给这一帧的命令缓冲登记 `addCompletedHandler:`，得到 `GPUEndTime`。
   - 设备的具体类的 `-newRenderPipelineStateWithDescriptor:error:`：只用于严格 archive 模式。是否需要它，取决于 [platform 设计「未决问题」](../design/platform.md#未决问题)第 1 条。
   - `requested` 来自 `platform` 自己在同一个显示器上建的 CVDisplayLink。它的 tick 与 GPUI 的帧源是同一个垂直同步。`started` 由 `workspace` 在 `on_next_frame` 的回调里报告。这两项都不替换任何方法。
2. 关键约束：
   - 方法替换的代码只在 `lectern-platform` 的 `bench-hooks` feature 里编译（架构规则 6）。只有 `lectern-bench` 的 `probe` feature 打开它，`app` 的 `bench-probe` 经 `lectern-bench/probe` 间接打开。发布构建不含任何方法替换。没有这个 feature 时，接口照样存在，返回 `Unsupported`。`scripts/check_architecture.py` 检查只有 `lectern-bench` 打开这个 feature；bench 第 5 步的 `cargo tree -e features` 检查发布构建里没有它。
   - 失败必须明显，不能静默地测出错的数字。安装时核对类、选择器和类型编码，任何一项不符就返回错误，不安装。探针收到错误后立即报告，并以退出码 3 退出。记录中对不上的帧（没有 `started` 的 drawable、到期限还没有完成时刻的帧、超出容量的帧）计数后交回，bench 把非零计数记为 `error`。
   - 首帧的钩子（`frame::on_first_presented`）在首帧之前只做方法替换本身：一次 `class_getInstanceMethod` 和 `method_setImplementation`，不做 IO，不建线程，不建 Metal 对象。耗时上限 100 µs。这部分计入冷启动的测量，由 `baseline/empty_window_cold_start` 一起测出。逐帧记录的钩子在首帧之后才安装。严格 archive 模式如果实现，首帧之前还要取设备、打开 archive（ADR 0017 要求的读取），它只在 `app/*` 的测量里，开销写进 platform 设计。
   - 替换的实现和 block 在 Metal、Core Animation、CoreVideo 的线程上运行。它们不分配内存，不加锁，不 panic。
   - 钩子依赖 gpui-pre 0.3.9 的调用顺序。按 ADR 0016 升级 GPUI 时，必须重新运行 `just bench baseline/` 和帧基准，确认没有错误计数。
3. 放弃的方案：

   | 方案 | 原因 |
   |---|---|
   | 给 GPUI 打补丁或 fork | ADR 0016：未经确认不得改动锁定的 GPUI。这要人同意 |
   | GPUI 的 `profiler` feature | 新增 `hdrhistogram`。测量构建与发布构建的差别不再只是探针：每个任务都有计时，还有帧日志。仍然缺少 `presentedTime` 和 GPU 的完成时刻 |
   | 用 `on_next_frame` 的回调时刻当作显示时刻 | ADR 0017 不接受：`present` 只表示已安排显示 |
   | 发布构建也安装钩子（例如为桌面版的启动屏障取精确的首帧时刻） | 发布构建会依赖 GPUI 的内部调用顺序。屏障用帧回调近似已经够用（[app 设计「启动屏障」](../design/app.md#启动屏障)） |
   | 替换 C 函数（dyld interpose、改写符号表） | 要在加载时设置，作用于整个进程。GPUI 的 CVDisplayLink 回调是私有的函数指针，替换不到 |

## 影响

- `platform`：新增 `frame` 模块和 `HookError`。`metal` 模块是否实现，取决于「未决问题」第 1 条。设计在 [platform 设计「测量构建的方法替换」](../design/platform.md#测量构建的方法替换)和「帧的时刻」。
- `bench`：`probe` feature 打开 `lectern-platform/bench-hooks`。接口形状的变化写在 bench 设计里。
- `workspace`：记录期间，在每一帧的 `on_next_frame` 回调里调用 `FrameRecorder::frame_started`。
- `app`、`kernel`、`logging` 的设计：桌面版（desktop profile）的启动屏障保持帧回调，不用 `on_first_presented`，因为它只在测量构建里有。这三份设计里「`on_first_presented` 实现以后改用它」的说法随本 ADR 改正。
- 本 ADR 不修订 ADR 0016 和 ADR 0017。ADR 0017「为首帧做的具体约束」要求发布构建的管线用 binary archive。在锁定的 GPUI 上，这只能靠方法替换或改 GPUI 做到，本 ADR 不为发布构建开这个口子。怎样处理写在 platform 设计「未决问题」第 1 条，由人决定。

## 已知限制

- GPUI 的快照改变调用顺序时（例如不在主线程上提交，或换用别的方法取 drawable），钩子失效。按上面的约束，失效的结果是安装出错或错误计数，不是错的数字。
- 测量构建比发布构建多了钩子的开销：首帧之前不超过 100 µs，记录期间每帧几微秒（[platform 设计「帧的时刻」](../design/platform.md#帧的时刻)）。
- CVDisplayLink 从 macOS 15 起标为弃用。GPUI 也在用它。
