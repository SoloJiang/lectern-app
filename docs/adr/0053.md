# ADR 0053：macOS 的基准按分片在几个并行的 CI 任务里运行，再由一个任务合并判定

- 状态：已接受
- 日期：2026-10-27
- 修订：[ADR 0036](0036.md)（「CI」：基准从一个任务改为几个分片任务加一个合并任务）

## 背景

ADR 0036 把 macOS 的基准拆成单独的 `Benchmarks (macOS arm64)` 任务，目标是典型 PR 的 macOS 墙钟时间 ≤ 15 分钟、基准任务 ≤ 12 分钟（[CI 设计「任务」](../design/ci.md#任务)），当时估计基准运行约 8 分钟。

bench 第 5 步（#277）合并后，main 上一次运行（托管的 M1 虚拟机，3 核）的基准这一步是 27.4 分钟：

| 部分 | 第 5 步之前（#273 之后） | 第 5 步之后 |
|---|---|---|
| 构建 `empty_window` | 1 分 58 秒 | 1 分 58 秒 |
| 构建 `bench-probe` 的 `lectern` | 无 | 5 分 33 秒 |
| 构建三个基准目标 | 2 分 51 秒 | 2 分 56 秒 |
| 运行基准 | 约 14.8 分钟 | 约 16.9 分钟 |

`lectern` 的构建每次重新编译依赖，原因是缓存键完全命中时 `rust-cache` 不再保存，#278 改键解决。剩下的主要是运行时间。按报告里每个基准的耗时（同一次 PR 运行）：`time` 目标 582 s，其中 `code_intel/` 253 s；`memory` 目标 179 s，其中 `code_intel/` 81 s；`process` 目标 191 s。同一个提交在 PR 上和 main 上的任务分别是 17.4 和 21.7 分钟，虚拟机之间的差别也有几分钟。

产品负责人的决定：拆成并行的任务，不减少样本，不放宽预算，不用 bench 设计里「减少启动次数」的后备方案。

## 决策

**分片**

- 预算按 ID 分成几个分片，分片表写在 `lectern-bench` 里（名字和 ID 前缀），最后一个分片收下其余所有预算。每条 `Active` 和 `Planned` 的预算恰好属于一个分片，由单元测试检查。
- 关键约束：`process` 目标的全部预算在同一个分片里。插件列表和语言服务器列表来自这个目标的一份报告，`plugin/*` 的展开依赖它。
- 第一版分三片：`code_intel/` 的预算（`time` 和 `memory`，要 10 万文件的夹具）；`process` 目标；其余。按上面的数字，每片的运行时间约 3 到 7 分钟。分片的划分是可以调整的数据，不是本 ADR 的决策：按报告里最慢的基准重新划分不需要新的 ADR。
- 采样规则、样本数、预算和判定都不变。每个分片只运行自己的预算，其余记为「在另一个分片」。

**CI**

- 每个分片是一个 macOS 任务（`Benchmarks shard (<名字>)`），运行 `just bench --shard <名字>`，只构建这个分片要用的基准目标和程序，上传自己的报告。分片任务不判定，报告写好了它就成功。
- 合并任务沿用检查名 `Benchmarks (macOS arm64)`，在全部分片任务结束后运行（分片失败时也运行），合并全部分片的报告并判定：每条预算在全部分片里恰好有一次不是「在另一个分片」的结果，缺少分片的报告、重复或缺少条目都是错误。`::error`、`::notice` 和任务摘要都在这个任务上，所以检查名、注释和合并规则看到的东西不变。合并只读 JSON，在 Linux runner 上运行。
- 缓存：每个分片用自己的 `rust-cache` 键，分片之间不互相覆盖。10 万文件的夹具缓存只在 `code_intel/` 分片上还原和保存。
- 目标：典型 PR 的 `Benchmarks (macOS arm64)`（从第一个分片开始到合并结束）≤ 15 分钟，最长的分片 ≤ 12 分钟。超过时先按报告重新划分或增加分片，不减少样本。
- 本地的 `just bench` 不带 `--shard` 时与现在相同：一次运行全部预算，最后合并。判定机器的 `Judge (physical Mac)` 不分片，只有一台机器。

**放弃**

- 只按基准目标分成 `time`、`memory`、`process` 三个任务：合并工具不用改，但 `time` 目标一片就有 582 s 的运行，加上构建约 14 分钟，达不到 12 分钟。
- 减少启动次数（bench 设计原来的后备方案）：`app/idle_empty` 从 3 次降到 1 次只省约 11 秒，一个离群值（本机见过一次 124 MB）就会误判；端到端基准还没有实现。
- PR 上只运行受影响的基准：理由同 ADR 0036。

## 影响

- `bench`：分片表、`--shard` 选项、「在另一个分片」的状态、合并多个分片目录的报告、报告的 `benches` 带分片名，写进 [bench 设计](../design/bench.md)「报告」「`just bench` 与 CI」「测试」，由 #279 的实现 PR 完成。
- CI：`.github/workflows/ci.yml` 和 [CI 设计「任务」](../design/ci.md#任务)。macOS 任务从两个变成一个加分片数，每次 PR 运行占用的 macOS runner 分钟数增加。
- ADR 0036 的状态行和索引注明「CI」一节已被本 ADR 修订。

## 已知限制

- 各分片在不同的虚拟机上运行，合并后的 `host` 取第一份报告的；虚拟机之间的差别会进入不同分片的预算。
- 每个分片都要准备环境、还原缓存和编译，总的 runner 时间比一个任务多。
- 一次 PR 运行同时占用分片数加一个 macOS runner；同时运行的 PR 多时会排队。
