# ADR 0056：GPUI 降到 gpui-pre 0.3.7；一个单独的自动化工作区用 gpui-mcp 打过补丁的快照接入 gpui-mcp

- 状态：已接受
- 日期：2026-10-29
- 修订：[ADR 0016](0016.md)（锁定的版本：gpui-pre `=0.3.9`、gpui-component `=0.7.3` 改为 `=0.3.7`、`=0.7.0`）

## 背景

agent 要在真实窗口里检查界面：点击、按键、读元素树、截图。现有的 `ui_probe` 只读（`hello`、`ui_tree`、`screenshot`、`quit`，[ui_probe 设计](../design/ui_probe.md)），输入方法留给 P1。computer-use 驱动不了 GPUI 窗口：后台点击只设置辅助功能标志，全屏控制会被其他应用的覆盖层挡住（#283 的实机检查，2026-10-29）。

社区已有 [gpui-mcp](https://github.com/themixednuts/gpui-mcp)（Apache-2.0）：应用内的桥接加一个 stdio 上的 MCP 服务端，按元素 ID 点击、输入、等待元素出现、截图。它需要给 GPUI 打补丁（`automation.patch`，2365 行，改 10 个文件），补丁系列只覆盖 gpui-pre 0.3.5–0.3.7。原因是维护跟不上，不是技术限制：作者在 2026-10-01 应 [issue #1](https://github.com/themixednuts/gpui-mcp/issues/1) 加入 gpui-pre 支持，之后 gpui-pre 每周发布（0.3.8 在 10-05，0.3.9 在 10-12，0.3.10 在 10-26），补丁没有跟进；最后一次推送是 10-09。实测 0.3.7 的补丁在 0.3.8 上有 1 处冲突，在 0.3.9 上有 7 处（`element.rs`、`window.rs`）。

降级的试验（本地分支，2026-10-29）：gpui-pre、gpui-pre-platform 改为 `=0.3.7`，gpui-component、gpui-kit-assets 改为 `=0.7.0`（gpui-component 0.7.0 精确依赖 gpui-pre 0.3.7），再把 gpui-pre 换成 gpui-mcp 仓库的补丁版，并以可选依赖加入 gpui-mcp：`cargo check --workspace --all-features --all-targets` 没有错误。`cargo deny` 多出两类错误：git 来源未放行，以及 `libbz2-rs-sys` 的许可证 `bzip2-1.0.6`（经 gpui-pre-http-client 0.3.7 → async-compression → bzip2 引入，0.3.9 的依赖树里没有）。

产品负责人的决定（2026-10-29）：降到 0.3.7，接入 gpui-mcp。

## 决策

- 锁定的版本：
  - `gpui = { package = "gpui-pre", version = "=0.3.7" }`，`gpui_platform = { package = "gpui-pre-platform", version = "=0.3.7", features = ["font-kit"] }`。
  - `gpui-component = "=0.7.0"`，`ui` 的 `gpui-kit-assets = "=0.7.0"`。
  - 四者仍按 ADR 0016 一起升级：GPUI 快照等于 gpui-component 发布时用的版本。
- 主工作区不打补丁：发布构建和 `just` 的检查、测试、基准都用 crates.io 上未改动的 gpui-pre 0.3.7。`deny.toml` 不放行任何 git 来源。
- 打过补丁的 GPUI 和 gpui-mcp 只出现在一个单独的自动化工作区（仓库里的一个目录，有自己的 `Cargo.toml` 和 `Cargo.lock`，被主工作区 `exclude`）。Cargo 的 `[patch]` 只在被构建的那个工作区生效，所以补丁到不了主工作区的任何构建：
  - 它的 `[patch.crates-io]` 把 `gpui-pre` 指向 `https://github.com/themixednuts/gpui-mcp` 的固定提交（`rev`，40 位哈希），不用分支；`Cargo.lock` 记下这个提交。
  - 用 gpui-mcp 仓库里的整份补丁版，含三个补丁：`automation`（桥接需要）、`font-fallback`（字体回退到其他字族时保留请求的字重和字形）、`grid`（只新增 CSS grid 的构造接口）。不把补丁版复制进本仓库（约 8 MB），也不自己去掉后两个补丁。
  - 它只有一个二进制：按路径依赖主工作区的 crate 组装出与 `lectern` 相同的应用，在首帧之后安装 gpui-mcp 的桥接（`default-features = false, features = ["gpui-pre"]`）。首帧之前的规则不变（[ADR 0017](0017.md)）。
  - `app` 为此提供一个不依赖 gpui-mcp 的扩展点：首帧之后把窗口交给调用方传入的回调。主工作区里没有 gpui-mcp 的代码，`--all-features` 的检查不会编译到它。
  - 这是 [ADR 0048](0048.md)、[ADR 0049](0049.md) 里「不改 GPUI」的一个例外，由产品负责人批准，只限这个工作区；发布构建仍不改 GPUI。
  - 它算 tool 层，不进安装包。主工作区的架构检查（`scripts/check_architecture.py`、插件规则 7）不覆盖它。
- 许可证：降级让主工作区多了 `libbz2-rs-sys`（许可证 `bzip2-1.0.6`，宽松许可证，经 gpui-pre-http-client 0.3.7 引入，与 gpui-mcp 无关），`deny.toml` 放行它。其余规则不变，GPL 仍被拒绝（架构规则 8）。
- MCP 服务端 `gpui-mcp-server` 不进本仓库的依赖图：由 `just` 配方用 `cargo install --git … --rev <同一个提交> --locked` 装到 `target/` 下，依赖由它自己的 `Cargo.lock` 决定。
- 应用和服务端用同一个 `HOME`：gpui-mcp 在 macOS 上把端点描述写在 `$HOME/Library/Application Support/gpui-mcp`，而调试运行的应用用临时 `HOME`（不读用户真实的 agent 会话目录）。配方给两者同一个只属于当前用户（0700）的固定目录作 `HOME`。
- `ui_probe` 保留已实现的 P0（`ui_tree`、`screenshot` 的函数也用在 `#[gpui::test]` 和 insta 快照里）。它的 P1 输入方法（`actions`、`dispatch`、`key`）不再做，agent 的输入改由 gpui-mcp 提供；`locate` 仍留在 P1。
- 以后升级 GPUI 的前提：gpui-mcp 有目标版本的补丁，或者我们自己移植补丁（优先提交给上游，DBFlux 在 issue #1 里就是这样做的）。没有补丁时不升级。

放弃的方案：

- 留在 0.3.9，自己把补丁移植过去：要解决 7 处冲突，此后每次升级都要自己移植；先用上游已有的版本，以后移植时再提交给上游。
- 扩展 `ui_probe` 的 P1 输入并自写 MCP 服务端：不改 GPUI，但工具集要从头做（点击、按键、Action、等待、截图对比）；产品负责人选择马上可用的完整工具集。
- 在主工作区里打补丁、用 feature 打开桥接：`[patch]` 不能按 feature 生效，发布构建会链接第三方修改过的 GPUI。
- 把补丁版复制进本仓库：便于审阅，但多 8 MB，升级时要自己重新生成；自动化工作区只在调试时构建，固定提交已足够。

## 影响

- 根 `Cargo.toml`、`Cargo.lock`、`crates/ui/Cargo.toml`、`deny.toml`：版本与许可证（降级 PR）。根 `Cargo.toml` 里没有 `[patch]`。
- 这次降级就是一次 GPUI 变更，按 [ADR 0048](0048.md) 的要求重新运行 `just bench baseline/` 和帧基准，确认 Metal 钩子没有错误计数。顶层预算（冷启动 20 ms、空闲内存 60 MB、安装包 80 MB）不按 ADR 0055 放宽，数字写进降级 PR。
- 设计文档里按 0.3.9 或 gpui-component 0.7.3 的源码写下的事实（[ADR 0034](0034.md) 的编辑器、[ADR 0048](0048.md) 与 [ADR 0049](0049.md) 的源码事实、`kernel`、`platform`、`terminal_view`、`file_reader`、`ui` 的相关段落）在降级 PR 里逐条对照 0.3.7 的源码，不成立的改正。
- [cargo-workspace 设计](../design/cargo-workspace.md)的锁定版本随降级 PR 更新。
- `app`：首帧之后的窗口回调；自动化工作区的位置与二进制、`justfile` 配方、MCP 客户端配置，由 [app 设计](../design/app.md)负责（接入 PR）。CI 不构建自动化工作区。
- [ui_probe 设计](../design/ui_probe.md)与[技术调研「UI 结构探针」](../design/tech-research.md#6-ui-结构探针)随本 ADR 更新：P1 输入改由 gpui-mcp 提供。

## 已知限制

- gpui-mcp 还没有正式版本，只有 main 分支受支持；固定的提交可能缺少之后的修复。
- 自动化构建与发布构建的 GPUI 不完全相同（三个补丁，其中 `font-fallback` 改变回退文字的显示）；在自动化构建里看到的回退字体问题要在普通构建里再确认。
- 自动化工作区的 `Cargo.lock` 与主工作区分开，主工作区升级依赖后要同步更新它。
- 自动化工作区不经 `cargo deny`、架构检查和 CI：它只在本机调试时构建，不发布；它的第三方依赖（gpui-mcp、xcap、MCP 的依赖）没有许可证与安全公告检查。
- 桥接能在窗口里点击和输入（包括终端视图）。gpui-mcp 只接受同一用户的本机连接（私有目录里的端点描述和令牌）；已经能以本用户身份运行程序的进程不在防护范围内，与 Analyze 的威胁模型一致。
- gpui-mcp 的截图经 xcap 截取系统窗口，macOS 会要求运行服务端的应用有屏幕录制权限；不想授权时用 `ui_probe` 的 `screenshot`（窗口自己的渲染器读回，不需要权限）。
- gpui-mcp 只把带 `.id(...)` 的元素当作节点；没有 ID 的元素点不到。
- gpui-mcp 用 `tracing` 写日志；Lectern 不安装 `tracing` 的订阅者，降级试验里 `tracing` 也没有开 `log` feature，所以这些记录被丢弃，不进入 Lectern 的日志（[ADR 0046](0046.md)）。自动化工作区的依赖若打开了这个 feature，接入 PR 要过滤掉 gpui-mcp 的 target。
