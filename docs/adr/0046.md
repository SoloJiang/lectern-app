# ADR 0046：运行日志经 `log` 门面写入本机文件，字段类型化，详细日志由用户开启

- 状态：已接受
- 日期：2026-10-22

## 背景

用户 2026-10-22 的要求：「在项目设计的时候，记得考虑 ide 运行的日志可追溯或者主动开启可以有更详细的日志落盘」。

现状：

- `kernel`、`executor`、`cache`、`fs_watch`、`syntax`、`code_intel` 各有一个只用标准库的 `util::log`，向 stderr 写一行带前缀的文字，合计约 80 处调用；`i18n` 也写 stderr。各设计文档写的是「由 `app` 重定向到日志文件」，但 `app` 还没有实现，文件位置、保留期限和记录格式都没有规定。从 Finder 启动的应用，stderr 不进入用户能找到的文件。
- `kernel` 的 `contain` 和 `executor` 的 `catch` 捕获 panic 后「只记日志」，记录里没有插件和激活的标识，事后无法对应到具体的那次激活。
- 发布构建里已经有 `log` 0.4.34 和 `tracing` 0.1.44（`cargo tree --target aarch64-apple-darwin -p lectern-app -i log`）：`gpui-pre`、`gpui-pre-macos`、`metal` 等经 `log` 输出警告，`gpui-pre-sum-tree` 依赖 `tracing`。`tracing-subscriber` 不在 Cargo.lock 里。
- 约束：冷启动 20 ms、首帧前不读 Lectern 自己的文件（[ADR 0017](0017.md)）；空闲内存 60 MB；安装包 80 MB（[ADR 0018](0018.md)）；UI 线程不做 IO；Analyze 转发的请求含提示词，凭据不进沙箱（[ADR 0019](0019.md)）。

门面开销的实测（Linux x86_64 四核虚拟机，release、thin LTO，每项 2000 万到 2 亿次调用，运行两次）：

| 调用 | 每次 |
|---|---|
| 空循环 | 0.34–0.60 ns |
| `log::debug!`，低于全局级别 | 0.35–0.41 ns |
| `tracing::debug!`，没有订阅者 | 0.61–0.63 ns |
| `log::debug!`，全局级别放行，日志器按 target 拒绝 | 4.0–4.4 ns |
| `log::info!`，日志器只计数 | 10.5–10.9 ns |

## 决策

### 门面与 crate

- 调用点经 `log` 0.4，只开 `std` 和 `kv` 两个 feature：这样配置时没有传递依赖，许可证 MIT OR Apache-2.0，crate 本身已经链接在发布构建里。GPUI 和第三方库的记录进入同一个日志器。
- 新建 `logging` crate（`lectern-logging`），放在 kernel 层。kernel 层的 crate 只能依赖 kernel 层，`kernel` 和 `services` 也要记日志，所以它不能放在基础设施层。它的依赖只有 `log`，不依赖 `platform`、`executor` 和 GPUI。它分为两部分：
  - 调用点：`error!`、`warn!`、`info!`、`debug!`、`trace!` 宏、类型化字段、关联作用域，所有 crate 都用。
  - 落盘（`sink` feature）：内存缓冲、写盘线程、滚动与清理、过滤、panic 钩子、导出。只有 `app` 和 tool 层启用。
- `kernel` 和 `executor` 依赖 `lectern-logging`（经它间接依赖 `log`）。[kernel 设计](../design/kernel.md)「只用标准库」和 [executor 设计](../design/executor.md)「只用标准库和 `lectern-kernel`」的约束只为这一个依赖放开，其他外部依赖仍按原约束先写 ADR。
- 工作区不开启 `log` 的 `max_level_*`、`release_max_level_*` feature：它们在编译期去掉低级别的调用，发布构建就无法开启详细日志。

放弃的方案：

| 方案 | 原因 |
|---|---|
| `tracing` + `tracing-subscriber` | 新增 `tracing-subscriber`、`sharded-slab`、`thread_local`、`tracing-log`、`nu-ansi-term`，按 target 过滤的 `env-filter` 还要 `matchers` 和 regex；kernel 从零依赖变成依赖 `tracing`、`tracing-core`、`pin-project-lite` 和过程宏；GPUI 的记录走 `log`，仍要桥接。span 放在 executor 的每次 poll 上开销更高，需要的关联字段用线程本地的作用域就能带上 |
| 只用标准库的自有门面，由 `app` 接上钩子 | 收不到 GPUI 的 `log` 记录，落盘部分仍要实现 `log::Log`，级别检查和全局开关要再写一份 |
| 各 crate 直接调用 `log` 的宏 | 消息和字段可以是任意字符串，内容数据在编译期挡不住 |
| 系统统一日志（`os_log`） | 要在 `platform` 写 FFI；用户附到 issue 时要另跑 `log collect`；按插件过滤和保留期限不受 Lectern 控制。错误也不转发，以后需要时另写 ADR |

### 默认日志

- 级别：error 是操作失败、结果或数据被放弃（分库停用、插件因 panic 失败）；warn 是降级后继续（跳过坏行、重试、退回慢路径）；info 是生命周期事件（启动耗时、插件激活及耗时、项目打开与关闭、日志设置变化）。Lectern 的 target 默认 info，第三方 target 默认 warn。
- target 是 crate 的短名（`lectern_cache` 记为 `cache`）；插件另记 `plugin` 字段，取 kernel 的稳定 ID。
- 位置：macOS 是 `~/Library/Logs/Lectern/`，Linux（CI）是 `$XDG_STATE_HOME/lectern/logs`，变量不可用时是 `~/.local/state/lectern/logs`，由 `platform::dirs::logs()` 给出。
- 每次运行新开一个文件，单个文件到 4 MiB 滚动；默认文件合计不超过 20 MiB、50 个、14 天，超出时从最旧的删起。
- 限流：同一调用点的 error、warn、info 每 10 秒最多写 20 条，其余只计数，下一条写出的记录带上省略的条数。Lectern 的调用点在宏展开的静态变量里计数；第三方记录（GPUI 等直接调用 `log` 的）按（target、文件、行）在一张固定大小的表里计数，规则相同，并且全部第三方记录合计每 10 秒最多 50 条。限流的判断在编码之前，被限流的调用不编码。

### 详细日志

- 开启方式：环境变量 `LECTERN_LOG` 或命令行 `--log <过滤>`（命令行优先），只对本次运行有效；在设置里开启的写进日志目录的状态文件，重启后仍有效，到期自动关闭，默认 24 小时。
- 过滤按 crate 或插件：`debug`（Lectern 的全部 target）、`cache=trace`（一个 crate）、`@review=debug`（一个插件作用域内的记录）、`gpui=info`（第三方 target 要单独写出）。
- 开启期间另写一组详细文件，收所有级别的记录，单个文件 16 MiB 滚动，合计不超过 200 MiB、保留 3 天；默认文件照常只收 info 及以上。
- 详细日志只降低级别门槛、扩大容量，隐私规则不变。

### 记录格式与关联

- JSON Lines，一行一条，每条不超过 4 KiB。固定字段：UTC 时间（毫秒）、进程启动后的微秒数、级别、target、线程名、源码位置、消息。处在作用域里的记录带关联 ID：`plugin`、`act`（激活序号）、`task`（executor 任务序号）、`session`、`review`、`req`、`analysis`。每个文件的第一行写格式版本、运行 ID、应用版本与构建、系统版本、架构和当前过滤。
- `kernel` 在每段由 `contain` 包住的插件代码外设 `plugin` 和 `act`；`executor` 在每次 poll 和最终 drop 外设 `task` 及闸门所属的插件与激活，提交任务时继承提交方的作用域。
- panic 钩子在首帧前装上，记录位置、线程、作用域和处理过的消息，然后交给原来的钩子；`contain` 和 `catch` 的调用方再记一条带阶段的失败记录。钩子等写盘线程把这条记录交给内核，最多等 100 ms，因此随后中止的进程也留下这条记录。写盘线程启动之前发生的 panic，由钩子在当前线程上直接写文件。
- 正常退出时 `app` 关闭日志，写入结束记录；下次启动发现上一次运行没有结束记录时，记一条 info。
- 导出：把最近几次运行的文件和一份清单复制到一个目录，供用户附到 issue。

### 隐私（约束）

- 不得记录：文件内容、diff 内容、提示词与回复、会话 JSONL 的内容、终端输出、⌘K 的查询文本、提交说明与 PR 的文字、token、凭据、API key、环境变量的值、子进程的参数、Analyze 转发的请求体、响应体和请求头。
- 可以记录：路径（主目录写成 `~`）、git OID、会话 UUID、长度、计数、耗时、错误种类与系统错误码、URL 的协议、主机和路径（不含 userinfo、查询串和片段）。
- 执行方式：
  - 宏的消息只接受字符串字面量；字段值必须实现 `Field`，它产出的 `Value` 只能由数字、布尔、`&'static str`、路径、OID、UUID、URL 和 `io::Error` 的种类构造，`String` 和非 `'static` 的 `&str` 编译不过。
  - `clippy.toml` 禁止直接调用 `log` 的宏；各 crate 接入完成后，非 tool crate 开启 `print_stderr` 和 `print_stdout`。
  - panic 消息按 payload 的类型区分。`&'static str` 的（`panic!("字面量")`、`Option::unwrap`）是代码里的文字，只取第一行、不超过 256 字节、形似凭据的串打码。格式化出的 `String`（`panic!("{x}")`、`Result::expect`、带消息的 `assert!`、std 的字符串切片越界等）只记源码位置、消息长度，以及固定表里的 std 前缀（如 `byte index`、`index out of bounds`）和它后面引号、反引号之外的数字；其余文字一律不写。
  - 第三方记录的消息：字面量按上一条的 `&'static str` 处理；格式化的只取第一行，双引号、单引号和反引号括住的片段换成 `…`（反引号里只保留 `Option::unwrap()` 这类 std 方法名和 `None`、`Err` 等变体名），第一个 `: ` 之后的文字换成 `…`，形似凭据的串打码，不超过 128 字节。
  - 测试：trybuild 的编译失败测试；落盘部分的处理测试，含字符串切片越界和格式化 `panic!` 的金丝雀；每个接入的 crate 有金丝雀测试：在 trace 级别运行一次带金丝雀字符串的流程，日志文件里没有金丝雀。
- 详细日志不放宽以上任何一条。

### 性能（约束）

- 低于全局级别的调用只读一个原子量，不超过 2 ns；全局级别放行、按 target 拒绝的不超过 5 ns；写出的调用在调用线程上编码并放进缓冲，不超过 1 µs，不分配内存。
- 调用线程不做 IO。记录进入有界的双缓冲，由名为 `lectern-log` 的线程写盘；缓冲满时丢弃新记录并计数，调用线程不等待（panic 钩子除外）。写盘线程没有周期性唤醒。
- 首帧前只做内存操作：装日志器和 panic 钩子、读 `HOME` 与 `LECTERN_LOG`、解析过滤，合计不超过 20 µs；不打开文件、不建线程。这期间的记录进一个 64 KiB 的缓冲，启动屏障放开后才建线程、建目录、写盘。唯一的例外是上文首帧前的 panic，它不在冷启动的测量路径上。
- 运行时缓冲 256 KiB，详细日志开启时 1 MiB。默认配置下日志占空闲内存不超过 512 KiB。
- 基准：`log/disabled_call`、`log/filtered_call`、`log/enabled_call`、`log/contended_call`、`log/third_party_limited`、`log/install_early`、`log/idle_memory`。

## 影响

- 新增 `crates/logging`（本 PR 只有 AGENTS.md）和 [logging 设计](../design/logging.md)，后者负责接口、记录格式、缓冲、滚动、过滤、处理规则和测试；[工作区与 crate 划分](../design/cargo-workspace.md)的 kernel 层加入 `logging`。
- `platform`：`dirs::logs()`。`app`：首帧前安装、启动屏障放开后启动、退出时关闭，解析 `--log`。
- `kernel`、`executor`、`cache`、`fs_watch`、`syntax`、`code_intel`、`i18n`、`agents`、`review` 等按 logging 设计「对其他 crate 的要求」的顺序接入，各自一个 PR。接入时删掉 stderr 的写法，并改掉各自设计文档里「写到 stderr、由 `app` 重定向」和 kernel「只用标准库」的描述；改之前，以本 ADR 为准。executor 设计的依赖一节在本 PR 里已经加上 `lectern-logging`。
- `bench` 加上述基准；CI 加 `clippy.toml` 的禁用宏，架构检查限制 `sink` feature 和 panic 消息接口的使用位置。
- 模板 [TEMPLATE.md](../design/TEMPLATE.md) 增加「日志与诊断」一节，[design-doc 技能](../../.claude/skills/design-doc/SKILL.md)要求填写；AGENTS.md「产品原则」加一条。

## 已知限制

- 类型化字段挡住的是无意的泄露。把内容当作路径传入、泄漏成 `&'static str` 这类有意的写法挡不住，靠审阅和金丝雀测试发现。
- 第三方格式化消息在第一个 `: ` 之前（没有 `: ` 时是整行）不带引号的插值内容，如 `log::warn!("{x}")`，最多保留 128 字节。
- 格式化的 panic 消息只剩位置、长度和 std 前缀，Lectern 自己的 `panic!("{x}")` 要靠源码位置定位。
- 设置里开启的详细日志从启动屏障放开后才生效，首帧前的 debug 记录要用 `LECTERN_LOG` 或 `--log`。
- 日志目录不可用时只有内存缓冲，进程退出即丢失。
- 进程被 `SIGKILL` 或系统崩溃时，还在缓冲里的记录丢失。
- 非 UTF-8 的路径字节写成替换字符。
