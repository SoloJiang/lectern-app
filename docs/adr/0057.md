# ADR 0057：产品能力完成之前，`app/open_diff` 在 CI 上按 < 120 ms 判定

- 状态：已接受
- 日期：2026-10-30
- 修订：[技术调研「性能预算」](../design/tech-research.md#性能预算)（「打开一个会话的 Diff < 50 ms」在 CI 上的判定值）

## 背景

`app/open_diff` 在 [#322](https://github.com/SoloJiang/lectern-app/pull/322) 第一次生效：测量构建打开一个合成仓库，再打开一个 Claude Code 会话的 Diff，从请求到 `DiffShown` 里程碑的那一帧（[bench 设计「进程级基准」](../design/bench.md#进程级基准)）。托管的 `macos-15` runner 上 5 次启动是 97.7、88.1、93.6、112.0、93.5 ms，中位数 93.6 ms；超标后再测的一轮中位数 96 ms。预算是中位数 < 50 ms。

同一次运行里，审阅引擎单独测量的 `review/open_session_50`（进程内，从 `open` 到第一份 `Ready` 快照）是 10.9 ms，预算 < 35 ms。空窗口的冷启动 `baseline/empty_window_cold_start` 是 164 ms，目标是 20 ms：这台 runner 上和帧有关的时间比实体 Mac 慢得多。本机（Apple M5 Pro）的 debug 自动化构建里，应用自己记下的 `diff shown` 的 `took_us`（从屏幕打开到第一屏的 diff 行）是 34–49 ms。

产品负责人的决定（2026-10-28，[ADR 0055](0055.md)）：产品能力完成之前，CI 上超标的预算按实测放宽，不再重跑和等待确认。ADR 0055 的规则写的是分项预算（`Tier::Share`）；`app/open_diff` 是技术调研表里的一项（`Tier::Top`），但不是 ADR 0055 排除的那三项（冷启动 20 ms、空闲内存 60 MB、安装包 80 MB）。负责推进的会话按这个决定处理它（2026-10-30）。

## 决策

- `app/open_diff`：CI 上的判定值从中位数 < 50 ms 改为 < 120 ms。有记录的最差中位数是 96 ms，120 ms 留 25% 的余量。测量方式、夹具和启动次数不变。
- 技术调研表里的目标 < 50 ms 不变，是产品能力完成之后要核对的值。
- 产品能力完成之后，按实体 Mac（判定机器，[ADR 0052](0052.md)）上的实测核对：达到 50 ms 时改回；达不到时查原因，另写 ADR。
- 冷启动、空闲内存、安装包仍不按这条处理（ADR 0055）。

放弃的方案：

- 把 `app/open_diff` 改为只在判定机器上判定（像冷启动那样）：判定机器还没有注册（ADR 0052），这一项就没有人判定了。
- 不放宽、先查原因：挡住 #15、#30 的完成，与 ADR 0055 的决定相反。

## 影响

- `lectern-bench` 的 `budgets.rs`：`app/open_diff` 的 `Limit::TimeBelow`。
- `docs/design/tech-research.md` 的性能预算表、`docs/design/bench.md` 的预算表、`docs/design/review_view.md` 的「性能」写这个数的地方。

## 已知限制

- 托管 runner 上的数字里有多少是 Lectern 自己的时间、多少是 runner 的帧节奏，还没有分开：`app/open_diff` 的备注从 #322 起同时记下应用日志里的 `took_us`，下一次 CI 运行之后可以比较。
