# ADR 0035：10 万文件的仓库空闲内存 < 120 MB，按份额分配；解析后的 index 计入 git

- 状态：已接受
- 日期：2026-10-19
- 修订：[ADR 0030](0030.md)（「内存与磁盘的目标份额」：10 万文件形状的份额之和不再对照 monorepo 的 100 MB）

## 背景

[ADR 0017](0017.md) 的空闲内存预算只有两个形状：空窗口 < 60 MB，打开 cloudprint-miniapps 量级的仓库（728 个跟踪文件、11 个 worktree）< 100 MB；[ADR 0029](0029.md) 让两者在后台工作暂停时和全部完成后都适用。`project`、`code_intel` 和 `app/index_100k` 还用一个 10 万文件的大仓库（[project 设计「性能」](../design/project.md#性能)的 `Shape::monorepo(100_000, 2_000)`，测内存时 17 个 worktree），它的各项份额没有总预算，也没有加总。ADR 0030 要求 `code_intel` 的 10 万文件份额（≤ 20 MB）「在 monorepo 100 MB 下」，但没有给出其余份额。

当前 worktree 解析后的 index（`git` 的 `TrackedPaths`）由 `git` 构造，fs_watch 的过滤器（`git` 实现的 `PathFilter`）和 `project` 保留的 worktree 句柄共用一份。它的归属有两个问题：

- 归属不对：`fs_watch/resident` 的定义含这份 index，而 fs_watch 既不构造它，也不决定它的布局。
- 缺失：10 万文件时这份 index 是 13.5 MB（project 第 5 步，[#127](https://github.com/SoloJiang/lectern-app/pull/127)），加上 `core.ignoreCase` 的折叠顺序和忽略规则，过滤器连同句柄是 13.9 MB（本 ADR 同时加入的 `git/filter_100k_bytes`，Linux 容器），而 `fs_watch/resident` 只有 11 个 worktree、728 个文件时的 < 1 MB。

`git` 的工作区比较（`changes`、`refresh`）不用 `TrackedPaths`，自己再解析一次 index（gix 的 `State`、逐条的 stat 与标志、`core.ignoreCase` 的折叠副本），按校验和缓存在 `Worktree` 里，句柄不释放就一直保留。项目主页统计「会话外的改动」要做一次全量比较，`project` 保留当前 worktree 的句柄（`review` 按 [git 设计「数据流与线程」](../design/git.md#数据流与线程)也保留），所以这份 index 在 ADR 0017 的采样状态里，而没有任何份额计入它。

10 万文件时实测（Linux 容器，进程内存活字节）：`project/resident_100k_bytes` 12.7 MB，`git/filter_100k_bytes` 13.9 MB；新 `Worktree` 上一次 `changes` 期间的峰值 65.8 MB，返回并丢掉改动集之后 `Worktree` 还持有 39 MB，几乎都是比较自己解析的 index。

## 决策

**归属：每个字节只计一次**

- 几个 crate 共用的结构，计入定义并构造它的 crate：大小由它的数据布局决定。使用方的预算不含它，基准在对照的两边都持有它，或者单独测量后不计入。
- `git`：fs_watch 过滤器的全部内容，即解析后的 index（与 `project` 的句柄共用的 `TrackedPaths`）、`core.ignoreCase` 的折叠顺序和忽略规则。由 `git/filter_cloudprint_bytes`（< 1 MB）和 `git/filter_100k_bytes`（≤ 16 MB）测量。
- `fs_watch`：只有本 crate 自己的状态（仓库与 worktree 状态、目标、订阅、reflog 进度、目录缓存、暂存、配置清单）。`fs_watch/resident`（cloudprint 形状）和新增的 `fs_watch/resident_100k` 都 < 1 MB，不含过滤器。
- `project`：不变，`project/resident_*` 不含过滤器。

**空闲时不保留比较用的 index（关键约束）**

- 工作区比较解析的 index 只在一次 `changes` / `refresh` 调用内持有，调用返回时释放；下一次比较重新解析（10 万文件时一次干净的全量比较从保留 index 时的 0.82–0.88 s 变为约 1.0 s，都在后台，`git/changes_clean_100k` 按重新解析测量，< 2 s；macOS CI 上是 9 s 多，这一行在 `git` 修正之前是计划中，见 git 设计「与设计的差异」）。采样状态里没有它。`git/compare_100k/retained_bytes`（调用返回、丢掉改动集之后 `Worktree` 仍持有的字节，< 1 MB）验证这一条；`git` 第 4 步实现，之前是计划中。
- 比较期间的内存是临时内存，与 ADR 0029 的建索引临时内存一样不设顶层预算，由 `git/compare_100k/peak_bytes`（≤ 72 MB）约束。
- 降低峰值的办法：比较与 `tracked` 共用一次解析，即一份带 stat、标志和 OID 的连续存储同时给出 `TrackedPaths` 和比较需要的条目（10 万文件估计约 12 MB，现在是 39 MB 加 13.9 MB 两份），与下文 `TrackedPaths` 和 `FileList` 共用路径与 OID 的改动一起做。

**10 万文件的总预算**

- 新增顶层预算 `app/idle_100k` 和 `app/idle_100k_indexed`：打开 10 万文件、17 个 worktree 的仓库，测量方式与 `app/idle_monorepo`、`app/idle_monorepo_indexed` 相同，中位数 < 120 MB。cloudprint 形状的 100 MB 不变。
- 分配：空窗口的部分 < 60 MB（ADR 0017），打开这个仓库增加的部分 ≤ 60 MB：

| 份额 | 预算 | 实测 |
|---|---|---|
| `project`：文件列表、facts、子项目及其缓存（`project/resident_100k_bytes`） | < 16 MB | 12.7 MB |
| `git`：过滤器与它共用的解析后 index（`git/filter_100k_bytes`）；比较用的 index 不在其中（见上） | ≤ 16 MB | 13.9 MB |
| `fs_watch`：自己的状态（`fs_watch/resident_100k`） | < 1 MB | 计划中 |
| `code_intel`：常驻（[code_intel 设计「性能」](../design/code_intel.md#性能)） | ≤ 10 MB | 计划中 |
| `cache`：项目分库的连接与页缓存（页缓存合计 ≤ 6 MiB，其中应用级分库的 ≤ 2 MiB 在空窗口里） | ≤ 4 MiB | 3.8 MiB（`cache/memory`，含应用级分库） |
| `agents`：会话列表（1000 个会话，[agents 设计「性能」](../design/agents.md#性能)的估算） | 约 1 MB | 没有基准 |
| 余量：首页统计改动的改动集（见下，≤ 4 MB）、`project_home`、`worktrees` 等尚未设计的部分 | 12 MB | 改动集在本 ADR 接受时是 76.7 MB（2001 个改动路径，含被 stat 缓存留住的内容）；stat 缓存修正后 2.12 MB，第 4 步之后要求每个改动路径 ≤ 1 KB |
| 合计（本表的 MB 与 bench 相同，都是 2^20 字节） | 60 MB | |

- 关键约束：分配对应 ADR 0017 的采样状态，即首页加载完成、没有打开文件、Diff 或会话时。只因阅读和审阅才填充的缓存不在这个状态里，由各自的上限约束：`git` 的 hunk LRU 16 MiB、打开 Diff 时改动集保留的工作区内容 ≤ 32 MiB、`file_reader` 的 8 MB 高亮与文本 LRU、`agents` 的 8 MB 轮次索引 LRU、⌘K 关闭 30 秒后释放的名字表。
- 关键约束：项目主页统计「会话外的改动」的比较在采样状态里运行，它的改动集为了增量刷新会一直保留，所以只能是计数用的改动集：`Limits` 取 `retained_bytes = 0`、`total_patch_bytes = 0`（与 `code_intel` 的 `changed_paths` 相同），不保留工作区内容、不算 hunk，只有路径、两侧的 OID 与 stat。它随改动路径数增长，不随跟踪文件数增长，每个改动路径 ≤ 1 KB（`git/changes_count/per_path_bytes`，含 `Worktree` 的 stat 缓存）；4000 个以内 ≤ 4 MB，在余量里。改动路径超过 4000 个时（未跟踪文件最多 2 万个）只保留计数，不保留改动集，之后的事件触发全量比较（10 万文件约 1 s，在后台）。
- 关键约束：跨调用保留的比较缓存（stat 缓存，以及以后加入的任何缓存）不持有让文件内容保持分配的引用，包括 `Weak`：`Arc<[u8]>` 的计数和字节在同一次分配里，`Weak` 也让整块分配一直存活。需要内容时按路径重新读取。上面每个路径 ≤ 1 KB 的上限以此为前提。本 ADR 接受时的 stat 缓存违反这一条：2001 个 10–50 KB 的改动文件加一个 16 MiB 的文件，计数用的改动集连同 `Worktree` 是 76.7 MB（`git/changes_count/total_bytes`，只记录），其中 74.5 MiB 是被留住的内容。`git` 的修正已经完成（[git 设计「与设计的差异」](../design/git.md#与设计的差异)第 3 步），同一测量降到 2.12 MB（每个改动路径约 1.11 KB，其余是比较用的 index）。`git/changes_count/per_path_bytes` 要这一条和上文「比较用的 index 只在调用内持有」（`git` 第 4 步）都做到才能通过（只修 stat 缓存时实测约 1.11 KB），现在只差第 4 步，随第 4 步生效。
- 以后新增的、10 万文件时常驻的份额从余量里分配，在它的设计文档「性能」里写明占用的数字；余量不够时另写 ADR 重新分配。
- 首帧之前不做其中任何一项（ADR 0017）：index 的解析、过滤器的构造和工作区比较都在打开项目之后的后台任务里，读 index 的耗时计入 `project/open_100k/files`（< 80 ms）。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 10 万文件同样 < 100 MB | 增加的部分只有 40 MB；实测的 `project` 与 `git` 两项已有 26.6 MB，加上 `code_intel` 10 MB 和 `cache` 4 MB 就超过 40 MB。要做到，需要 `git` 的 `TrackedPaths` 与 `project` 的 `FileList` 共用一份路径和 OID（约省 7 MB），并把 `TrackedPaths` 改成连续存储，涉及 `git`、`services`、`project` 三个 crate 的数据结构，还没有实测收益；做完之后可以按实测降低本预算 |
| index 继续计入 `fs_watch` | `fs_watch` 不构造也不决定它的布局，大小随 `git` 的改动变化，`fs_watch` 自己改不了 |
| 比较用的 index 随 `Worktree` 常驻，记入 `git` 的份额 | 10 万文件时 39 MB，比 12 MB 的余量多出两倍以上；保留它只省下每次比较重新解析的时间，比较本来就在后台 |
| index 计入 `project` | 没有监听器时 `project` 每轮扫描打开新句柄、不保留；过滤器总是持有这份 index |
| 只设份额，不设 10 万文件的总预算 | 份额没有加总，10 万文件时的 13.9 MB 就是这样没有预算的 |

## 影响

- `bench`（[#7](https://github.com/SoloJiang/lectern-app/issues/7)）：预算表加入 `app/idle_100k`、`app/idle_100k_indexed`（`Tier::Top`，计划中，分别由 `project_home` 和 `code_intel` [#17](https://github.com/SoloJiang/lectern-app/issues/17) 改为生效）、`git/filter_cloudprint_bytes`、`git/filter_100k_bytes` 和 `git/compare_100k/peak_bytes`（生效）、`git/compare_100k/retained_bytes`（计划中，git 第 4 步）、`fs_watch/resident_100k`（计划中，fs_watch 第 4 步）；`fs_watch/resident` 的说明改为不含过滤器。10 万文件读 index 和刷新的耗时份额（`git/open_100k` 生效；`git/filter_100k`、`git/changes_clean_100k` 在 macOS CI 上超标，计划中，由定位并修正这项开销的 `git` PR 改为生效，另有只记录的 `git/filter_100k/walk`、`git/changes_clean_100k/stat_all`、`git/changes_clean_100k/read_all` 帮助定位）由 [git 设计「性能」](../design/git.md#性能)给出，同时加入。
- 计算改动统计的 `review`（[#15](https://github.com/SoloJiang/lectern-app/issues/15)），供 `project_home`（[#30](https://github.com/SoloJiang/lectern-app/issues/30)）显示：首页的计数比较按上面的 `Limits` 和 4000 个路径的上限，写进 `crates/review/AGENTS.md`，由 review 的设计文档展开；`bench` 加入只记录的 `git/changes_count/total_bytes` 和计划中的 `git/changes_count/per_path_bytes`。
- `git`：stat 缓存不持有文件内容，单独一个 PR，已完成；`git/changes_count/per_path_bytes` 随第 4 步生效，见 [git 设计「与设计的差异」](../design/git.md#与设计的差异)第 3 步。
- `git` 第 4 步：比较用的 index 只在调用内持有，接口说明、测试和验收写在 [git 设计](../design/git.md)「缓存」「验收」。
- `code_intel`：`code_intel/batch_peak` 的 ≤ 40 MB 不含 `git` 比较期间的临时内存，后者是 `git/compare_100k/peak_bytes`（见 code_intel 设计「性能」）。
- 同时修改的文档：[技术调研「性能预算」](../design/tech-research.md#性能预算)的空闲内存一行、[bench 设计「预算表」](../design/bench.md#预算表)、[git 设计「性能」](../design/git.md#性能)、[fs_watch 设计「性能」](../design/fs_watch.md#性能)、[project 设计「性能」](../design/project.md#性能)、[code_intel 设计「性能」](../design/code_intel.md#性能)，ADR 0030 的状态行。

## 已知限制

- 审阅之后的空闲内存可以比采样状态多出上面几个缓存的上限，不在本预算里。
- 份额都是进程内的存活字节，`app/idle_100k` 是 `phys_footprint`，多出分配器的开销和碎片；两者的差别由 `app` 的测量构建实测（bench 第 5 步）。
- 实测来自 Linux 容器，M 系列上由 macOS CI 判定。
