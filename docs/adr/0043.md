# ADR 0043：时间盒截断的轮次计为不合格的样本，判定仍按中位数

- 状态：已接受
- 日期：2026-10-21
- 修订：[ADR 0037](0037.md)（「影响」中「`references_full` 的夹具存着每个单元，每次都要 `Complete`」：满额模式下被时间盒截断的轮次不再是错误）

## 背景

`code_intel/references_full`（10 万文件、命名空间满额，查 300 个文件用到的函数的引用）判定 `/all` 中位数 ≤ 2 s、`/first` 中位数 ≤ 200 ms，并要求 12 轮（1 轮预热加 11 个样本）每一轮都是 `Complete`，任何一轮不完整整项报 `error`。

macOS CI 上它间歇失败，报错形状相同，都是 `unsearched` 为 0、`outside` 几千到几万：

- main 4fe40b9（运行 39625455292）：`Partial { unsearched: 0, outside: 33670 }`。同一次运行的 git 基准不慢；`references_full` 的墙钟 16.3 s，与通过的运行（11.8–18.2 s）相当，失败的是十几轮里的某一轮，不是第一轮。
- main 6932074（运行 39583529109）：`outside: 8916`。
- PR #144（只改文档，较慢的 runner）：`outside: 30080`。

满额模式下，查询在计为已入索引之前按批与存储核对提示，每条语句之前检查时间盒；查引用的时间盒是 1.9 s，到时没核对的范围外文件计入 `outside`（ADR 0037）。Linux 上的复现（4 核虚拟机，release，加临时计时）：

- 无负载：每轮 1.08–1.27 s，其中 `ci_ref` 一轮 0.85–1.02 s（解析 300 个文件），核算的遍历 0.23–0.31 s（52 301 个提示，108 条语句）；存储里 90 301 个单元都在，0 次淘汰，每轮 `Complete`。
- 4 个忙循环占满 4 核：前 10 轮 1.36–1.76 s，完整；第 11 轮的 `ci_ref` 一轮用了 1.60 s，1.917 s 结束，范围外的核对在时间盒截断，7 497 个提示没核对，结果 `Partial { unsearched: 0, outside: 7430 }`，单元齐全、0 次淘汰。与 CI 的报错相同。

排除的原因：夹具准备与后台索引的竞争会让第一轮就失败，而存储齐全、查询期间提示没有变化；夹具模板的缓存状态（ADR 0039）不改变存储内容；冷页缓存已由模板按字节复制避免，慢读也只是让核对变慢，同属时间盒。

所以产品按设计在时间盒交出 `Partial`。问题在判定：一轮约 0.7 s 的停顿就让整项报错，中位数和超标重跑一次（ADR 0036）都不起作用。

## 决策

- 预算的数值不变（`/all` ≤ 2 s、`/first` ≤ 200 ms，中位数），产品行为不变（时间盒 1.9 s，到时没核对的计入 `outside`）。
- 满额模式下，被时间盒截断的一轮是不合格的样本，不是错误：它的两个 ID 的样本都记为这一轮的耗时加一个时间盒（≥ 3.8 s）。截断的一轮在 1.9 s 加一条语句时结束，按自己的耗时计在 2 s 之内，反而会通过；完整的答案至少还要再查一次。
- `/first` 同样记为这个值，不用这一轮第一批的实际时间。两个 ID 来自同一轮，完整性是两者共同的前提；这样两者的通过条件相同：11 个样本里截断的不超过 5 轮时两者按实测判定，超过一半时两者都超标。
- 预热轮按同一规则：截断不报错，计入下面的记录项，不进样本。
- 「被时间盒截断」的依据：查询的公开结果说不出范围外的文件为什么没算入，只能用可得的证据，全部成立才算截断：`unsearched` 为 0、`outside` 大于 0、从查询到最后一批不短于时间盒、存储的单元数不少于夹具写入的（0 缺失）、0 次淘汰。缺一条或无法得知，仍是错误。
- 仍是错误的：`unsearched` 大于 0（范围内有文件没搜，答案可能真的少了引用，包括停顿长到截断 `ci_ref` 一轮本身）、证据不全的 `Partial`、没有 `Done`、没有第一批、引用少于 300 个。
- 新增只记录的 `code_intel/references_full/partial_rounds`（截断的轮数，含预热）和 `code_intel/references_full/outside`（一轮留在范围外的最多文件数）。有截断时，这两项和两条判定项都带说明（截断的轮数，最后一轮的 `outside`、耗时、时间盒、单元数、淘汰数），出现在 CI 的 `::notice` 和 `::error` 注释里。
- 中位数规则和超标重跑一次（ADR 0036）不变。

逐个看过判定里要求完整的其他基准，都不改：

- `goto_full`：`/done` 判定最大值 ≤ 1.02 s，本来就是「每一轮」。截断的一轮在 1 s 加一条语句内结束，按耗时计会通过；按本规则计费也是单轮超标，结果仍是不通过（只多一次 ADR 0036 的重试）。平常 `Done` 在 0.29–0.35 s，余量约 3 倍，截断说明有真正的退化。
- `references_100k`：命名空间没满时不核对存储，时间盒不会产生 `outside`；它被截断只能是 `ci_ref` 一轮读不完，表现为 `unsearched`，按上面的规则仍是错误。手动设置 `CODE_INTEL_BENCH_FULL` 记录满额数字时按本规则处理。
- `goto_indexed`、`goto_uncached`、`goto_popular`：完整性检查的是夹具（每个单元都存着），`Done` 只记录、在几十毫秒内，离 1 s 的时间盒很远；不完整只会是 `unsearched`，说明夹具或查询坏了。
- `named_50k`（只记录，`Partial` 照常记录）和 `search_stop`（要求 `Partial`）本来就不把 `Partial` 当错误。

放弃的方案：

- 截断的一轮按自己的耗时计入：在 2 s 之内，等于把 `Partial` 判为合格。
- 截断的一轮重跑或不计：把不完整藏起来，每轮都截断时也会通过。
- 放宽时间盒，或让范围外的核对越过时间盒：与 ADR 0030 的全部结果 ≤ 2 s 和 ADR 0037 的取消约束冲突。

## 影响

- `bench`：`lectern_bench::rounds`（判定与计费）、`Measured::note`（报告的 `note` 字段，notice 和 error 注释带上它）、budgets.rs 的两条记录项；写进 [bench 设计](../design/bench.md)「时间盒截断的轮次」「报告」「预算表」。
- `code_intel`：[设计](../design/code_intel.md)「性能」「验收」里 `references_full` 的判定写法；产品代码不变。
- CI：单次停顿不再让 macOS 基准任务失败；截断超过一半的轮次时中位数超标，重跑仍超标，CI 照常失败；截断的轮次从注释里直接看得到。
- 以后可以做的产品改动：范围外的核对与 `ci_ref` 一轮同时进行，拓宽余量；那是 code_intel 的设计变更，另行决定。

## 已知限制

- 「被时间盒截断」是由证据推断的：范围外有文件因为别的原因（如提示没有置位）没算入、恰好又到了时间盒的一轮，也会计为截断；这个夹具在准备之后不再写入，存储齐全，这种情况不会出现。
- 计费值是约定（耗时加一个时间盒），不是测得的完成时间；截断过半时中位数的数值只说明超标。
- 截断轮次第一批的实际时间不进样本。
