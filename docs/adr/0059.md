# ADR 0059：产品能力完成之前，`app/open_diff` 在 CI 上按 < 260 ms 判定

- 状态：已接受
- 日期：2026-10-31
- 修订：[ADR 0057](0057.md)（CI 上的判定值 120 ms）

## 背景

[ADR 0057](0057.md) 把 `app/open_diff` 在 CI 上的判定值定为中位数 < 120 ms。之后托管 runner 上最近 11 次其他运行的中位数是 83.1–120 ms，一次运行（[41211235428](https://github.com/SoloJiang/lectern-app/actions/runs/41211235428)）是 209 ms、183 ms。那次运行的 [#346](https://github.com/SoloJiang/lectern-app/pull/346) 只加了一个路由表，不在这条路径的耗时上，其他运行都在 120 ms 以内。判定值已经落在常见范围的上沿，所以这一项会反复挡住与它无关的 PR。

产品负责人的决定（2026-10-28，[ADR 0055](0055.md)）：产品能力完成之前，CI 上超标的预算按实测放宽，不再重跑和等待确认。

## 决策

- `app/open_diff`：CI 上的判定值从中位数 < 120 ms 改为 < 260 ms。有记录的最差中位数是 209 ms，留 25% 的余量。测量方式、夹具和启动次数不变。
- 技术调研表里的目标 < 50 ms 不变，ADR 0057 里产品能力完成之后的核对方式不变。

放弃的方案：

- 按常见范围定为 < 150 ms：那次 209 ms 的运行仍然失败，要靠重跑通过，与 ADR 0055 相反。
- 重跑一次：不解决问题，下一次噪声仍然挡住无关的 PR。

## 影响

- `lectern-bench` 的 `budgets.rs`：`app/open_diff` 的 `Limit::TimeBelow`。
- `docs/design/tech-research.md`、`docs/design/bench.md`、`docs/design/review_view.md` 写这个数的地方。

## 已知限制

- 常见值约 100 ms，所以 260 ms 挡不住翻倍以内的退化。`took_us` 仍在基准的备注里，可以比较。
- 209 ms 这次运行里，应用日志的 `took_us` 也升到 75–185 ms，所以这一次的时间在应用内，不只是 runner 的帧节奏。原因没有查明。
