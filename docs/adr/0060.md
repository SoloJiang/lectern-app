# ADR 0060：ACP 客户端自己实现 stdio 上的 JSON-RPC，不引入 `agent-client-protocol` crate

- 状态：已接受
- 日期：2026-11-01

## 背景

[技术调研「Agent 原生面板」](../design/tech-research.md#4-agent-原生面板第二阶段)的选型表把 ACP 客户端写成「`agent-client-protocol` crate」。[ADR 0050](0050.md) 和 [conversation 设计「对其他 crate 的要求」C](../design/conversation.md#对其他-crate-的要求) 规定了客户端的形状：

- 每个连接一个读 agent 输出的专用线程，不启动异步运行时（架构规则 3：单进程、无常驻运行时）；
- 一行至多 16 MiB，超过时关闭连接；
- 不认识的 `session/update` 种类跳过并计数，不报错；
- `initialize` 不声明 `fs`、`terminal`，`mcpServers` 为空，协商出的版本不是 1 时不使用这个 agent。

实现前核对了 crates.io 上的 `agent-client-protocol` 3.6.0：它的客户端连接建立在 `futures` 的异步任务之上，`stdio` 与 `process` 两个 feature 另外引入 `blocking`、`async-io`、`async-process`，用它就要在专用线程上再跑一个本地的 futures 执行器，并且它的 major 版本在快速变化（2026 年已到 3.x，部分会话方法在 `unstable_*` feature 之后）。Lectern 用到的消息只有六种：`initialize`、`session/resume`、`session/load`、`session/prompt`、`session/cancel`，以及 agent 发来的 `session/update` 与 `session/request_permission`。

## 决策

- **`agents` 自己实现 ACP 的 JSON-RPC 层**：按行读写 stdio，用 `serde` / `serde_json`（工作区已有）反序列化到只声明用到字段的结构，请求按 `id` 对应回复。不新增外部 crate，Cargo.lock 只因新增本仓库内的依赖边而变化。
- 线程模型、行长上限、跳过并计数不认识的消息、能力声明按 ADR 0050 和 conversation 设计 C，不因本决定改变。
- 协议版本固定为 ACP v1。以后升级协议时，在 `agents` 的设计文档里改消息结构；不需要追随第三方 crate 的 major 版本。

放弃的方案：

| 方案 | 原因 |
|---|---|
| 用 `agent-client-protocol` crate | 需要异步执行器，与「专用线程、无运行时」冲突；依赖树更大（`cargo-deny` 要逐个核对）；major 版本变化快 |
| 只用 `agent-client-protocol-schema`（只含类型） | 省去传输层，但类型是为完整协议生成的（要为协议的全部枚举跟随上游），而我们要跳过未知种类；用到的消息很少，自写的结构更小；仍然多一个外部依赖和它的 major 版本跟随 |

## 影响

- `agents`：设计文档新增「ACP 客户端」一节（[agents 设计](../design/agents.md#acp-客户端)），含对两个适配器的核对结果；消息结构放在 `crates/agents/src/acp/wire.rs`（第 7 步）。
- [技术调研](../design/tech-research.md)选型表里 ACP 一行改为指向本 ADR。
- 无新的外部依赖，`cargo deny` 的结果不变。

## 已知限制

- 协议的新方法与字段要自己跟进。缓解：只用上面六种消息；未知字段忽略，未知的 `session/update` 种类计数后跳过，所以适配器增加字段不会让连接失败。
- 没有协议一致性测试套件可用；一致性靠对两个适配器的核对和合成的消息样本（`crates/agents/tests/fixtures/acp/`，第 7 步）。
