# ADR 0061：为修复 SQLite 的安全公告升级到 SQLite 3.54，`usage/backfill_batch` 暂时放宽到 270 ms

- 状态：已接受
- 日期：2026-11-17
- 修订：[ADR 0027](0027.md)（rusqlite 的版本）

## 背景

[RUSTSEC-2026-0459](https://rustsec.org/advisories/RUSTSEC-2026-0459.html)（CVE-2026-119375）：3.54.0 之前的 SQLite 在打开页面大小不同的数据库与 `-wal` 文件时会返回未初始化的内存。`libsqlite3-sys` 0.38.2（`rusqlite` 0.40.2）内含的 SQLite 3.53.2 受影响，`cargo deny` 因此在所有分支上失败（`deny.toml`：漏洞一律失败）。修复的版本是 `libsqlite3-sys` ≥ 0.39，只能随 `rusqlite` ≥ 0.41 取得。

升级后 `usage` 的写入路径变慢。本机同一棵树、只改 rusqlite 的版本：`usage/backfill_batch` 的中位数从 89 ms（0.40.2）变为 148–155 ms（0.41.1）和 142 ms（0.43.0）；`usage/ingest_append_4k` 从 320 µs 变为约 400 µs。托管 runner 上 0.41.1 测得 209 ms、193 ms，超过 150 ms 的预算。CPU 采样显示原因在 SQLite 里：缓存的语句在 `sqlite3_step` 里过期并重新编译（`sqlite3Reprepare`），解析和查询规划约占 22% 的样本，3.53 上约 1%。唯一改变的编译选项 `SQLITE_ENABLE_MEMORY_MANAGEMENT` 不是原因。

[ADR 0055](0055.md) 的放宽规则不适用：这个 PR 改了被测的代码（SQLite 本身）。

## 决策

- `rusqlite` 锁定为 `=0.43.0`（`libsqlite3-sys` 0.40.0，SQLite 3.54.1）。选它而不是 0.41.1：同样修复了漏洞，本机略快（142 ms 对 148–155 ms）。`bundled`、`cache` 特性和精确锁定的方式不变（ADR 0027）。
- `usage/backfill_batch` 的预算从中位数 < 150 ms 暂时放宽到 < 270 ms：托管 runner 上有记录的最差值 209 ms，加约 30% 的余量。其余 `usage` 预算不变。
- [#386](https://github.com/SoloJiang/lectern-app/issues/386) 追查语句为什么过期，在 `usage` 里修复后改回 150 ms。

放弃的方案：

- 在 `deny.toml` 里忽略这条公告、留在 3.53：Lectern 只打开自己应用数据目录里的数据库，能改写它们的已是本机用户，不在威胁模型里；但以后的 rusqlite 都内含 3.54 或更新的 SQLite，回归只是推迟，而且会留一条被忽略的漏洞。
- 改用系统的 SQLite：放弃 ADR 0027 的静态链接和版本锁定，macOS 自带的版本由系统决定。

## 影响

- 根 `Cargo.toml`、`Cargo.lock`；`usage` 的一处调用（`Statement::column_names` 改为返回迭代器）。
- `lectern-bench` 的 `budgets.rs`；[usage 设计「性能」](../design/usage.md#性能)。
- ADR 0027 的状态行、升级记录和索引。
