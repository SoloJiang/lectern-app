# ADR 0020：token 用量按 MR 和项目两级统计

- 状态：已接受
- 日期：2026-10-16
- 修订：[ADR 0014](0014.md)（统计单位与界面位置）

## 背景

[ADR 0014](0014.md) 按会话和轮次统计 token。2026-10-16 人确认，比起每个会话花了多少，更关心两个数：每个 MR 花了多少（一个改动从开始到合并一共用了多少 token、折合多少费用），以及每个项目花了多少。

会话和 MR 不是一一对应的。一个 MR 通常由多个会话完成：第一次实现、审阅意见发回后的修改、并行 agent 各做一部分。一个会话也可能改到多个分支：agent 的工作目录是一个 worktree，却通过绝对路径修改另一个 worktree 里的文件。所以 MR 级别的统计不能简单地把会话加起来。

## 决策

**统计单位**

统计分两级：项目和 MR。会话和轮次保留为 MR 之下的明细，不再作为主要的汇总单位。

- 项目指 Lectern 里打开的一个项目（[ADR 0006](0006.md)、[ADR 0012](0012.md)）。git 仓库以仓库为准：项目按 git 公共目录的规范绝对路径识别，同一仓库的所有 worktree 属于同一个项目，即使在不同窗口里分别打开，用量也只计一次。每个项目有一个 Lectern 分配的固定标识，路径只是它的位置，每条观察记下当时的项目标识。同一个路径之后可能被另一个仓库占用（原仓库删除或移走后，在原处新建或克隆了无关的仓库）：每次打开一个已知路径、或经别名指向已知项目的路径时，都重新比对根提交 OID。根提交不一致不一定是另一个仓库：`git filter-repo`、`git rebase --root` 改写全部历史后根提交也会变。所以判断是不是同一个仓库时比对完整的标识，根提交一致也要比对：两边都有代码平台仓库 ID 时以它为准，相同就是同一个项目（根提交不一致说明改写了历史，记下新的根提交），不同就不是（如在原路径放了一个 fork 或另一个同源的克隆）；没有仓库 ID 时，根提交一致、且远端地址集合有交集（或两边都没有远端）才是同一个项目，根提交不一致时要求非空的远端地址集合有交集（添加或删除远端是日常操作，不要求完全相同）；对不上时才算路径被另一个仓库占用，给这个路径分配一个新项目，之后的观察记到新项目，原项目和以前的记录不变，经这个路径的别名也不再指向原项目；已知项目有根提交 OID、而这个路径上的仓库还没有提交时，先给它一个临时项目，不记到已知项目名下；出现第一个提交后比对：根提交 OID 与已知项目一致，临时项目记为它的别名，之前的用量随之并入，不一致则临时项目转为新项目。已知项目自己也一直没有提交（没有根提交 OID 可比）时，按路径视为同一个项目。仓库目录被移动或改名后路径会变：打开一个没见过的 git 公共目录时，Lectern 用它的根提交 OID 和远端地址集合（规范化后的 URL；`forge` 可用时再加代码平台仓库 ID）与原路径已不存在的已知项目比对。全部一致、远端地址集合非空（或有代码平台仓库 ID）、而且只有一个候选时，才记下「旧路径 → 新路径」的别名，以前的用量随之归入新路径；fork 的远端不同，不会被当成移动。没有远端也没有代码平台仓库 ID 的仓库（如从同一份历史复制出的本地仓库）缺少能区分副本的标识，有多个候选或只有根提交一致时同样不自动合并，旧项目在所有项目的列表里保留为「路径已不存在」，用户可以在 Usage 页手动合并（入口见[交互规范](../design/interaction.md)的 Usage 屏幕）：合并记下与自动识别相同的别名，可以撤销。不是 git 仓库的普通文件夹以打开的根目录为准，同样是项目，它的用量全部计入项目合计，只是没有分支和 MR 这一级。项目的用量是归属到这个项目的全部用量：它的所有 MR、未开 MR 的分支、「不属于任何 MR」的部分，以及 Lectern 自己发起的分析。有改动的轮次按改动所在的项目归属，改动跨了几个项目时按改动权重（见「归属规则」）分摊到这些项目，不看 cwd；没有改动的轮次跟随同一会话里最近的有改动轮次，项目和分支一起跟随（见「归属规则」），会话里没有任何改动时才按 cwd 所在的项目归属。会话的 cwd 和改动都不在任何已打开项目里时，暂时归入「其他」；之后打开了包含它们的项目，这些用量自动归入该项目。已打开的项目互相包含时（一个普通文件夹里有另一个已打开的文件夹或仓库），每条记录只归一个项目：取包含它的最内层项目，git 仓库优先于包含它的普通文件夹。
- 项目级别按时间窗口统计（7 天 / 14 天 / 30 天），可以按 MR、按 agent、按模型拆分；按 MR 拆分时，每行是这个 MR 在所选时间窗口内的用量；同一次使用（同一个分支）上统计区间重叠的几个 MR 合为一行（同一分支上先后开出、区间不重叠的 MR 各占一行；不同分支上的 MR 即使时间重叠也各占一行，它们的用量本来就不相交），列出这些 MR；「不属于任何 MR」单独一行；各行相加等于项目合计。时间窗口按每条用量记录自己的时间（agent 回复的时间戳）划分，不按会话开始或导入的时间；「最近 7 天」指用户本地时区的今天和之前 6 个自然日，14 天、30 天同理。MR 级别（worktree 列表、简报、MR 视图）显示这个 MR 从开始到合并的累计值，两者在界面上分别标明。
- MR 指一个分支上准备合并的一组改动。已经在 GitHub 或 GitLab 上开了 PR / MR 的，以代码平台上的那个 MR 为准；还没有开的，按分支显示为「未开 MR」，开了之后自动关联。
- 默认分支上的直接改动、detached HEAD、无法确定分支的用量，归入「不属于任何 MR」。默认分支本身是某个 MR 的源分支时（例如 fork 的默认分支向上游仓库开 MR），以 `forge` 报告的 MR 为准，只有 `forge` 没有对应 MR 时才按这一条处理。

**归属规则**

- 有改动的轮次按改动归属：这一轮改了哪些文件，就归到这些文件所在 worktree 当时的分支。一轮改了多个分支时，按权重分摊这一轮的 token，每个分支的权重是改动行数加上改动文件数，所以只换了二进制文件、只改了文件模式或只重命名的分支也分到用量。分摊结果按分数保存（整数 token 数和整数权重，不预先取整），汇总时精确相加；显示整数时按最大余数法分配余数（余数相同时按分支标识排序），所以各行相加始终等于合计。改动来自 `review` 对轮次的归因结果。
- 没有改动的轮次（阅读、讨论、跑测试、回答问题）跟随同一会话里最近的有改动轮次：先找它之前最近的一个，没有再找之后最近的一个，按那一轮的分支和权重归属。例外是跟踪中的会话里、这一轮自己有确定的观察（不是「不确定」）显示 cwd 所在 worktree 换了分支：那一轮最近的有改动轮次改的是同一个 worktree，而这一轮观察到的分支与那时不同（会话中途切到了别的分支跑测试、读代码），这一轮按自己观察到的分支归属，不跟随；最近的有改动轮次改的是别的 worktree（通过绝对路径改另一个 worktree）时仍然跟随，因为 cwd 的分支说明不了这一轮在为哪个分支工作。会话里没有任何改动时，按每一轮自己的分支：Lectern 正在跟踪的会话，每一轮结束时（以及每个可能切换分支的工具调用之后）记下 cwd 所在 worktree 的分支和 HEAD，与有改动的观察一起保存，所以 Codex 会话中途切到功能分支后只读代码、跑测试，也归到功能分支；一轮里观察到不止一个分支时（包括一次调用期间 HEAD 停留过的分支：调用开始时检出的分支，以及 HEAD reflog 里确定落在调用开始与工具结果之间的每次切换的目标分支，先后无法确定的切换不计入），这一轮的 token 在这些分支间平均分摊，所以 `git switch B && cargo test && git switch A` 这样回到原分支的命令，B 也分到一份；导入的旧会话没有这些观察，用日志里记录的分支（Claude Code 每条记录带 `gitBranch`，Codex 只有会话开头 `session_meta` 里的 `git.branch`）；记录的是默认分支（且 `forge` 没有对应 MR）或没有记录时，归入「不属于任何 MR」。
- 子 agent 会话先按它自己的改动和以上规则归属，再把用量计入父会话的合计（ADR 0014）。子 agent 里没有改动的轮次先在子 agent 自己的会话里按最近的有改动轮次归属；只有子 agent 整个会话都没有改动时，才跟随启动它的那一轮父会话轮次。所以几个子 agent 分别改不同分支时，各自的用量落在各自的分支上。父会话里只负责派出子 agent、自己没有改动的轮次，按它派出的子 agent 的改动权重分摊到这些分支上，不按父会话记录的分支归属。父轮次和它派出的所有子 agent 都没有改动时，整棵子树按普通的没有改动的轮次处理（跟随父会话里最近的有改动轮次；会话里没有改动时用上一条的规则：跟踪中的会话按每一轮观察到的分支，导入的旧会话才用日志记录的分支）。
- 分支按「一次使用」区分，不只看分支名：一次使用从 Lectern 第一次观察到这个分支开始。观察里写进去的是一个固定的片段标识：每遇到一个可能的边界（删除后重建、`reset` 类丢弃）就开始一个新片段，并记下边界事件的时间和种类；哪些片段属于同一次使用在汇总时按下面的规则计算，不在写观察时决定。所以 P1、P2 或离线期间发生的边界，在 `forge` 之后拿到 MR 的状态时间线、证明边界发生时这个分支开着 MR 时，前后片段在汇总时合并为同一次使用，以前的用量随之并入这个 MR。分支改名（`git branch -m`）不是新的一次使用：Lectern 从分支 reflog 里的 `Branch: renamed refs/heads/A to refs/heads/B` 记录（或旧名消失、新名带着同一份 reflog 出现）识别改名，记下改名关系，标识沿用，所以改名前的用量随分支并入之后开出的 MR。以下两种情况算新的一次使用，之前那次的用量不并入新的：没有开着的 MR 时，分支被删除后重新创建（reflog 里有新的创建记录，或两次观察之间分支不存在）；没有开着的 MR 时，分支被重置、丢弃了上一次观察到的分支独有的提交。是否连续只看分支 reflog 里让分支移动的那条记录的动作，不比较提交内容：`rebase`（包括交互式 rebase 里删除、合并提交）、`commit`（含 `--amend`）、`merge`、`cherry-pick`、`pull` 都算同一次使用里的日常更新；`reset`、`branch -f`、`checkout -B` / `switch -C` 把分支移到一个不包含上一次观察到的分支独有提交的位置时，才算丢弃。还没有提交、只有未提交改动的分支，被观察到回到起点（没有分支独有的提交）而且工作区没有改动时（如 `git reset --hard`、`git restore` 丢弃了全部改动），这次使用结束，之后的改动算新的一次使用。用 `git stash` 暂存改动不算丢弃：这时 `refs/stash` 的 reflog 会新增一条来自这个分支的记录（`WIP on <分支>` 或 `On <分支>`），这次使用只是挂起；之后 `stash pop` / `apply` 恢复了改动就接着算；这条 stash 被删掉（`drop`、`clear`）而改动没有恢复、分支仍在起点且工作区干净时，这次使用才结束。`forge` 仍把这个分支对应到一个开着的 MR 时，本地删除重建也留在同一次使用里。所以合并默认分支、rebase（无论是否删改了提交）、强制推送这类日常更新都留在同一次使用里；分支开着 MR 时，`reset` 也留在同一次使用里。
- MR 的统计区间：在同一次使用之内，从上一个 MR 最终合并或关闭之后（没有上一个就从这次使用开始），到这个 MR 最终合并或关闭为止。这个 MR 的起点是它开出之前、同一次使用里最近的一次合并或关闭事件的时刻（没有就从这次使用开始），按事件时间线确定，之后的状态变化不改变它：A 先开、B 后开、A 先关时，A 的关闭在 B 开出之后，不是 B 的起点，A、B 同时开着的那段在两者的区间里都有；A 关闭、B 开出、A 之后又重新打开时，B 的起点仍是 A 那次关闭，A 自己的区间随重新打开延长到它最终关闭，A 只在关闭之前的工作不计入 B。MR 关闭后又重新打开时，以最后一次合并或关闭为准：关闭期间分支上的工作与开 MR 之前的工作同样对待，重新打开后并入这个 MR；一直没有重新打开时，关闭之后的用量留在分支上，显示为未开 MR 的分支。MR 的状态变化（打开、关闭、重新打开、合并及其时间）由 `forge` 提供，汇总时按最新状态重新计算。开 MR 之前在分支上的工作也计入，未开 MR 的分支在 MR 开出后整体并入；被放弃的分支（删除后没有开 MR）的用量留在它自己那次使用里，显示为未开 MR 的分支，不并入之后同名的 MR。同一次使用同时开着多个 MR（如向不同的目标分支各开一个）时，用量只计一次。每个 MR 的详情（worktree 列表、简报、MR 视图）显示它自己区间内的用量：几个 MR 同时开着的那段时间的用量在每个 MR 里都出现，并注明与哪些 MR 共用；其中一个合并或关闭后，之后的用量只计入还开着的 MR。Usage 页只把同一次使用里统计区间互相重叠的 MR 合为一行（不同分支、不同次使用的 MR 不合并；区间重叠具有传递性：A 与 B 重叠、B 与 C 重叠时三者合为一行），同一次使用里先后开出、区间不重叠的 MR（一个合并或关闭之后才开出下一个）各占一行；合并的这一行只包含这些 MR 统计区间内的用量（加上明确指向这些 MR 的「审阅」），且在时间窗口内；同一次使用里落在所有 MR 区间之外的用量（如最后一个 MR 关闭后、没有重新打开时的工作）单独一行，显示为未开 MR 的分支，项目合计不重复计算。
- Lectern 自己发起的模型调用（如会话简报的分析）归到被分析的改动所属的 MR，标为「审阅」，与 agent 写代码的「编写」分开显示。从 MR 视图发起的调用带着那个 MR 的标识，直接记到它名下；从会话简报发起、只知道分支的调用，分支同时有几个开着的 MR 时，按共用分支的规则处理（用量只计一次，每个 MR 的详情里注明共用，Usage 页合为一行）。「审阅」不受 MR 统计区间限制：MR 合并或关闭之后再分析它，用量仍计入这个 MR 的累计值；项目合计照常按调用的时间落在时间窗口里。一次分析覆盖多个分支（如简报分析了改动多个分支的整个会话）时，按被分析的改动在各分支的权重（改动行数加改动文件数）分摊。被分析的会话没有任何改动时，按这个会话没有改动时的规则归属（跟踪中的会话按每一轮观察到的分支，被分析的轮次落在几个分支上时，按这些轮次在各分支的 token 数分摊；导入的旧会话用日志记录的分支；默认分支则归入「不属于任何 MR」）。
- 观察结果在一轮结束后记录：一轮在下一条用户输入出现、或会话结束时视为结束，结束之前读到的部分只作为临时结果，随着日志追加继续更新。每个产生改动的工具调用执行之后，Lectern 记下该 worktree 在工具结果时间戳那一刻的分支和 HEAD：不直接读当前状态（日志读到时 agent 可能已经开始下一条命令），而是按这个 worktree 的 HEAD reflog 还原那个时间点的分支和 HEAD。reflog 的时间只精确到秒，所以 Lectern 用文件监听记下每一条 reflog 新增的时刻（亚秒精度）和它的序号。这个监听直接监视 git 公共目录里的 `logs/HEAD`、`logs/refs/heads/`、`logs/refs/stash` 和 `worktrees/*/logs/HEAD`，不经过按 git index 过滤的工作区监听（reflog 不是受跟踪的文件，linked worktree 的 reflog 也不在它的工作区目录下）。文件监听的通知是异步的，可能延迟或合并，所以「监听时刻早于工具结果」只能证明这条记录在结果之前；判断一条 reflog 记录与某个工具结果的先后，只用两条确定的规则：监听时刻早于结果时间戳的，在结果之前；git 自己记下的时间（秒）晚于结果所在那一秒的，在结果之后。两条都不适用时，这一次调用的分支标为「不确定」；有改动的按内容的去向归属（之后的提交在哪个分支的 reflog 里、或未提交的改动留在哪个分支上），没有改动的调用按普通的没有改动的轮次处理（跟随同一会话里最近的有改动轮次），不按猜测的分支归属，所以 `git switch feature && 改文件` 这样的命令记到的是执行后的分支。一次调用里分支切换了不止一次（如 `git switch B && 改文件 && git commit && git switch A`）时，Lectern 同时读取这次调用期间各分支 reflog 新增的条目：调用期间新增的提交归到 reflog 里记下它们的那个分支，调用结束时仍未提交的改动归到调用结束时检出的分支（切换分支时未提交的改动随工作区一起带过去）；一轮里切换了分支、改了几个分支时各自记录；每条观察同时记下仓库的稳定标识（git 公共目录的规范绝对路径，以及 `forge` 可用时代码平台给仓库的不变 ID，如 GitHub 的 repository id、GitLab 的 project id，仓库改名或转移后不变；owner/name 只用于显示），所以 worktree 删除、分支删除之后，重建仍能把这些记录对应到项目和 MR。一轮结束时，这些观察连同会话的 cwd、改动文件的路径、每个改动的改动行数，按「文件 × 分支观察」记录（同一个文件在一轮里先后在两个分支上改动时分开记，分支和项目的权重都由它算出，普通文件夹没有分支也能按项目分摊），以及各分支当时是否为默认分支，写入 Lectern 的 SQLite，之后不再修改（默认分支改名后，旧的记录仍按当时的分类处理），汇总和重建都以这份记录为准。项目和 MR 的归属在汇总时由这份记录计算，所以之后打开的项目、之后开出的 MR 都能拿到以前的用量。导入较早的会话时，如果改动所在的 worktree 已经删除或换了分支、无法确定当时的分支，这些轮次归入「不属于任何 MR」，并标为「无法归属」。

**分阶段**

- P1、P2：按项目和分支汇总，界面上（包括 P2 的 Usage 页）标为「分支用量」，不称为 MR。`forge` 就绪后（P3）关联到代码平台上的 MR，显示 MR 编号和标题，统计区间按上面的规则切分。
- 离线或代码平台不可用时，按分支显示，不影响统计。

**界面位置**（取代 ADR 0014 的「界面位置」表）

| 位置 | 内容 | 阶段 |

## 影响

- `agents`：除了原始用量记录，按顺序交出每个可能产生改动或切换分支的工具调用（写文件的工具和所有执行命令的工具）的开始与结果事件（调用开始的时间戳、结果的时间戳、所在会话与轮次、目标路径，执行命令的工具另带命令文本），`usage` 用同样两条确定的规则判断 reflog 记录是否在调用开始之后、结果之前，所以命令开始之前的外部切换不会算进这次调用停留过的分支。命令可能进入别的 worktree（`cd ../other && git switch B && cargo test`）：`usage` 从命令文本里取出 `cd`、`pushd` 的目标和 `git -C` 的参数，相对路径从调用的工作目录解析，落在已知 worktree 里的，把那些 worktree 的 HEAD reflog 一并按同样的规则读取，这次调用停留过的分支也包括它们；用变量、子 shell、脚本间接进入的 worktree 解析不出来，这部分按普通的没有改动的轮次处理（跟随最近的有改动轮次），不猜测；`usage` 据此按每个结果的时间戳从 HEAD reflog 还原当时的分支和 HEAD，没有改动的轮次中途切换过分支也能还原。
- `fs_watch` 与 `platform`：除了按 git index 过滤的工作区监听，再提供一个不过滤的 git 元数据监听，监视公共目录里的 reflog（`logs/HEAD`、`logs/refs/heads/`、`worktrees/*/logs/HEAD`），给每条新增记录打上亚秒时刻和序号。
- `agents`：Lectern 自己发起的分析（ADR 0019 的会话简报与 MR 分析）由凭据转发端点计量，每个请求转发之前就交给 `usage` 落盘一条计量记录（状态为「已准备」，输入 token 用转发前算出的值，输出为 0），请求体完整写入上游连接之后改为「已转发」；流式响应经过端点时边转发边估算输出 token（按已转发的文本），至少每秒或每 4 KB 把估算值写回记录一次，响应里的最终用量到达时用真实值替换，分析结束时标明完成、取消或失败；Lectern 异常退出后再启动时，「已转发」的记录按已知的值结算并标为「估算」，「已准备」的记录（请求还没发出）直接作废、不计费，所以模型服务已经消耗、但 Lectern 没等到结束的调用计入，没发出的请求不计入。写完请求体到改为「已转发」之间崩溃的极短窗口会漏计一次请求，这一侧的误差比多计更可接受。记录的内容：时间戳、agent 与模型、按 ADR 0014 的类别分开的 token（输入、输出、缓存读取、缓存写入，服务商报告的缓存字段原样保存，费用按各自的单价计算；端点估算的标为「估算」）、是否为重试，以及发起时的上下文（项目标识、MR 标识或分支、被分析的会话与轮次）。日志里没有这些调用，`usage` 只从这条记录得到「审阅」的用量。
- `usage`：在去重和聚合之外增加归属：输入是每轮的用量、Lectern 分析的计量记录、`review` 给出的每轮改动、`project` 给出的 worktree 与分支，以及 `forge` 给出的 MR 列表（可选）；读到日志时把每轮的 worktree、分支和 HEAD 一并保存；输出按项目和 MR 两级汇总的快照，会话和轮次作为明细。
- `project_home`：侧栏底部的 Usage 入口显示本项目合计，会话卡片不再显示 token。
- `worktrees`、`review_view`、`usage_view`：按上表调整显示位置。
- `forge`（P3）：提供分支与 MR 的对应关系，以及每个 MR 的状态变化（打开、关闭、重新打开、合并）和时间。
- 交互规范「用量」、路线图、README 同步修改。
