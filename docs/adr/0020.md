# ADR 0020：token 用量按 MR 和项目两级统计

- 状态：已接受
- 日期：2026-10-16
- 修订：[ADR 0014](0014.md)（统计单位与界面位置）

## 背景

[ADR 0014](0014.md) 按会话和轮次统计 token。2026-10-16 人确认，比起每个会话花了多少，更关心两个数：每个 MR 花了多少（一个改动从开始到合并一共用了多少 token、折合多少费用），以及每个项目花了多少。

会话和 MR 不是一一对应的。一个 MR 通常由多个会话完成：第一次实现、审阅意见发回后的修改、并行 agent 各做一部分。一个会话也可能改到多个分支：agent 的工作目录是一个 worktree，却通过绝对路径修改另一个 worktree 里的文件。所以 MR 级别的统计不能简单地把会话加起来。

## 决策

**统计单位**

统计分两级：项目和 MR。会话和轮次保留为 MR 之下的明细，不再作为主要的汇总单位。

- 项目指 Lectern 里打开的一个项目（[ADR 0006](0006.md)、[ADR 0012](0012.md)）。git 仓库以仓库为准：项目按 git 公共目录的规范绝对路径识别，同一仓库的所有 worktree 属于同一个项目，即使在不同窗口里分别打开，用量也只计一次。每个项目有一个 Lectern 分配的固定标识，路径只是它的位置，每条观察记下当时的项目标识。同一个路径之后可能被另一个仓库占用（原仓库删除或移走后，在原处新建或克隆了无关的仓库）：每次打开一个已知路径、或经别名指向已知项目的路径时，都重新比对根提交 OID。根提交不一致不一定是另一个仓库：`git filter-repo`、`git rebase --root` 改写全部历史后根提交也会变。所以判断是不是同一个仓库时比对完整的标识，根提交一致也要比对：两边都有代码平台仓库 ID 时以它为准（仓库 ID 只在同一个代码平台主机上唯一，所以比较的是「平台主机 + 仓库 ID」，本 ADR 里的代码平台仓库 ID 都指这个组合），相同就是同一个项目（根提交不一致说明改写了历史，记下新的根提交），不同就不是（如在原路径放了一个 fork 或另一个同源的克隆）；已知项目记有仓库 ID、而这次取不到（`forge` 离线、没有凭据、接口出错）时，ID 按未知处理，不当作不同，也不改用主远端得出「不是同一个项目」的结论：无论根提交是否一致，都像还没有提交的仓库那样先给一个临时项目（原路径上可能已经换成共享同一个根提交的 fork），等取到 ID 后再按完整标识比对，并入或转为新项目。两边都确实没有仓库 ID 时比对主远端：默认分支的上游所在的远端（通常是 `origin`；没有上游时取 `origin`；也没有 `origin` 时，只有一个远端就取它，有多个远端时改为比较完整的远端集合是否相同）的规范化地址。主远端在第一次识别这个项目时选定，记下远端名和规范化地址，之后比对沿用记下的那个远端：它还在就比较它的地址，后来新增的其他远端不影响（只有一个 `upstream` 时选了它，之后加了备份远端，仍然比较 `upstream`）；它被删掉或改名时才按上面的顺序重新选，根提交一致、主远端地址相同（或两边都没有远端）才是同一个项目，根提交不一致时要求两边都有主远端且地址相同；两边都没有远端也没有仓库 ID、根提交变了时（本地仓库做了 `git filter-repo`、`rebase --root`），无法区分改写历史和换了一个仓库，先给临时项目，在 Usage 页提示用户确认是同一个项目（合并）还是新项目，确认之前按临时项目统计，不直接分成新项目；只比集合是否有交集不够，fork 常常把原仓库加成 `upstream`，两边的集合会有交集；添加或删除其他远端不影响判断；同一路径上、没有仓库 ID、根提交不变而只有记下的主远端地址变了（仓库改名或转移后更新了远端地址，也可能是原处换成了共享根提交的 fork）时，同样无法确定，先给临时项目并请用户确认，不直接分成新项目；对不上时才算路径被另一个仓库占用，给这个路径分配一个新项目，之后的观察记到新项目，原项目和以前的记录不变，经这个路径的别名也不再指向原项目；已知项目有根提交 OID、而这个路径上的仓库还没有提交时，先给它一个临时项目，不记到已知项目名下；出现第一个提交后按上面同一套完整标识比对，不只看根提交：根提交一致、仓库 ID 或主远端也一致，或者根提交不一致但两边的仓库 ID 相同（没有仓库 ID 时两边都有主远端且地址相同，视为改写了历史），临时项目记为已知项目的别名，之前的用量随之并入；对不上则临时项目转为新项目。已知项目自己也一直没有提交（没有根提交 OID 可比）时，按路径视为同一个项目。仓库目录被移动或改名后路径会变：打开一个没见过的 git 公共目录时，Lectern 用它的根提交 OID 和远端地址集合（规范化后的 URL；`forge` 可用时再加代码平台仓库 ID）与原路径已不存在的已知项目比对。全部一致、远端地址集合非空（或有代码平台仓库 ID）、而且只有一个候选时，才记下「旧路径 → 新路径」的别名；两边都有代码平台仓库 ID 时以它为准，ID 相同、且只有一个候选时，根提交和远端不一致（仓库移动之前或之后改写过历史、改过远端）也记下别名，以前的用量随之归入新路径；fork 的远端不同，不会被当成移动。没有远端也没有代码平台仓库 ID 的仓库（如从同一份历史复制出的本地仓库）缺少能区分副本的标识，有多个候选或只有根提交一致时同样不自动合并，旧项目在所有项目的列表里保留为「路径已不存在」，用户可以在 Usage 页手动合并（入口见[交互规范](../design/interaction.md)的 Usage 屏幕）：合并记下与自动识别相同的别名，可以撤销。不是 git 仓库的普通文件夹以打开的根目录为准，同样是项目，它的用量全部计入项目合计，只是没有分支和 MR 这一级。项目的用量是归属到这个项目的全部用量：它的所有 MR、未开 MR 的分支、「不属于任何 MR」的部分，以及 Lectern 自己发起的分析。有改动的轮次按改动所在的项目归属，改动跨了几个项目时按改动权重（见「归属规则」）分摊到这些项目，不看 cwd；没有改动的轮次跟随同一会话里最近的有改动轮次，项目和分支一起跟随（见「归属规则」），会话里没有任何改动时才按 cwd 所在的项目归属。会话的 cwd 和改动都不在任何已打开项目里时，暂时归入「其他」；之后打开了包含它们的项目，这些用量自动归入该项目。已打开的项目互相包含时（一个普通文件夹里有另一个已打开的文件夹或仓库），每条记录只归一个项目：取包含它的最内层项目，git 仓库优先于包含它的普通文件夹。
- 项目级别按时间窗口统计（7 天 / 14 天 / 30 天），可以按 MR、按 agent、按模型拆分；按 MR 拆分时，每行是这个 MR 在所选时间窗口内的用量；同一次使用（同一个分支）上统计区间重叠的几个 MR 合为一行（同一分支上先后开出、区间不重叠的 MR 各占一行；不同分支上的 MR 即使时间重叠也各占一行，它们的用量本来就不相交），列出这些 MR；「不属于任何 MR」单独一行；各行相加等于项目合计。时间窗口按每条用量记录自己的时间（agent 回复的时间戳）划分，不按会话开始或导入的时间；「最近 7 天」指用户本地时区的今天和之前 6 个自然日，14 天、30 天同理。MR 级别（worktree 列表、简报、MR 视图）显示这个 MR 从开始到合并的累计值，两者在界面上分别标明。
- MR 指一个分支上准备合并的一组改动。已经在 GitHub 或 GitLab 上开了 PR / MR 的，以代码平台上的那个 MR 为准；还没有开的，按分支显示为「未开 MR」，开了之后自动关联。本地分支和 MR 的对应不只比较分支名，因为推送时本地名和远端名可以不同（`git push origin feature:users/alice/feature`）：按本地分支配置的上游和推送目标（`branch.<名字>.remote` / `merge`、`pushRemote`、`remote.pushDefault`，以及推送时观察到的 `<源>:<目标>`）解析出远端仓库的标识和远端分支名，与 MR 的源仓库、源分支比较；都没有配置时按 git 的默认推送规则，取主远端上的同名分支（`git push origin feature` 推到的就是它），与 MR 的源分支比较；本地分支的提交恰好是某个开着的 MR 的 head、且只有一个 MR 符合，也算对应。
- 默认分支上的直接改动、detached HEAD、无法确定分支的用量，归入「不属于任何 MR」。例外是这些工作随后被带进一个新分支：agent 先在默认分支或 detached HEAD 上改，再 `git switch -c feature`（或 `checkout -b`、`branch` 后切换）把未提交的改动或 detached 上的提交带过去；切到一个已经存在的分支（`git switch feature`）时，git 会把不冲突的未提交改动一起带过去，同样按下面的规则转移。Lectern 不看新分支从哪个提交开始（`git switch -c feature old` 的 reflog 是 `branch: Created from old`），而看这个 worktree 的切换：HEAD reflog 里的 `checkout: moving from <原分支或提交> to feature` 加上切换前后观察到的工作区改动，未提交的改动在切换后仍在工作区里，就说明被带进了新分支；新分支从当时的 HEAD 创建时（`Created from HEAD`），detached 上的提交也随之带过去。据此记下「片段 → 新分支」的来源关系；汇总时，原片段里改动在创建时仍未提交（随工作区带到新分支）的轮次，以及改出了新分支包含、默认分支不包含的提交的轮次，归到新分支，随它开出的 MR 计入；已经提交在默认分支上的改动仍归入「不属于任何 MR」。`git worktree add -b <分支> <路径> <起点>` 直接在新的 worktree 里创建分支，原来的 worktree 没有 `checkout` 记录：`agents` 交来的命令里有这条命令时，按命令执行前解析出起点提交，新分支的创建记录（`branch: Created from …`）与它一致、而起点是 detached HEAD 上的提交时，这些 detached 提交随之归到新分支，与 `switch -c` 的规则相同。用 `git cherry-pick -n`（`--no-commit`）只应用改动、之后再普通地提交时，目标分支的 reflog 里没有 `cherry-pick` 记录：`agents` 交来的命令里有这条命令时，按命令解析出原提交，把它的改动记为这个 worktree 上未提交改动的来源，这些改动之后提交到哪个分支，就按下面同样的条件转移。提交被 cherry-pick 到新分支时同样转移：目标分支的 reflog 里有 `cherry-pick` 记录时，先看 `agents` 交来的命令里有没有在这个 worktree 上执行的 `git cherry-pick`，有就按命令执行前的仓库状态把它的全部参数展开成原提交（一条命令可以有多个提交和区间，如 `A B`、`A..C`），每个原提交分别记来源；`-n` 把几个原提交合成一个普通提交时，这些原提交的轮次都随这个提交转移；没有命令（用户在终端里操作）时，按 `git patch-id --stable` 在原片段的提交里找改动相同的原提交（cherry-pick 生成新的提交 OID，不能按 OID 找；`--stable` 忽略空白，重复的等价改动也会同号），候选恰好一个才算找到；找到、而且原提交归在「不属于任何 MR」时，改出它的轮次转到目标分支；原提交已经在某个 MR 的分支上时不转移，同一份工作不计两次。所以常见的修正流程（误提交到默认分支，从旧提交建分支、把那个提交 cherry-pick 过去，再 reset 默认分支）也能把用量带进新分支的 MR。detached HEAD 上的提交被直接推到某个 MR 的源分支时也转移：`agents` 交来的命令里有 `git push <远端> <源>:<目标分支>`（源可以是 `HEAD` 或提交 OID，按命令执行前解析），而且推送确实成功：对应的远端跟踪分支（`refs/remotes/<远端>/<目标分支>`）在这次调用期间更新到了这个提交（推送被拒绝时 git 不更新它），或之后 `forge` 报告这个 MR 的 head 就是它，或之后 `forge` 报告的某个 MR 的 head 包含这些提交（head 就是它们或以它们为祖先）、而这个 MR 的目标分支在合并之前不包含它们（用 `forge` 提供的历史 base 提交判断：代码平台记录的 base OID，已合并的 MR 取合并前目标分支的提交，不用目标分支当前的位置，否则离线期间正常合并的 MR 会因为合并本身而包含这些提交）（已经直接推到默认分支的提交，之后从默认分支开出的 MR 的 head 也会包含，不能算经这个 MR 交付），而且只有一个 MR 符合时，改出这些提交的轮次转到这个 MR；符合的不止一个时不转移。默认分支本身是某个 MR 的源分支时（例如 fork 的默认分支向上游仓库开 MR），以 `forge` 报告的 MR 为准，只有 `forge` 没有对应 MR 时才按这一条处理。

**归属规则**

- 有改动的轮次按改动归属：这一轮改了哪些文件，就归到这些文件所在 worktree 当时的分支。一轮改了多个分支时，按权重分摊这一轮的 token，每个分支的权重是改动行数加上改动文件数，所以只换了二进制文件、只改了文件模式或只重命名的分支也分到用量。分摊结果按分数保存（整数 token 数和整数权重，不预先取整），汇总时精确相加；显示整数时按最大余数法分配余数（余数相同时按分支标识排序），所以各行相加始终等于合计。改动来自 `review` 对轮次的归因结果。
- 没有改动的轮次（阅读、讨论、跑测试、回答问题）跟随同一会话里最近的有改动轮次：先找它之前最近的一个，没有再找之后最近的一个，按那一轮的分支和权重归属。例外是跟踪中的会话里、这一轮自己有确定的观察（不是「不确定」），按两种情况处理。命令明确进入了某个 worktree（从命令文本解析出的 `cd`、`pushd`、`git -C`，见「影响」里的 `agents`），或读文件、搜索的工具以某个 worktree 里的路径为目标（用 `cd ../B` 读和用读文件工具读 `B` 里的绝对路径是同一件事，归属应当相同），或这一轮写过文件、但结束时没有留下改动（写了又还原，如失败的尝试），写文件工具的目标路径所在的 worktree 同样算明确进入：这一轮按进入的 worktree 当时的分支（和它所属的项目）归属，进入了几个就在它们之间平均分摊，不跟随，因为命令明确指出了在哪里工作。只是 cwd 所在 worktree 换了分支：最近的有改动轮次改的是同一个 worktree、而这一轮观察到的分支与那时不同（会话中途切到了别的分支跑测试、读代码）时，按自己观察到的分支归属；最近的有改动轮次改的是别的 worktree（通过绝对路径改另一个 worktree）时仍然跟随，因为 cwd 的分支说明不了这一轮在为哪个分支工作。会话里没有任何改动时，按每一轮自己的分支：Lectern 正在跟踪的会话，每一轮结束时（以及每个可能切换分支的工具调用之后）记下 cwd 所在 worktree 的分支和 HEAD，与有改动的观察一起保存，所以 Codex 会话中途切到功能分支后只读代码、跑测试，也归到功能分支；一轮里观察到不止一个分支时（包括一次调用期间 HEAD 停留过的分支：调用开始时检出的分支，以及 HEAD reflog 里确定落在调用开始与工具结果之间的每次切换的目标分支，以及确定在结果之前、但不确定是否在开始之后的切换的目标分支（理由见「影响」里的 `agents`），其余先后无法确定的切换不计入），这一轮的 token 在这些分支间平均分摊，所以 `git switch B && cargo test && git switch A` 这样回到原分支的命令，B 也分到一份；导入的旧会话没有这些观察，用日志里记录的分支（Claude Code 每条记录带 `gitBranch`，Codex 只有会话开头 `session_meta` 里的 `git.branch`）；记录的是默认分支（且 `forge` 没有对应 MR）或没有记录时，归入「不属于任何 MR」。
- 子 agent 会话先按它自己的改动和以上规则归属，再把用量计入父会话的合计（ADR 0014）。子 agent 里没有改动的轮次先在子 agent 自己的会话里按最近的有改动轮次归属；只有子 agent 整个会话都没有改动时，才跟随启动它的那一轮父会话轮次。所以几个子 agent 分别改不同分支时，各自的用量落在各自的分支上。父会话里只负责派出子 agent、自己没有改动的轮次，按它派出的子 agent 的改动权重分摊到这些分支上，不按父会话记录的分支归属。父轮次和它派出的所有子 agent 都没有改动时，整棵子树按普通的没有改动的轮次处理（跟随父会话里最近的有改动轮次；会话里没有改动时用上一条的规则：跟踪中的会话按每一轮观察到的分支，导入的旧会话才用日志记录的分支）。
- 分支按「一次使用」区分，不只看分支名：一次使用从 Lectern 第一次观察到这个分支开始。观察里写进去的是一个固定的片段标识：每遇到一个可能的边界（删除后重建、`reset` 类丢弃）就开始一个新片段，并记下边界事件的时间和种类；哪些片段属于同一次使用在汇总时按下面的规则计算，不在写观察时决定。所以 P1、P2 或离线期间发生的边界，在 `forge` 之后拿到 MR 的状态时间线、证明边界发生时这个分支开着 MR 时，前后片段在汇总时合并为同一次使用，以前的用量随之并入这个 MR。边界发生时 MR 是关闭的、之后同一个 MR 又重新打开、而且重新打开后它的源分支就是边界之后的片段时，同样合并：重新打开说明这仍是同一件工作，关闭期间的工作按 MR 统计区间的规则并入这个 MR，不会因为片段不同被拆成两份或重复计算。分支改名（`git branch -m`）不是新的一次使用：Lectern 从分支 reflog 里的 `Branch: renamed refs/heads/A to refs/heads/B` 记录（或旧名消失、新名带着同一份 reflog 出现）识别改名，记下改名关系，标识沿用，所以改名前的用量随分支并入之后开出的 MR。以下两种情况算新的一次使用，之前那次的用量不并入新的：没有开着的 MR 时，分支被删除后重新创建（reflog 里有新的创建记录，或两次观察之间分支不存在）；没有开着的 MR 时，分支被重置、丢弃了上一次观察到的分支独有的提交。是否连续按新旧位置的提交关系判断，不只看 reflog 记录的说明文字（`git update-ref` 等命令可以写任意说明，也可以不带 `reset` 字样就把分支移回去）：新位置包含上一次观察到的分支独有提交（旧位置是新位置的祖先，如 `commit`、`merge`、`pull`、`cherry-pick`）就是连续，不看说明；不包含时，有改写的证据才算连续：`agents` 交来的命令里有这次改写（`git rebase`，包括交互式 rebase 里删除、合并提交，以及 `commit --amend`、`pull --rebase`），或旧的每一个独有提交都能在新位置按 `git patch-id --stable` 找到唯一的对应（一一对应，改写保留了全部内容；`--stable` 忽略空白、重复的等价改动会同号，所以只有部分对应、或对应不唯一时不算，交互式 rebase 删掉了提交的情况要靠命令证据）；没有这些证据的（`reset`、`branch -f`、`checkout -B` / `switch -C`、`update-ref` 回退，以及说明写着 rebase 却找不到任何对应内容的移动），算丢弃。还没有提交、只有未提交改动的分支，被观察到回到起点（没有分支独有的提交）而且工作区没有改动时（如 `git reset --hard`、`git restore` 丢弃了全部改动），这次使用结束，之后的改动算新的一次使用。用 `git stash` 暂存改动不算丢弃：这时 `refs/stash` 的 reflog 会新增一条来自这个分支的记录（`WIP on <分支>` 或 `On <分支>`），这次使用只是挂起；之后 `stash pop` / `apply` 恢复了改动就接着算；恢复到另一个分支上时（`stash apply` 不改 `refs/stash` 的 reflog，`pop` 只删除一条记录，都不说明恢复的是哪一条，所以按内容判断：工作区在另一个分支上新出现的改动，包含某条 stash 提交相对它父提交的改动，就认定是这条 stash 被恢复了（`git stash push -u` / `-a` 存下的未跟踪和被忽略的文件不在这个差异里，而在 stash 提交的第三个父提交里，所以比较时把这个父提交里的文件也算进 stash 的改动：工作区新出现了这些文件、内容相同，即算匹配）；按改动块比较，不比较整个文件的 blob：stash 的每个改动块按恢复后的工作区文件判断：它加上的行都在工作区文件里、删掉的行在那个位置已经不在（目标分支 HEAD 已经有其中一部分时也算满足，`git stash apply` 只补上缺的部分，工作区相对 HEAD 的改动里只出现补上的那几行），而且至少有一行出现在工作区相对 HEAD 的改动里（说明这次确实改了工作区）；没有行可比的改动（二进制文件、只改文件模式）按 blob OID 和模式比较：工作区文件按同样的规范化算出的 blob OID 和模式与 stash 里的新版本相同，即算满足，这样的改动出现在工作区相对 HEAD 的改动里时同样说明确实改了工作区，所以 stash 与目标分支上的其他修改三方合并后（文件内容已经不同）也能认出；有冲突的恢复里，已经解决的块同样参与比较，stash 提交从 `refs/stash` 的 reflog 读取，pop 之前已经读到的也保留）。只有内容匹配还不够，还要有恢复的证据，二者之一：`agents` 交来的命令里有在这个 worktree 上执行的 `git stash apply` / `pop`（按「影响」里的目录变化规则解析出 worktree），而且这条命令选中的就是这条 stash：按命令执行前 `refs/stash` 的 reflog 解析命令里的 `stash@{n}` 或提交 OID（不写就是 `stash@{0}`），只有它指向的那一条算恢复；引用解析不出来（用了变量等）时，只有内容匹配的候选恰好一条才认定；或这条 stash 的记录从 `refs/stash` 的 reflog 里消失（文件监听记下时刻），而这些改动在工作区出现的时刻与它相差不超过 5 秒。没有恢复证据时（一个常见的单行改动碰巧也出现在别的分支上）不认定恢复。另外，匹配的改动里至少有一处要确实在恢复的时候出现在工作区：文件监听在这次调用期间或结果之后 5 秒内（命令证据；FSEvents 的通知会延迟，短命令结束时事件可能还没到）、或 reflog 记录消失前后 5 秒内（reflog 证据）记到了这些文件的变化（工作区监听按 git index 过滤，所以 `-u` / `-a` 存下的未跟踪和被忽略文件另外登记为临时的不过滤路径，候选 stash 存在期间这些路径的事件照常交付）；工作区本来就有同样的改动时 `git stash apply` 会因为会覆盖本地改动而中止，工作区没有变化，不认定恢复，有冲突、只恢复了一部分的仍然认定。认定恢复之后按「随工作区带进新分支」的规则处理：产生这些改动的轮次归到恢复它的分支，随它开出的 MR 计入；这条 stash 被删掉（`drop`、`clear`）而改动没有恢复、分支仍在起点且工作区干净时，这次使用才结束。`forge` 仍把这个分支对应到一个开着的 MR 时，本地删除重建也留在同一次使用里。所以合并默认分支、rebase（无论是否删改了提交）、强制推送这类日常更新都留在同一次使用里；分支开着 MR 时，`reset` 也留在同一次使用里。
- MR 的统计区间：在同一次使用之内，从上一个 MR 最终合并或关闭之后（没有上一个就从这次使用开始），到这个 MR 最终合并或关闭为止。这个 MR 的起点是它开出之前、同一次使用里最近的一次合并或关闭事件的时刻（没有就从这次使用开始），按事件时间线确定，之后的状态变化不改变它：A 先开、B 后开、A 先关时，A 的关闭在 B 开出之后，不是 B 的起点，A、B 同时开着的那段在两者的区间里都有；A 关闭、B 开出、A 之后又重新打开时，B 的起点仍是 A 那次关闭，A 自己的区间随重新打开延长到它最终关闭，A 只在关闭之前的工作不计入 B。MR 关闭后又重新打开时，以最后一次合并或关闭为准：关闭期间分支上的工作与开 MR 之前的工作同样对待，重新打开后并入这个 MR；一直没有重新打开时，关闭之后的用量留在分支上，显示为未开 MR 的分支。MR 的状态变化（打开、关闭、重新打开、合并及其时间）由 `forge` 提供，汇总时按最新状态重新计算。开 MR 之前在分支上的工作也计入，未开 MR 的分支在 MR 开出后整体并入；被放弃的分支（删除后没有开 MR）的用量留在它自己那次使用里，显示为未开 MR 的分支，不并入之后同名的 MR。同一次使用同时开着多个 MR（如向不同的目标分支各开一个）时，用量只计一次。每个 MR 的详情（worktree 列表、简报、MR 视图）显示它自己区间内的用量：几个 MR 同时开着的那段时间的用量在每个 MR 里都出现，并注明与哪些 MR 共用；其中一个合并或关闭后，之后的用量只计入还开着的 MR。Usage 页只把同一次使用里统计区间互相重叠的 MR 合为一行（不同分支、不同次使用的 MR 不合并；区间重叠具有传递性：A 与 B 重叠、B 与 C 重叠时三者合为一行），同一次使用里先后开出、区间不重叠的 MR（一个合并或关闭之后才开出下一个）各占一行；合并的这一行只包含这些 MR 统计区间内的用量（加上明确指向这些 MR 的「审阅」），且在时间窗口内；同一次使用里落在所有 MR 区间之外的用量（如最后一个 MR 关闭后、没有重新打开时的工作）单独一行，显示为未开 MR 的分支，项目合计不重复计算。
- Lectern 自己发起的模型调用（如会话简报的分析）归到被分析的改动所属的 MR，标为「审阅」，与 agent 写代码的「编写」分开显示。从 MR 视图发起的调用带着那个 MR 的标识，直接记到它名下；从会话简报发起的调用，发起时按被分析的轮次当时的归属（包括已经合并或关闭的 MR）解析出 MR 标识，随计量记录一起保存，不等汇总时再按分支推断，所以 MR 关闭之后再分析它的会话，用量仍记到这个 MR，不会落进区间之外的分支用量或之后复用这个分支的 MR；解析出几个开着的 MR 共用这个分支时，按共用分支的规则处理（用量只计一次，每个 MR 的详情里注明共用，Usage 页合为一行）。「审阅」不受 MR 统计区间限制：MR 合并或关闭之后再分析它，用量仍计入这个 MR 的累计值；项目合计照常按调用的时间落在时间窗口里。一次分析覆盖多个分支（如简报分析了改动多个分支的整个会话）时，按被分析的改动在各分支的权重（改动行数加改动文件数）分摊。被分析的会话没有任何改动时，按这个会话没有改动时的规则归属（跟踪中的会话按每一轮观察到的分支，被分析的轮次落在几个分支上时，按这些轮次在各分支的 token 数分摊；导入的旧会话用日志记录的分支；默认分支则归入「不属于任何 MR」）。
- 观察结果在一轮结束后定稿：一轮在下一条用户输入出现、或会话结束时视为结束，结束之前的归属只作为临时结果，随着日志追加继续更新。但每个工具调用的观察（还原出的分支和 HEAD、命令进入的 worktree）以及判断先后用到的证据（文件监听记下的每条 reflog 的亚秒时刻和序号）在到达时就写入 SQLite，不等一轮结束：Lectern 在一轮中途退出时，重启后从已保存的观察和证据继续，亚秒时刻不会丢失，只有一轮级别的分摊在一轮结束时计算。没有改动的轮次跟随哪一轮不在这时定死：它在汇总时按整个会话的记录计算，会话开头的规划、测试轮次之后才出现第一个有改动的轮次时，它照常跟随那一轮。每个产生改动的工具调用执行之后，Lectern 记下该 worktree 在工具结果时间戳那一刻的分支和 HEAD：不直接读当前状态（日志读到时 agent 可能已经开始下一条命令），而是按这个 worktree 的 HEAD reflog 还原那个时间点的分支和 HEAD。reflog 的时间只精确到秒，所以 Lectern 用文件监听记下每一条 reflog 新增的时刻（亚秒精度）和它的序号。这个监听直接监视 git 公共目录里的 `logs/HEAD`、`logs/refs/heads/`、`logs/refs/stash` 和 `worktrees/*/logs/HEAD`；仓库用 reftable 存引用（`extensions.refStorage=reftable`，`git init --ref-format=reftable` 创建）时，引用和 reflog 都在 `reftable/` 目录的表里，改为监视这个目录取得新增记录的时刻，记录内容一律通过与存储格式无关的 git 接口读取（`git reflog` 一类），不直接解析文件；不经过按 git index 过滤的工作区监听（reflog 不是受跟踪的文件，linked worktree 的 reflog 也不在它的工作区目录下）。文件监听的通知是异步的，可能延迟或合并，所以「监听时刻早于工具结果」只能证明这条记录在结果之前；判断一条 reflog 记录与某个工具结果的先后，只用两条确定的规则：监听时刻早于结果时间戳的，在结果之前；git 自己记下的时间（秒）晚于结果所在那一秒的，在结果之后。两条都不适用时，这一次调用的分支标为「不确定」（例外是确定在结果之前、只是不确定是否在开始之后的切换：只有一条时，它的目标在调用期间一定被检出过，按「影响」里的规则计入，不标为不确定；连续有几条时按「影响」里的规则标为不确定）；有改动的按内容的去向归属（之后的提交在哪个分支的 reflog 里、或未提交的改动留在哪个分支上），没有改动的调用按普通的没有改动的轮次处理（跟随同一会话里最近的有改动轮次），不按猜测的分支归属，所以 `git switch feature && 改文件` 这样的命令记到的是执行后的分支。一次调用里分支切换了不止一次（如 `git switch B && 改文件 && git commit && git switch A`）时，Lectern 同时读取这次调用期间各分支 reflog 新增的条目：调用期间新增的提交归到 reflog 里记下它们的那个分支，调用结束时仍未提交的改动归到调用结束时检出的分支（切换分支时未提交的改动随工作区一起带过去）；一轮里切换了分支、改了几个分支时各自记录；每条观察同时记下仓库的稳定标识（git 公共目录的规范绝对路径，以及 `forge` 可用时代码平台给仓库的不变 ID，如 GitHub 的 repository id、GitLab 的 project id，仓库改名或转移后不变；owner/name 只用于显示），所以 worktree 删除、分支删除之后，重建仍能把这些记录对应到项目和 MR。一轮结束时，这些观察连同会话的 cwd、改动文件的路径、每个改动的改动行数，按「文件 × 分支观察」记录（同一个文件在一轮里先后在两个分支上改动时分开记，分支和项目的权重都由它算出，普通文件夹没有分支也能按项目分摊），以及各分支当时是否为默认分支，写入 Lectern 的 SQLite，之后不再修改（默认分支改名后，旧的记录仍按当时的分类处理），汇总和重建都以这份记录为准。项目和 MR 的归属在汇总时由这份记录计算，所以之后打开的项目、之后开出的 MR 都能拿到以前的用量。导入较早的会话时，如果改动所在的 worktree 已经删除或换了分支、无法确定当时的分支，这些轮次归入「不属于任何 MR」，并标为「无法归属」。

**分阶段**

- P1、P2：按项目和分支汇总，界面上（包括 P2 的 Usage 页）标为「分支用量」，不称为 MR。`forge` 就绪后（P3）关联到代码平台上的 MR，显示 MR 编号和标题，统计区间按上面的规则切分。
- 离线或代码平台不可用时，按分支显示，不影响统计。

### 已知限制

以下情况按上面的规则会归属不准，影响的是个别轮次，不做专门处理：

- 命令文本的目录解析只覆盖常见写法：顶层的 `return`、少见的 shell 选项等，从那里起按「不确定」处理，这一轮跟随最近的有改动轮次。
- `git branch <名字>` 不切换分支、随后 `reset` 掉默认分支上的提交再推送这个新分支，这样的补救流程不转移原来的用量；只认 `switch -c` / `checkout -b`、`worktree add -b`、cherry-pick 和推送这几种来源。
- 同一个提交被 cherry-pick 到几个分支、各自开 MR 时（如往几个发布分支回合），产生它的轮次只计入第一个转移到的 MR。

## 影响

- `agents`：除了原始用量记录，按顺序交出每个可能产生改动或切换分支的工具调用（写文件的工具和所有执行命令的工具）的开始与结果事件（调用开始的时间戳、结果的时间戳、所在会话与轮次、目标路径，执行命令的工具另带命令文本），以及读文件、搜索工具的目标路径和时间戳（供没有改动的轮次判断明确进入了哪个 worktree），`usage` 用同样两条确定的规则判断 reflog 记录是否在调用开始之后、结果之前，所以命令开始之前的外部切换不会算进这次调用停留过的分支。只是不确定是否在调用开始之后、但确定在结果之前的切换（短命令里第一个 `git switch B` 常常落在开始的同一秒），它的目标分支仍然算作这次调用停留过的分支：不论这次切换发生在开始之前还是之后，调用期间 HEAD 都在 B 上；它之前的那个分支只有在这次切换确定发生在开始之后时才算。这样的切换连续有几条时（如开始之前的同一秒里先切到 B、又切回 A，监听通知延迟到结果之前才到），开始时刻可能落在它们之间的任何位置：只有序号最后的那一条的目标确定在调用期间被检出过，前面几条是否在调用期间无法判断，所以这次调用的分支标为「不确定」，不只记最后一条的目标，按普通的没有改动的轮次处理。所以 `git switch B && cargo test && git switch A` 里，`git switch A` 的记录确定在开始之后时（git 记下的时间晚于开始所在的那一秒，测试跑了一秒以上就是这样），B 是最后一条不确定的切换，照常计入；两条记录都落在不确定的范围里时，这次调用标为不确定，不会全部记到 A。命令可能进入别的 worktree（`cd ../other && git switch B && cargo test`）：`usage` 从命令文本里取出 `cd`、`pushd` 的目标和 `git -C` 的参数，按命令里的顺序模拟目录变化：从调用的工作目录开始，每个 `cd`、`pushd`、`popd` 之后更新当前目录；`pushd -n`、`popd -n` 只改目录栈、不改当前目录；`popd` 和不带目录参数的 `pushd` 按模拟出的目录栈计算，要用到这次调用之前的栈（栈里没有这次调用自己压入的项）时从这里起按「不确定」处理；`cd -`、`pushd` / `popd` 的 `+N`、`-N` 形式和其他不认识的选项同样按「不确定」处理；不带参数的 `cd`（进入 `$HOME`）、以 `~` 开头的目标和含 `$`、反引号的目标依赖执行命令的 shell 的环境，事件里没有，同样从这里起按「不确定」处理；`cd`、`pushd` 的相对目标不以 `.`、`..` 开头时（`cd repo`），shell 会先在 `CDPATH` 里查找，事件里没有执行命令的 shell 的环境变量，所以这类目标从这里起按「不确定」处理，`./repo`、`../B` 和绝对路径不经过 `CDPATH`，照常解析（`git -C` 不查 `CDPATH`）；`cd` 是否成功按目标在调用开始和工具结果两个时刻是否存在判断：开始时就存在、而且在结果时检查是可进入的目录（路径每一级都有搜索权限，`access(X_OK)`；agent 与 Lectern 以同一用户运行）的算成功，存在但不可进入或不是目录的从这里起按「不确定」处理；两个时刻都不存在的算失败（如 `cd /missing; cd ../B`），当前目录不变，后面的 `cd ../B` 从原目录解析；开始时不存在、结果时存在的（前面的命令刚创建，如 `git worktree add ../B feature; cd ../B`）无法确定 `cd` 执行时它是否已经存在，从这里起按「不确定」处理，目录在调用之后被删除、无法判断的，从这里起按「不确定」处理，后面的相对路径从更新后的目录解析（`cd .. && cd B` 进入的是上一级的 `B`），`git -C` 的参数按当时的目录解析，事件里没有中间命令的退出状态，所以只计入确定执行过的目录变化：用 `;` 接在后面的，以及用 `&&` 接在只有 `cd`、`pushd`、`popd` 组成的前缀后面的（`cd .. && cd B`）；遇到会结束 shell 的命令（`exit`、`return`、`logout`，以及带了要执行的命令的 `exec`）就停止解析，后面的目录变化不计入；只有重定向、没有命令的 `exec`（`exec 3>&1`）只在当前 shell 里生效，照常往下解析；`set -e`（以及 `set -o errexit`、`set -eu` 这类组合）之后任何命令失败都会结束 shell，`;` 不再保证后面的命令执行，按接在其他命令的 `&&` 之后处理，直到 `set +e`（`set +o errexit`、`set +eu` 这类组合）关掉它为止；接在其他命令的 `&&` 之后（`false && cd B`）或任何 `||` 之后的目录变化不确定，从这里起的目录按「不确定」处理，后面的部分不再解析，`|`、子 shell 和以 `&` 结尾放到后台执行的命令（后台命令在子 shell 里运行）里的 `cd` 不影响外面的目录，落在已知 worktree 里的，把那些 worktree 的 HEAD reflog 一并按同样的规则读取，这次调用停留过的分支也包括它们；用变量、子 shell、脚本间接进入的 worktree 解析不出来，这部分按普通的没有改动的轮次处理（跟随最近的有改动轮次），不猜测；`usage` 据此按每个结果的时间戳从 HEAD reflog 还原当时的分支和 HEAD，没有改动的轮次中途切换过分支也能还原。
- `fs_watch` 与 `platform`：除了按 git index 过滤的工作区监听，再提供一个不过滤的 git 元数据监听，监视公共目录里的 reflog（`logs/HEAD`、`logs/refs/heads/`、`worktrees/*/logs/HEAD`），给每条新增记录打上亚秒时刻和序号。
- `agents`：Lectern 自己发起的分析（ADR 0019 的会话简报与 MR 分析）由凭据转发端点计量，每个请求转发之前就交给 `usage` 落盘一条计量记录（状态为「已准备」，输入 token 用转发前算出的值，输出为 0），请求体完整写入上游连接之后改为「已转发」；收到 2xx 响应后，无论流式还是一次性返回的响应，端点都边转发边按已转发的响应体估算输出 token（一次性返回的 JSON 按已收到的字节数估算），至少每秒或每 4 KB 把估算值写回记录一次，响应里的最终用量到达时用真实值替换，分析结束时标明完成、取消或失败；模型服务没有接受请求时不计费：响应状态不是 2xx（如 400、401、413、429、5xx）且响应里没有用量字段时，记录标为「被拒绝」，输入 token 记为 0，不按转发前的估算收费；错误响应里带了用量的，按它记录。收到 2xx 响应头时记录改为「已接受」。Lectern 异常退出后再启动时，「已接受」的记录按已知的值结算并标为「估算」；「已转发」但还没收到响应头的记录无法确定服务是否已经开始处理，同样按漏计一侧处理，记为 0 并标为「未确认」，「已准备」的记录（请求还没发出）直接作废、不计费，所以模型服务已经消耗、但 Lectern 没等到结束的调用计入，没发出的请求不计入。写完请求体到改为「已转发」之间崩溃的极短窗口会漏计一次请求，这一侧的误差比多计更可接受。记录的内容：时间戳、agent 与模型、按 ADR 0014 的类别分开的 token（输入、输出、缓存读取、缓存写入，服务商报告的原始字段原样保存一份，计算 token 合计和费用之前先按服务商规范化成互不重叠的类别，规则与 ADR 0014 的去重一致：OpenAI / Codex 的 `input_tokens` 已经包含 `cached_tokens`，所以非缓存输入是两者之差，Anthropic 的 `input_tokens` 不含 `cache_read_input_tokens` 和 `cache_creation_input_tokens`，原样使用；规范化之后每个类别按各自的单价计算，缓存命中不会既按输入又按缓存计一次；端点估算的标为「估算」）、是否为重试，以及发起时的上下文（项目标识、MR 标识或分支、被分析的会话与轮次）。日志里没有这些调用，`usage` 只从这条记录得到「审阅」的用量。
- `usage`：在去重和聚合之外增加归属：输入是每轮的用量、Lectern 分析的计量记录、`review` 给出的每轮改动、`project` 给出的 worktree 与分支，以及 `forge` 给出的 MR 列表（可选）；读到日志时把每轮的 worktree、分支和 HEAD 一并保存；输出按项目和 MR 两级汇总的快照，会话和轮次作为明细。
- `project_home`：侧栏底部的 Usage 入口显示本项目合计，会话卡片不再显示 token。
- `worktrees`、`review_view`、`usage_view`：按上表调整显示位置。
- `forge`（P3）：提供分支与 MR 的对应关系，以及每个 MR 的状态变化（打开、关闭、重新打开、合并）和时间。
- 交互规范「用量」、路线图、README 同步修改。
