# i18n 设计

对应 issue [#28](https://github.com/SoloJiang/lectern-app/issues/28)。界面英文优先，支持简体中文，所有界面字符串从第一天起走 Fluent 资源文件（[ADR 0013](../adr/0013.md)、[交互规范「语言」](interaction.md#语言)）。

## 范围

- 做：
  - en 与 zh-CN 的 Fluent 资源，嵌入二进制。
  - 从系统的首选语言列表协商出界面语言。
  - 按键取字符串、带参数格式化、复数。
  - 编译期生成的键常量：键写错是编译错误。
  - 数量与相对时间的格式化。
  - 一组测试，检查两种语言的资源一致，由 CI 运行。
- 不做：
  - 读写系统语言设置：归 `platform`（架构规则 6），由 `app` 把结果传进来。
  - 把字符串交给视图的 GPUI 胶水（全局状态、切换后刷新窗口）：归 `ui`。
  - 翻译人和 agent 写的内容：prompt、说明、评论、代码、路径、命令、快捷键原样显示。
- 本 issue 之外：
  - 插件市场下载的额外界面语言（[ADR 0018](../adr/0018.md)）。
  - 调试用的伪语言（拉长、加重音，检查截断）。
  - 在类型上禁止视图传字面量：`ui` 的控件只接受来自本 crate 的文本或标明原样显示的文本，写进 `ui` 的设计文档。

## 依赖

| 依赖 | 用途 | 为什么是它 |
|---|---|---|
| `fluent-bundle` 0.16 | 解析资源、格式化、复数规则 | ADR 0013 选定的 fluent-rs；MIT / Apache-2.0；传递依赖小（`fluent-syntax`、`intl_pluralrules`、`unic-langid`、`intl-memoizer`、`self_cell`、`smallvec`、`rustc-hash`），不带 ICU 数据 |
| `unic-langid` 0.9 | 语言标识 | `fluent-bundle` 的公开 API 用它 |
| `fluent-syntax` 0.12（build-dependency） | `build.rs` 解析 en 资源，生成键常量 | 与 `fluent-bundle` 用同一个版本，不增加新的 crate |

不用 `fluent-langneg` 做协商：它把 `zh-TW`、`zh-Hant` 也匹配到 `zh-CN`（P0 原型实测），见「未决问题」。不用 icu4x：数据体积与安装包预算（ADR 0018）不相称，需要的格式化只有下面几种。

## 接口

```rust
/// 界面语言。新增语言就是在这里加一项、加一个资源目录。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Locale {
    En,
    ZhCn,
}

impl Locale {
    pub const ALL: [Locale; 2] = [Locale::En, Locale::ZhCn];

    /// BCP 47 标签："en"、"zh-CN"。
    pub fn tag(self) -> &'static str;

    /// 语言选择器里显示的名字，总是用该语言自己的写法："English"、"简体中文"。
    pub fn native_name(self) -> &'static str;

    /// 按顺序遍历系统的首选语言列表（如 macOS 的 `["ja-JP", "zh-Hans-CN", "en-US"]`），
    /// 取第一个能对应到已有语言的；都对应不上时为 `En`。纯函数，任何线程。
    pub fn negotiate<'a>(preferred: impl IntoIterator<Item = &'a str>) -> Locale;
}

/// 一条消息或消息的一个属性。只由生成的 `keys` 模块构造。
#[derive(Clone, Copy, Debug)]
pub struct Key { /* id: &'static str, attr: Option<&'static str> */ }

/// build.rs 从 locales/en/*.ftl 生成。`review-looks-good` → `keys::review::LOOKS_GOOD`，
/// 属性 `review-looks-good.tooltip` → `keys::review::LOOKS_GOOD_TOOLTIP`。
pub mod keys;

/// 格式化参数。
#[derive(Default)]
pub struct Args<'a> { /* FluentArgs<'a> */ }

impl<'a> Args<'a> {
    pub fn new() -> Self;
    pub fn num(self, name: &'a str, value: impl Into<f64>) -> Self; // 参与复数选择
    pub fn str(self, name: &'a str, value: &'a str) -> Self;        // 原样插入，如路径、会话标题
}

/// 一种语言的全部界面字符串。不可变，`Send + Sync`，用 `Arc` 共享；切换语言就是换一个新的。
pub struct Strings { /* locale, concurrent::FluentBundle<FluentResource> */ }

impl Strings {
    /// 解析这种语言的嵌入资源。不读文件；耗时见「性能」。
    pub fn load(locale: Locale) -> Strings;

    pub fn locale(&self) -> Locale;

    /// 没有参数的消息。
    pub fn get(&self, key: Key) -> Cow<'_, str>;

    /// 带参数的消息。
    pub fn format(&self, key: Key, args: &Args<'_>) -> Cow<'_, str>;

    /// "just now"、"5 min ago"、"3 days ago" / "刚刚"、"5 分钟前"、"3 天前"。
    /// 文案来自 common.ftl，本函数只选消息和单位。
    pub fn relative_time(&self, elapsed: Duration) -> Cow<'_, str>;
}

/// 数量的紧凑写法，用于 token 数：`950`、`12.3K`、`4.5M`。两种语言写法相同，见「数据结构」。
pub fn count_compact(n: u64) -> String;
```

调用方：

- `app` 启动时调用 `Locale::negotiate` 和 `Strings::load`（见「数据流与线程」）。
- 视图通过 `ui` 拿到当前的 `Arc<Strings>`，在渲染时调用 `get` / `format`。格式化是纯计算，在 UI 线程上调用。
- 领域层不依赖本 crate：领域层交出的是数据和错误枚举，由视图映射到键。

错误处理：

- 资源在编译期嵌入，并由测试保证可解析、两种语言的键一致，运行时不会缺键。
- 格式化出错（如漏传参数）时：调试构建 `debug_assert!` 失败；发布构建返回 Fluent 的兜底输出（缺的参数显示为 `{$name}`）并记一条日志，不崩溃。

## 数据结构

资源目录：

```
crates/i18n/
├── build.rs                # 生成 keys 模块
└── locales/
    ├── en/
    │   ├── common.ftl      # 通用：按钮、相对时间、空状态
    │   ├── welcome.ftl     # 每个视图 crate 一个文件
    │   ├── review.ftl
    │   └── ...
    └── zh-CN/              # 与 en 同名同键
        └── ...
```

规则：

- 键的前缀等于文件名：`review.ftl` 里只有 `review-*`，避免跨文件重名。
- 用属性放同一个元素的附属文案：`.tooltip`、`.label`（无障碍标签）、`.placeholder`。
- 复数用选择表达式：en 写 `[one]` 和 `*[other]`；zh-CN 只有 `other`，写成不带选择的普通消息即可。
- 不写 Fluent 函数 `NUMBER()` 的格式选项：fluent-bundle 不带 ICU，分组与小数位的格式由调用方算好后用 `Args::str` 传入（如 `count_compact` 的结果）。
- `set_use_isolating(false)`：两种语言都是从左到右书写，不插入 Unicode 方向隔离符，避免文字渲染里出现不可见字符。

示例：

```ftl
# en/review.ftl
review-looks-good = Looks good
    .tooltip = Mark every file as reviewed
review-progress = { $reviewed }/{ $total } reviewed
review-files-changed = { $count ->
    [one] { $count } file changed
   *[other] { $count } files changed
}
```

```ftl
# zh-CN/review.ftl
review-looks-good = 看起来没问题
    .tooltip = 将所有文件标记为已看
review-progress = 已看 { $reviewed }/{ $total }
review-files-changed = { $count } 个文件有改动
```

语言协商规则（`Locale::negotiate`）：

| 首选语言 | 结果 |
|---|---|
| `zh-Hans*`；没有书写系统的 `zh`、`zh-CN`、`zh-SG`、`zh-MY` | `ZhCn` |
| `zh-Hant*`、`zh-TW`、`zh-HK`、`zh-MO` | 跳过，继续看下一个首选语言（见「未决问题」） |
| `en*` | `En` |
| 其他 | 跳过 |

数量：token 数在两种语言里都写成 `12.3K`、`4.5M`，不用「万」：这是开发工具里的计数，与 agent 自己的界面和日志写法一致，也和英文界面的列宽相同。文件数、轮次等小数字直接显示。

## 数据流与线程

启动（首帧之前）：

1. `app` 进入 `main` 后先向 `executor` 提交一个任务：调 `platform` 读系统首选语言列表，`Locale::negotiate`，`Strings::load`。
2. 主线程同时创建窗口和 Metal 设备。
3. 布局首帧之前等这个任务完成。解析与窗口创建并行，不加长冷启动的关键路径。

资源用 `include_str!` 嵌入，首帧之前不读我们自己的文件（[性能预算](tech-research.md#性能预算)）。

语言设置：

- 设置里的选项是「跟随系统 / English / 简体中文」。
- 选择保存在应用自己的 user defaults 的 `AppleLanguages` 键里，由 `platform` 读写；选「跟随系统」就删掉这个键。这样：
  - 下次启动时，第 1 步读到的首选语言列表已经是用户选的语言，首帧就是正确的语言，不需要在首帧之前读我们自己的设置文件。
  - 与 macOS「系统设置 › 通用 › 语言与地区 › 应用」里的按应用设置语言是同一个设置，两边一致。
- 发布用的 `.app` 在 `Info.plist` 的 `CFBundleLocalizations` 里声明 `en` 与 `zh-Hans`，并带对应的 `.lproj`。这样系统提供的界面（打开文件夹面板、标准菜单项）与 Lectern 的界面语言一致。这一项在打包时做（[#38](https://github.com/SoloJiang/lectern-app/issues/38)）。

运行中切换：

1. 视图发出切换命令。
2. 后台任务写 `AppleLanguages`，并为新语言 `Strings::load`。
3. 加载完成后替换 `ui` 持有的 `Arc<Strings>`，所有窗口重绘，立即生效。

## 性能

- 首帧之前只解析当前语言一份资源，不解析英文兜底：键一致由测试保证，运行时不需要兜底。
- 原型实测（Linux 容器，release）：125 KB 的 FTL 解析并建 bundle 约 1.3 ms，800 次带复数的格式化约 0.45 ms。预计全部界面文案在 50 KB 以内，M 系列 Mac 上解析低于 0.5 ms，而且与窗口创建并行。
- 内存：一种语言的资源和语法树在 1 MB 以内。
- `bench`（[#7](https://github.com/SoloJiang/lectern-app/issues/7)）增加两项：`Strings::load` 的耗时（每种语言），以及首帧之前等它完成的时间（应为 0）。超过 1 ms 时，按视图拆分资源，各视图在第一次显示时再解析。

## 状态与异常

- 系统首选语言都对应不上：英文。
- `platform` 读系统语言失败：英文，记日志。
- 写 `AppleLanguages` 失败：本次运行仍切换语言，提示一次「语言设置未能保存」，下次启动按系统语言。

## 测试

全部在 Linux 上也能跑（`just test -p lectern-i18n`），CI 的 Linux 任务即可覆盖：

- 资源一致性（这就是 issue 要求的 CI 检查）：
  - 两种语言的文件名集合相同。
  - 每个文件里，消息 ID 集合相同，每条消息的属性集合相同。
  - 每条消息在两种语言里引用的变量集合相同，选择器里的变量也算。
  - 资源全部能解析，没有语法错误和重复的 ID。
  - 键的前缀等于文件名。
- `Locale::negotiate`：上面的协商表逐行覆盖，包括 `["ja-JP", "zh-Hans-CN"]` 这种第一项对应不上的列表，以及空列表。
- 格式化：用 insta 快照记录两种语言下的复数、`relative_time` 的各个区间、`count_compact` 的边界值（999、1000、999 949、1 000 000）。
- `build.rs` 生成的常量与 en 资源一一对应（编译期由用法保证；测试再检查数量一致）。

调系统 API 的部分在 `platform` 里测，不在本 crate。

## 未决问题

1. **繁体中文用户看什么。** 选项：
   - (a) 显示英文（倾向）：不把简体当成繁体给台湾、香港用户；以后可以加 zh-TW 资源。
   - (b) 显示简体中文：多数繁体用户读得懂简体，比英文更易读。

   请产品负责人决定。默认按 (a) 实现，改成 (b) 只需改协商表的一行。

## 验收

- `Strings::load` 对两种语言都能成功；`keys` 模块由 en 资源生成。
- en 与 zh-CN 的键、属性、变量不一致时，`just test` 失败，CI 的 Linux 任务失败。
- 协商表的每一行都有测试。
- 首帧之前不读文件，`Strings::load` 在后台任务里与窗口创建并行（`app` 接入时验证，基准在 #7）。
- 交互规范与 ADR 0013 里过时的字体说明改为 ADR 0015 的 SF Pro / SF Mono（随本设计文档一起修改）。
