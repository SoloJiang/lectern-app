# 依赖源码、空闲解析、大文件与渲染调研

2026-10-18。调研对象有四个：依赖目录（node_modules 等）里的源码怎样为跳转服务，后台解析怎样利用空闲时间，单个大文件怎样快速打开，渲染侧有哪些瓶颈。Lectern 自己的数字来自 Linux 容器上的微基准（见「实测说明」），标为「本文实测」；GPUI 和 gpui-component 的结论来自读锁定版本的源码，标为「读源码」，在 macOS 上由 `#[gpui::test]` 和 UI 探针验证。

## 背景与目标

产品要求（原话译文）：「代码跳转的索引解析，某些语言或技术栈的依赖文件，比如 node_modules，可以异步解析。解析策略要充分利用空闲时间解析和流式、分片解析；尤其是打开单个大文件要非常快。另外检查渲染侧有没有瓶颈和对应的优化，比如虚拟化。」另已决定：省电模式暂不考虑，建索引不区分电源（已写进 [ADR 0032](../adr/0032.md)），本文不做任何针对电池的设计。

现有设计已经定下的前提：

- 导航第 1 层「语法索引」由 `code_intel` 实现：按 blob 抽取、五层优先级、可暂停的批量层、后台 1 MiB 与打开文件 4 MiB 的大小上限、后台 250 ms 与交互 1 s 的单文件截止时间（[code_intel 设计](../design/code_intel.md)「范围」「数据流与线程」「建索引的分层」「调度、批次与取消」「性能」）。第 1–3 步已合并，第 4 步（查询与插件）在另一个分支上进行。
- 后台工作的两类守卫、批量线程组和 kernel 的暂停开关（[ADR 0029](../adr/0029.md)）；抽取用一次遍历、吞吐预算 4 MB/s（[ADR 0030](../adr/0030.md)、[ADR 0031](../adr/0031.md)）；导航第 3 层「依赖源码」按需（[ADR 0007](../adr/0007.md)、[技术调研「代码导航与编辑」](../design/tech-research.md#代码导航与编辑)）。
- 预算：冷启动 20 ms、空闲内存 60 / 100 MB（[ADR 0017](../adr/0017.md)）；安装包 80 MB、非核心功能做成插件（[ADR 0018](../adr/0018.md)）；打开文件到首屏高亮 < 16 ms，首屏经有界的范围读取（[#103](https://github.com/SoloJiang/lectern-app/issues/103)）、只解析可见区域；滚动与输入稳定 120 fps，靠虚拟滚动（[性能预算](../design/tech-research.md#性能预算)）。
- 被 .gitignore 忽略的目录（node_modules、target、.next）不进文件列表、不建索引、不监听（[技术调研「排除的功能」](../design/tech-research.md#排除的功能)）；TS 的包名解析跳过 node_modules 里的符号链接，把工作区里的包解析到源码（[技术调研「跨子项目导航」](../design/tech-research.md#跨子项目导航)）。

### 结论

1. **依赖目录不整体索引，只索引直接依赖的声明闭包。** 一个 21 个直接依赖的 Vite + React + TS 项目，`node_modules` 有 10,053 个文件、116 MiB；跳转需要的直接依赖声明（从 `types` / `exports` 入口沿相对 import 走到的文件）约 250 个文件、5 MiB，是整个目录的 1/24。跳转时按需解析裸模块名；当前子项目的直接依赖在批量层上作为「依赖层」建索引，排在第 4 层之后、第 5 层之前，存进自己的命名空间、有自己的配额；依赖的依赖只按需。依赖根的读取有严格限制：工作区内的根不跟随符号链接打开，工作区外只允许依赖缓存的源码子树，只读声明和源码的扩展名。放在核心的 `code_intel`，不新增依赖（[ADR 0033](../adr/0033.md)）。
2. **依赖的缓存键按内容求 blob OID，用包的身份避免重读。** 读文件加求 OID 约 500 MiB/s，整个 `node_modules` 要 0.2–0.3 s，声明闭包约 10 ms。lockfile 里的 `integrity`（以及 `Cargo.lock`、`go.sum`、`RECORD`）不变就不读、不 stat；取不到身份时用含 ctime 的 stat 表，每个文件约 3 µs；跳转打开目标时按字节核对。失效靠受跟踪的 lockfile 的变化，依赖目录仍不监听。
3. **空闲时解析有了具体的定义和两种用途。** 交互静止是 300 ms 无输入、无动效、无交互任务。交互静止时预取下一个未看文件、抽屉第一个候选和唯一跳转目标的高亮，结果只进已有的 8 MB LRU。kernel 增加一个让路开关：打开时第 4 层、依赖层、第 5 层在分片边界停下、保留状态（第 3 层不停），之后只在全局每 500 ms 一个、最长 50 ms 的保活时段里前进，合计不超过一个核的 10%；实测证据不足以证明需要它，所以默认关闭，由 macOS 上的 `app/scroll_frames_indexing` 决定是否启用。索引覆盖的预算不变。建索引不区分电源（ADR 0032）。
4. **语法树太大，不能常驻。** tree-sitter 0.27.1 解析 TS 约 6 MiB/s，树占输入的 14–41 倍（压缩 JS 47–83 倍）：4 MiB 的 TS 树 134 MiB，64 MiB 的 2.1 GiB。高亮结果存成按行的着色区间，算完即释放语法树。
5. **解析可以分片恢复，但分片不省内存。** 进度回调中止的解析在下一次调用时继续，54 组测量得到的树全部与一次解析相同，5–8 ms 一片的额外开销在噪声以内。分片用于让路和取消；解决大文件靠窗口。
6. **首屏用窗口，耗时与文件大小无关。** 从安全位置开始的 14–25 KiB 窗口单独解析，平均 0.6–6 ms、最差 15 ms，64 MiB 的文件与 1 MiB 的相同；文件开头的窗口与整文件解析逐字节一致，文件中部 40 个随机位置里 85–100% 完全一致；高亮查询限定在可见行时 0.1–0.4 ms（压缩文件 2–4 ms）。首屏窗口带 8 ms 截止时间，超时先画文本、随后上色。首屏路径上的准备工作都有界：选起点只看目标前后至多 64 KiB，不用行索引、不从文件开头扫描，实测最多 0.07 ms，64 MiB 的一行 JSON 合计 2–3.4 ms；64 KiB 内找不到起点时先画纯文本。打开到文件中部要按字节偏移定位：跳转、diff hunk、保存的位置都带偏移，只有行号时用按 OID 缓存的行检查点。ADR 0034 保证的范围是：目标以字节偏移给出、或检查点已在缓存里、或目标在文件开头时，任何大小的文件首屏 < 16 ms；只给行号的第一次打开要扫描到那一行，不在这个保证内。
7. **整个文件按窗口高亮，内存与文件大小无关。** 按前一个窗口的语法树决定下一个窗口的起点，64 KiB 一个窗口，一致率合成文件 100%、真实文件 98.9–100%，总耗时与整文件解析相同，同时只有一个窗口的树（2–5 MiB）。按大小分三档：≤ 1 MiB 整文件分片解析；1–16 MiB 顺序按窗口；> 16 MiB 只算可见附近、文本按页读。多秒的计算都在批量线程上、持有 `BackgroundGuard`，只有可见窗口和前后各一个在 `Interactive` 上。打开文件的符号抽取用同样的窗口，每个窗口完成即写入 `cache`，上限从 4 MiB 提高到 16 MiB（[ADR 0034](../adr/0034.md)）。
8. **gpui-component 的编辑器不适合当大文件的阅读视图。** 读源码：超过 256 KiB 的文件在防抖和整文件解析之后才有高亮，软换行在 UI 线程上测量整个文件，每帧复制整行；它的高亮要 tree-sitter 0.26.13，与 Lectern 的 0.27.1 是两份。阅读视图改为自绘的固定行高列表，只排版可见的显示行，长行折行，滚动位置按行保存（GPUI 的 f32 坐标在约 93 万行之后不再精确）；编辑模式继续用它，只对档位 A 的文件（≤ 1 MiB、没有超过 4 KiB 的行）开放，编辑期间的语法树（上限处 34–41 MiB）在退出编辑时释放。
9. **其余界面用 GPUI 现有的虚拟化。** 等高的行（文件树、diff 展示行、终端）用 `uniform_list` 或同类的自绘元素，不等高的项（对话、审阅叙事）用 `list`；没有上限的集合不用 `div` 滚动；不做 minimap。这部分只读了源码，在 macOS 上由 `#[gpui::test]` 和帧时间基准验证。

## 1. 依赖源码

### 跳转用到哪些文件

跳转进依赖时用的是声明文件：

| 生态 | 依赖根 | 跳转用到的文件 | 入口 |
|---|---|---|---|
| npm / pnpm / yarn | 项目里的 `node_modules` | `.d.ts` / `.d.mts` / `.d.cts`；没有声明文件的包用 `@types/<名字>` | `package.json` 的 `exports["."]` 里的 `types` 条件（可能嵌套在 `import` / `require` 之下），然后 `types` / `typings`，然后 `index.d.ts`、`main` 换成 `.d.ts`；都没有时找 `@types/<名字>` |
| Cargo | `$CARGO_HOME/registry/src/<索引>/<crate>-<版本>/`，git 依赖在 `git/checkouts/` | crate 的 `src/` 下从 `lib.rs` 起的模块树 | `Cargo.toml` 的 `[lib] path`，默认 `src/lib.rs` |
| Go | 模块缓存 `$GOMODCACHE/<模块>@<版本>/`（默认 `~/go/pkg/mod`），或项目的 `vendor/` | 项目 import 到的那些包目录里的 `.go`（不含 `_test.go`），不是整个模块 | import 路径减去模块路径 |
| Python | 项目里的 `.venv` / `venv` 的 `site-packages` | 包的 `__init__.py`、`.pyi` 存根优先 | 顶层包目录；`*.dist-info/RECORD` 列出包的全部文件 |
| Maven / Gradle | `~/.m2/repository`、`~/.gradle/caches/modules-2/files-2.1` | `-sources.jar` 里的 `.java`（[#26](https://github.com/SoloJiang/lectern-app/issues/26)） | 全限定名对应的条目路径 |

TS 的声明文件之间用相对 import、`export * from`、`/// <reference path>` 连起来；从入口出发沿这些边走到的文件集合，本文称为这个包的「声明闭包」。`/// <reference types>` 和裸模块名指向别的包，只记录，不跟随。

pnpm 的布局：`node_modules/<名字>` 是符号链接，指向 `node_modules/.pnpm/<名字>@<版本>/node_modules/<名字>`，包自己的依赖是同一个 `.pnpm/<名字>@<版本>/node_modules/` 下的兄弟目录，文件是内容存储的硬链接（本文实测链接数为 2）。`SafeRoot` 不跟随根目录之下的符号链接（[ADR 0028](../adr/0028.md)），所以 pnpm 的链接要由 Lectern 在依赖根内部解析，规则见下一节。

### 读取限制

威胁模型与 AGENTS.md「Review guidelines」相同：被审阅的 agent 和它启动的进程可以任意改写工作区。它可以把 `node_modules` 或 `.venv` 整个换成指向 `$HOME` 的符号链接，在 `package.json` 里写 `"types": "../../.ssh/id_ed25519"`，或在依赖目录里建指向别处的链接。`SafeRoot::open` 会跟随根路径本身里的符号链接（[platform 设计「接口」](../design/platform.md#接口)），所以「按路径为 `node_modules` 另开一个根」本身就会越界；依赖缓存的整个目录里还放着凭据（`$CARGO_HOME/credentials.toml`、`~/.m2/settings.xml` 和 `settings-security.xml`、`~/.gradle/gradle.properties`）。规则：

1. 工作区之内的依赖根（`node_modules`、`.venv`、`vendor/`）从工作区根的 `SafeRoot` 以不跟随符号链接的方式打开子目录，路径的任何一级是符号链接都失败。`platform` 为此增加 `SafeRoot::open_dir(&self, rel: RelPath) -> Result<SafeRoot, SafeError>`，用与 `read` 相同的一步打开和 `Walk` 后备，返回绑定到那个目录描述符的新根。
2. 工作区之外只允许依赖缓存里的源码子树：`$CARGO_HOME/registry/src`、`$CARGO_HOME` 下的 `git/checkouts`、`$GOMODCACHE` 里 `cache/` 之外的部分（`cache/download` 是 zip 和校验文件）、`~/.m2/repository`、`~/.gradle/caches/modules-2/files-2.1`。路径取自 Lectern 自己进程的环境变量和默认值；项目文件里写的路径（如 `.cargo/config.toml` 指向工作区之外的 vendor 目录）不扩大范围，不为取路径运行 `go env` 这类外部命令。`$CARGO_HOME`、`~/.m2`、`~/.gradle` 本身不作为根打开。
3. 包内的路径（`types`、`exports`、import 的相对路径）按词法相对包目录解析，结果离开所在的依赖根就丢弃。符号链接只在同一生态的同一个根内解析：读出链接目标，按词法拼出目标路径，仍在这个根之内才继续，再经这个根的 `SafeRoot` 读取，其余各级不得是符号链接。
4. 只读声明和源码的扩展名：TS 的 `.d.ts`、`.d.mts`、`.d.cts`、`.ts`、`.tsx` 和 `package.json`；Rust 的 `.rs` 和 `Cargo.toml`；Go 的 `.go` 和 `go.mod`；Python 的 `.py`、`.pyi` 和 `*.dist-info/RECORD`。单个文件最多 1 MiB。

### 策略

- **不整体索引**：依赖目录不进文件列表、不建整仓索引、不监听，这条规则不变。
- **按需解析**：跳转的 import 步骤（`code_intel`「跳转到定义」第 2 步，经解析扩展点，TS 由 [#19](https://github.com/SoloJiang/lectern-app/issues/19) 实现）把裸模块名解析到依赖根里的声明文件，当场读取、抽取，只沿 re-export 走到定义所在的文件，通常 1–3 个文件。`@types/react` 的入口 186 KiB，按 ADR 0031 的抽取吞吐约 40–50 ms（Linux），在跳转的第一批预算（≤ 300 ms）以内。
- **空闲时索引直接依赖**：当前子项目清单里列出的直接依赖，在批量层上建声明闭包的索引（「依赖层」，见第 2 节）。依赖的依赖不索引：跳转第 2 步按需解析时才读它们。
- **限额**：每个包的声明闭包最多 4,000 个文件、16 MiB；单个文件仍按后台上限 1 MiB；每个项目的依赖层最多读 64 MiB 源码，写入自己的命名空间（下文「磁盘份额与命名空间」）。实测 TS 项目的直接依赖闭包在 5 MiB 以内；Rust 项目一个 crate 的 `src/` 就可能有几 MiB，64 MiB 大约是 20 个 tokio 量级的直接依赖。超出限额的部分只走按需解析。

### 缓存键

架构规则 5 要求派生数据以 git blob OID 为键。被忽略的文件不在 index 里，没有现成的 OID，所以与文件夹项目一样，按 git 的 blob 格式对内容求哈希（`blob <长度>\0` 加内容，gix 用的 sha1dc；ADR 0030「符号抽取」）。抽取结果的键与项目文件相同（OID、语言、grammar 版本、查询版本），同一份 `.d.ts` 在 npm 与 pnpm 的布局里、在两个项目里都是同一个键。

求 OID 要读完整个文件。本文实测（页缓存已热）：sha1dc 单线程约 930–1,330 MiB/s；读文件加求哈希 430–570 MiB/s，Vite 项目的整个 `node_modules`（10,053 个文件）216–270 ms，直接依赖的声明闭包（约 5 MiB）约 10 ms。

两级捷径，避免每次打开项目都读一遍：

1. **包的身份**：一个包的内容由它的身份决定，身份不变就沿用上次记下的（相对路径、OID）表，不读、不 stat。身份按生态取：npm / pnpm / yarn 取 lockfile 里这个包的 `integrity`（tarball 的 sha512）；Cargo 取 `Cargo.lock` 的 `checksum`，git 依赖取提交；Go 取 `go.sum` 里的 `h1:` 哈希；Python 取 `*.dist-info/RECORD` 的 OID（RECORD 里有每个文件的 sha256）；没有这些时取包清单文件（`package.json` 等）的 OID。
2. **stat 表**：身份取不到、或身份变了时，对闭包里的每个文件记（设备号、inode、大小、修改时间、状态改变时间，后两者精确到纳秒），与上次相同就沿用 OID。代价是每个文件一次 `lstat`，本文实测 1.9–3.9 µs（10,053 个文件 30–40 ms），表的每行约 80 字节加路径。修改时间可以被解包程序设回旧值（tarball 里的时间戳是 1985-10-26，npm 10.9 解包时改成了安装时间，pnpm 是内容存储的硬链接），所以状态改变时间必须在键里：它只能由内核更新。与 git 的 racy-clean 相同，记录时刻之前 2 秒内被改过的文件不走捷径。

无论走哪条捷径，跳转真正打开目标文件时都按读到的字节重新求 OID，与记下的不同就当场重新抽取、更新这一行（与 `code_intel`「读取核对」相同），所以手工改过的 `node_modules`（patch-package）只会让索引里的位置暂时过期，不会让跳转显示错的内容。

### 磁盘份额与命名空间

- 依赖的抽取结果写进项目分库的新命名空间 `code_intel.deps`，同一套表结构，单元的键与项目文件相同，但 LRU 和配额与 `code_intel.tags` 分开：依赖的单元只淘汰依赖的单元。共用 `code_intel.tags` 不可行：单元没有来源字段，无法按项目统计依赖写了多少；10 万文件的仓库本来就超过配额（第 3 步实测约 270 MiB），依赖会挤掉项目自己的单元。
- 配额：`code_intel.deps` 32 MiB，从 `code_intel` 原来的 256 MiB 里划出，`code_intel.tags` 改为 224 MiB，两者合计仍是 256 MiB，项目分库里 hunk 缓存至少保留 256 MiB 的约定不变。代价是 10 万文件的仓库更早进入「配额已满、冻结游标」的状态（code_intel 设计「调度、批次与取消」的配额一条），被挤出的单元由第 1 层和查询现场补上。
- 包的（相对路径、OID）表作为同一命名空间里的条目存放，键是（生态、包名、版本、身份）。按实测，一个 TS 项目的直接依赖约 250 行，一个 Rust 项目约几千行，每行约 70 字节，远小于配额。
- 依赖的「blob → 路径」映射只在内存里，按项目、按包存放，项目关闭时释放；它不进 `code_intel` 的工作区映射，查询时作为单独的一层合并（候选的分层见「对 Lectern 的建议」）。

### 失效与监听

依赖目录不监听（[技术调研「性能要点」](../design/tech-research.md#性能要点)），失效靠以下来源：

| 来源 | 作用 |
|---|---|
| lockfile 与清单（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`Cargo.lock`、`go.sum`、`uv.lock` / `poetry.lock`、各自的清单） | 它们是受跟踪的文件，`fs_watch` 照常交付（[fs_watch 设计「路径分类」](../design/fs_watch.md#路径分类)第 5 步）；变化后重新算包的身份，身份变了的包重新走一遍闭包 |
| 打开项目 | 按 lockfile 算身份，与 `code_intel.deps` 里的表对照；另对每个直接依赖的清单文件做一次 `lstat`（20 个直接依赖约 0.1 ms），发现重新安装 |
| 跳转时的读取核对 | 见上一节，兜住 lockfile 没有反映的改动 |
| lockfile 被忽略或不存在 | 只剩打开项目时的检查和读取核对（已知限制） |

`npm install` 在 `node_modules` 里写的 `.package-lock.json` 在被忽略的目录里，`fs_watch` 不交付它，不依赖它。

### 分层、守卫与线程组

| 工作 | 守卫 | 优先级 | 理由 |
|---|---|---|---|
| 跳转时的按需解析、读取与抽取 | `BusyGuard` | `Interactive` | 用户正在等的查询的一部分，计入查询的预算 |
| 打开项目时读 lockfile、算包的身份 | `BusyGuard` | `Background` | 初始化与刷新 |
| 依赖层：直接依赖的声明闭包的读取、求 OID、存在检查、抽取、写入 | `BackgroundGuard` | `Batch` | 满足 ADR 0029 的四条：跳转按需解析，不等它；结果按 OID 写入 `cache`；按批暂停与取消；不是用户刚发起的操作 |

依赖层排在第 4 层之后、第 5 层之前。排在第 3 层之后会占用 [ADR 0031](../adr/0031.md) 为 `app/index_100k`（10 万文件 ≤ 2 分钟）留下的余量：达到上限的 64 MiB 依赖源码在 2 个批量线程、每线程 4 MB/s 下约 8 s。跳转进依赖的当前需要由按需解析覆盖，依赖层只让之后的跳转命中缓存。`app/index_100k` 的夹具里加一个达到依赖层上限的 `node_modules`，用来确认依赖层不推迟它的里程碑（第 3、4 层完成）。它不改变第 1–5 层的编号和含义。

### 核心与插件的归属

放在核心，作为 `code_intel` 解析扩展点的一部分：

- 不新增依赖：读 `package.json` 用已有的 serde_json，`Cargo.lock` 和 `go.sum` 是文本，求 OID 经 `git`；安装包几乎不变（ADR 0018）。
- TS / JS 是核心语言，审阅 agent 改动时最常见的跳转之一就是跳进它调用的库。
- `-sources.jar`（Java）不在本文的决定里：读 jar 要一个 zip 解码器（新依赖），按 [ADR 0007](../adr/0007.md) 和 #26 决定放在核心还是 jdtls / SCIP 的插件里；键、身份（jar 的 OID 加条目路径）、配额和分层沿用本节的规则。
- Rust、Go、Python 目前只有按名字的分层，没有 import 解析；依赖根的发现和闭包规则在它们的解析扩展点实现时接入，在那之前依赖层只为 TS / JS 运行。

## 2. 空闲时解析

### 「空闲」的定义

交互静止指同时满足以下条件的状态，由 `app` 在 UI 线程上判断（它是唯一同时知道输入、滚动和动画的地方）：

- 300 ms 内没有键盘、鼠标按键、滚轮（含触控板的惯性阶段）和拖拽事件。只移动指针不算交互。
- 没有正在运行的 `ui` 动效（`ui` 的统一动画原语知道自己是否在运行，[交互规范「动效」](../design/interaction.md#动效)）。
- executor 的 `Interactive` 队列为空，也没有在途的 `Interactive` 任务：用户正在等的跳转、打开文件、限时搜索还没做完时不算空闲。

300 ms 取自两个数字：最长的动效 380 ms 已由第二条覆盖；键盘连续输入的间隔通常在 100–200 ms，300 ms 让一段连续操作算作一次交互。窗口被遮挡或最小化时没有输入，按空闲处理。电源状态不参与判断（ADR 0032）。

### 交互时让路

本文实测（`contend`，见「实测说明」）：主线程每 8.33 ms 做一份固定的约 2 ms 的工作，另有 0–3 个线程不停地解析。

| 解析线程 | 每帧工作的中位数 | p99 | 最大 |
|---|---|---|---|
| 0 | 2.03 ms | 5.13 ms | 6.76 ms |
| 1 | 2.07 ms | 6.52 ms | 10.20 ms |
| 2 | 2.07 ms | 10.12 ms | 15.65 ms |
| 3 | 2.03 ms | 10.06 ms | 113.88 ms |

这台 4 个 vCPU 的共享虚拟机上，中位数不受影响，尾部随解析线程数变长；3 个线程占满其余 vCPU 时出现一次 114 ms。这是普通优先级的线程；生产配置是 utility QoS、默认 `clamp(核数 / 4, 1, 3)` 个批量线程（ADR 0029），对应表里 1–2 个线程的情况，1 个线程时 p99 是 6.5 ms，仍在 8.3 ms 以内。所以这组数据不足以证明交互时必须停下批量层，只说明有这种风险。

做法：设计里加上让路开关，是否启用由 macOS 上的基准决定。

- kernel 在测量用的暂停开关之外加一个交互让路开关，`app` 在离开交互静止时打开、回到交互静止时关闭。
- 打开时，第 4 层、依赖层、第 5 层和两类只存内存的批量工作（空闲预取、大文件的整文件高亮，见下文和第 3 节）在下一个批次边界（`BackgroundGuard::proceed`）停下，关闭后从停下处继续。第 3 层（当前子项目）不让路：它守的是 ADR 0030「当前子项目 ≤ 10 s」的目标，用户正在看的就是这个子项目。
- 在途的那个文件不放弃，但要立即停下：批次只在文件边界结束，一个文件可以运行到 250 ms 的截止时间，「在批次边界停下」在 3 个批量线程时仍可能占掉约一半的时间。所以开关打开时，在途的解析在下一个分片边界停下、保留状态（第 3 节「分片解析与恢复」：恢复后的树与一次解析相同，不超过 1 MiB 的文件一片最多超出 0–4 ms，后台上限正是 1 MiB），一次遍历抽取在节点计数的检查点停下。不能恢复的 tree-sitter-tags（语言包）照暂停的规则放弃这一项。
- 之后只在保活时段里前进：kernel 发放全局的保活令牌，同一时刻最多一个批量线程持有；一个时段最长 50 ms（到期时同样在分片边界停下，下一个时段接着做），相邻两个时段的开始至少相隔 500 ms；时段里只做一个文件，超过 256 KiB 的文件不进入时段、等交互静止。所以无论有几个批量线程，开关打开期间批量层合计最多用一个核的 10%（加上开关打开那一刻每个线程至多一片的超出）。取 10% 的理由：上表里一个线程一直运行时 p99 也只到 6.5 ms，10% 远低于它；同时连续滚动几分钟时第 4、5 层仍在前进，不会无限期停着。
- 它与测量用的暂停不同：不放弃在途的文件（`pause_requested()` 不受影响），所以连续滚动不会让一个大文件反复重做；不改变「静止」和后台工作的计数，`Kernel::pause` 的语义和 bench 的采样方式不变。开关只有一个、全局，插件不自己判断空闲。
- 默认关闭：新增 `app/scroll_frames_indexing`（批量层有工作时在大文件里滚动，预算与 `app/scroll_frames` 相同：每帧工作时间 ≤ 8.3 ms、不掉帧）。macOS 上不让路就通过时，开关保持关闭；超标时 `app` 启用它，启用的条件（交互静止的阈值、占空比）由这个基准校准。
- 索引覆盖的预算（ADR 0030）和测量方式不变。另加只记录的 `app/index_100k_interaction`：建索引期间按脚本持续滚动，记下第 3、4 层的完成时间，用来观察让路启用后的影响。

### 空闲预取

只在交互静止时运行的预取，预先算好用户很可能下一步要看的文件的高亮区间（和第 1 层的符号抽取）：

| 来源 | 内容 | 上限 |
|---|---|---|
| 审阅集合 | 下一个未看文件（按 V 之后打开的那个） | 1 个 |
| 上下文抽屉 | 当前候选列表的第一个候选所在的文件 | 1 个 |
| 跳转 | 唯一候选的目标文件（[代码导航调研第 7 节](code-navigation.md#7-预测与预先计算)） | 1 个 |
| 光标停留 | 光标在符号上停留约 150 ms 后的定义候选（同上，只查不渲染） | 1 次查询 |

- 每次进入交互静止最多预取 4 个文件；不超过 1 MiB 的文件算整个文件的区间，更大的只算第一屏的窗口（第 3 节）。
- 结果按（blob OID、语言、grammar 版本、查询版本）放进 `file_reader` 已有的 8 MB 高亮与文本 LRU，不另占常驻内存；预取的条目在 LRU 里排在用户打开过的条目之后，先被淘汰。
- 预取持有 `BackgroundGuard`、在批量线程上运行，受上面的让路开关约束，不计入静止。它不满足 ADR 0029 的第二条（结果按 OID 写入 `cache`）：结果只在内存里。理由是预取的结果丢了只需在用到时现算，暂停或退出最多丢掉在途的一个文件。所以预取与第 3 节档位 B、C 的整文件高亮一起，作为 ADR 0029 四条之外有上限的例外写进 [ADR 0033](../adr/0033.md)。
- 首帧之前不做：没有打开的项目就没有预取的来源，第一次预取在项目打开、第一次进入交互静止之后。

### 依赖层与批量层

第 1 节的「依赖层」（直接依赖的声明闭包）和 `code_intel` 的第 3–5 层一样是可暂停的后台工作。批量线程上的顺序是：打开的大文件的窗口抽取（第 3 节） → 预取 → 第 3 层（当前子项目） → 第 4 层 → 依赖层 → 第 5 层；打开的大文件的整文件高亮与它们排在同一个队列里，位置在预取之后。前两项是用户正在看或下一步很可能要看的内容，量有上限（一个打开的文件、每次最多 4 个预取的文件）。

## 3. 大文件的解析与高亮

本节的数字都是本文实测：tree-sitter 0.27.1，grammar 版本与 Lectern 的 Cargo.lock 相同（JSON 用 gpui-component 0.7.3 声明的 tree-sitter-json 0.24.8），单线程，release 构建。合成文件由 `bench` 的 `gen` 生成（TS、Rust 是带注释、模板字符串、嵌套块的代码单元重复拼接，JSON 是 package-lock 形状，压缩 JS 是一行），真实文件来自公开的 npm 和 crates.io 包（见「实测说明」）。高亮查询用各 grammar 自带的 `highlights.scm`（TS 是 JS 的查询加 TS 的查询）。

### 整文件解析与语法树内存

| 文件 | 大小 | 行 | 解析 | 吞吐 | 语法树 | 树 / 输入 |
|---|---|---|---|---|---|---|
| 合成 TS | 1 / 4 / 16 / 64 MiB | 3.6 万 / 14 万 / 57 万 / 228 万 | 167 ms / 655 ms / 2.7 s / 10.9–17.7 s | 5.8–6.1 MiB/s（64 MiB 时 3.6–5.9） | 34 / 134 / 537 / 2,147 MiB | 33.5 |
| 合成 Rust | 同上 | 3.5 万 / 14 万 / 56 万 / 225 万 | 160–218 ms / 713 ms / 2.7–3.9 s / 12.4–13.7 s | 4.1–6.0 MiB/s | 41 / 163 / 653 / 2,614 MiB | 40.8 |
| 合成 JSON | 同上 | 3.3 万 / 13 万 / 52 万 / 210 万 | 50 ms / 210 ms / 924 ms / 4.1 s | 15.6–20.0 MiB/s | 14 / 56 / 223 / 892 MiB | 13.9 |
| 合成压缩 JS（一行） | 1 / 4 MiB | 2 | 295 ms / 1.4 s | 2.9–3.4 MiB/s | 84 / 332 MiB | 83 |
| `typescript/lib/typescript.js` | 8.7 MiB | 20 万 | 915 ms | 9.5 MiB/s | 202 MiB | 23.3 |
| `typescript/lib/typescript.d.ts` | 0.56 MiB | 1.1 万 | 36 ms | 15.4 MiB/s | 8.9 MiB | 15.8 |
| `@babel/standalone/babel.min.js` | 2.9 MiB | 5 | 549 ms | 5.3 MiB/s | 139 MiB | 47.3 |
| `@mdn/browser-compat-data/data.json`（一行） | 16.4 MiB | 1 | 1.6 s | 10.5 MiB/s | 376 MiB | 22.9 |
| `windows` crate 的一个生成文件（`mod.rs`） | 3.9 MiB | 5.3 万 | 707 ms | 5.5 MiB/s | 105 MiB | 27.0 |

- 解析时间与大小成正比；超过 16 MiB 后吞吐下降（64 MiB 的第一次解析要分配 2 GiB，伴随大量缺页）。合成文件比真实文件密（每 MiB 的节点数多 50% 左右），解析时间偏保守。
- 解析过程中的峰值内存就是最后那棵树（在进度回调里采样 `mallinfo2`，峰值与树的大小相差不到 1%），没有临时的翻倍。
- 树占输入的 14–41 倍，压缩 JS 47–83 倍。4 MiB 的 TS 文件的树（134 MiB）就超过了打开 monorepo 的空闲内存预算（100 MB）。所以语法树不能常驻，也不能在一个文件打开期间一直留着。

M 系列上 `code_intel` 的抽取吞吐是这台机器的 1.22–1.68 倍（[ADR 0031](../adr/0031.md)），解析应在同一量级，由 bench 校准；内存比例与 CPU 无关。

### 分片解析与恢复

`Parser::parse_with_options` 的进度回调返回 `Break` 时解析中止、返回 None；不调用 `Parser::reset`、用同一份输入再次调用时，解析从中止处继续（tree-sitter 0.27.1 `Parser::reset` 的文档；回调每约 100 次解析操作调用一次，`OP_COUNT_PER_PARSER_CALLBACK_CHECK`）。实测 18 个文件 × 3 种片长：

| 片长 | 恢复后得到的树与一次解析相同 | 总耗时相对一次解析 | 不超过 1 MiB 的文件，最长的一片 | 16–64 MiB 的文件，最长的一片 | p99 |
|---|---|---|---|---|---|
| 2 ms | 54 / 54（全部） | −4% 到 +56%，中位数约 +11% | 2.1–6.0 ms | 16–43 ms | 2.0–10 ms |
| 5 ms | 同上 | −11% 到 +72%，中位数约 +6% | 5.0–9.1 ms | 17–66 ms | 5.0–12 ms |
| 8 ms | 同上 | −8% 到 +45%，中位数约 +3% | 8.0–10.0 ms | 21–53 ms | 8.0–14 ms |

（树相同按全部节点的（种类、起点、终点）的哈希判断。总耗时的离散主要来自这台共享虚拟机的噪声：同一个文件一次解析的时间本身就相差 10–20%。）

结论：

- 按 5–10 ms 分片是可行的，额外开销在噪声以内；2 ms 的片太短，每片多出约 0.3–0.5 ms 的恢复开销。
- 解析器在两片之间保留状态和已经建好的子树，所以分片不省内存：内存仍按整棵树算。分片的用途是让交互任务插进来、让取消和让路及时生效，不是解决大文件。
- 不超过 1 MiB 的文件，最长的一片只比片长多 0–4 ms；越大的文件偶尔有越长的一片（64 MiB 时 40–65 ms），推测是大块内存的重新分配，未逐项验证。这只影响后台线程，UI 线程上不解析。
- 输入变了（文件被改、换了文件）必须先 `reset`，否则解析器会接着上一次没做完的状态。gpui-component 的高亮在超时后不 `reset`（第 4 节）。

### 分块输入

| 输入方式 | 1–64 MiB 各文件的解析时间相对连续的 `&str` |
|---|---|
| ropey 的 Rope（叶子不超过 1 KiB，回调返回所在叶子的剩余部分） | −31% 到 +17%，在噪声以内 |
| 固定 4 KiB 的块 | −24% 到 +15% |
| 固定 64 KiB 的块 | −27% 到 +7% |

（64 MiB 的 TS 第一次解析异常地慢，不计入。）

输入回调的开销可以忽略，所以文本可以存成不可变的分块（范围读取得到的 64 KiB 页、Rope 的叶子），解析时不拼成一整块。

### 首屏窗口

首屏的窗口从可见区域之前的一个安全位置开始，到可见区域之后不远处结束，单独解析；只用它给出可见的 60 行（一行的文件取 8 KiB）的高亮。与整文件解析的高亮逐字节比较（只比非空白字节；每个字节取最内层的捕获，同一节点上取查询里靠前的模式）：

| 文件 | 文件开头：16 KiB 窗口的解析 | 文件中部：窗口大小 | 解析（平均 / 最大） | 可见部分的查询 | 与整文件一致的字节（平均 / 最差） | 完全一致的位置 |
|---|---|---|---|---|---|---|
| 合成 TS 1–64 MiB | 2.8–4.9 ms | 14 KiB | 2.3–2.6 / 3.0–6.5 ms | 0.3–0.4 ms | 100% / 100% | 100% |
| 合成 Rust 1–64 MiB | 2.8–3.3 ms | 14 KiB | 2.3–2.9 / 2.7–7.5 ms | 0.3–0.6 ms | 100% / 100% | 100% |
| 合成 JSON 1–64 MiB | 0.7–0.8 ms | 14 KiB | 0.6–0.8 / 0.8–4.8 ms | 0.1 ms | 100% / 100% | 100% |
| 合成压缩 JS 1 / 4 MiB | 4.7–4.9 ms | 20 KiB | 5.7–6.1 / 7.4–10.3 ms | 2.3–2.5 ms | 100% / 100% | 100% |
| `typescript.js` | 1.5 ms | 15 KiB | 2.0 / 3.6 ms | 0.3 ms | 100% / 100% | 100% |
| `typescript.d.ts` | 1.1 ms | 15 KiB | 1.7 / 13.9 ms | 0.2 ms | 98.3% / 33.9% | 95% |

文件开头的窗口在每个文件上都与整文件解析一致。文件中部取 40 个随机位置；不一致的位置是安全位置的规则判断错了（起点落在多行注释或模板字符串里）。首屏的这种错误由之后的整文件计算改正（下一节），改正前最多持续到整文件的区间算完。

安全位置的规则，按文件形状：

- 普通代码：可见区域之前约 8 KiB 处往回，4 KiB 之内第 0 列开始、不是右括号和注释续行的行；没有时取这段里缩进最少、不是注释续行的行。对照：固定往回 200 行、不看内容的起点，在 `typescript.d.ts` 里会落进多行 JSDoc，最差 64%。
- 一行很长（压缩 JS）：往回找 `;` 或 `}` 之后的位置。从任意字节开始（naive）最差只有 5%：起点落在字符串里时，之后的引号全部反过来。
- JSON：多行的按缩进最少的行；一行的找成员开头。上表的测量从文件开头做词法扫描来判断字符串状态，不能用在首屏路径上；实现用下一节有界的规则（形如 `,"键":` 的成员开头），实测一致率相同。窗口单独解析时，开头的成员没有外层对象、结尾的对象没有闭合，键会被当成普通字符串（不处理时只有约 91%）；在窗口前补上外层的 `{`（窗口开头先出现的右括号，各补一个 `"":{` 或 `"":[`），在末尾补上没有闭合的括号，就与整文件解析一致。

首屏的时间预算：打开文件到首屏高亮 < 16 ms，其中范围读取（[#103](https://github.com/SoloJiang/lectern-app/issues/103)）读几十 KiB、页缓存已热时在百微秒级，窗口解析和可见行的查询见上表，余下的是排版和绘制。窗口解析平均在 6 ms 以内，最差的位置在这台机器上 14–15 ms（`typescript.d.ts`、`babel.min.js`），所以首屏窗口的解析带 8 ms 的截止时间（M 系列上校准）：超时时这一帧先画出没有高亮的文本，窗口解析完成后再上色，与 [ADR 0018](../adr/0018.md) 原来的做法一致。

### 首屏路径的准备工作

上表的计时从选好窗口之后开始，选窗口本身用了完整的行索引（`line_starts`），一行的 JSON 还从文件开头做了一遍判断字符串状态的词法扫描（`json_boundary_before`）。打开一个 64 MiB 的一行文件时，这些准备工作要扫描几十 MiB，不在计时内却在首屏的路径上。实现时首屏路径上的每一步都要有界：

| 步骤 | 有界的做法 |
|---|---|
| 目标所在的行 | 从目标的字节偏移往前找换行，至多 4 KiB；找不到按长行处理（不需要行索引） |
| 可见部分 | 从行首往后数 60 个换行，至多 64 KiB；长行取 8 KiB |
| 安全位置 | 只看目标之前至多 64 KiB：普通代码按第 0 列的语句、缩进最少的行；长行按 `;` / `}`；一行的 JSON 不判断字符串状态，找形如 `,"键":`（键不超过 256 字节、不含反斜杠）的成员开头 |
| 找不到安全位置 | 首屏先画纯文本，起点、行检查点和字符串状态在后台扫描后再上色 |
| 编码、BOM、二进制 | 只看文件头 8 KiB 和窗口本身 |
| 长行判断 | 只看可见的行；档位（有没有超过 4 KiB 的行）在后台扫描时决定，首屏不需要它 |
| 行号栏 | 有行检查点时精确，否则先按估计显示，后台扫描后改正 |

本文实测了这条有界的路径（`first`：40 个随机字节偏移，选起点、JSON 补括号、解析、可见部分的查询都在计时内；一行的 16 / 64 MiB 文件由 `gen-oneline` 生成）：

| 文件 | 找不到起点 | 窗口 | 选起点（最大） | 合计：平均 / p95 / 最大 | 与整文件一致：平均 / 最差 / 完全一致的位置 |
|---|---|---|---|---|---|
| 合成 TS、Rust 1–64 MiB | 0 | 14 KiB | ≤ 0.07 ms | 2.5–3.3 / 2.9–5.6 / 3.2–8.2 ms | 100% / 100% / 100% |
| 合成 JSON 1–64 MiB（多行） | 0 | 14 KiB | ≤ 0.04 ms | 0.8–0.9 / 0.9–1.6 / 0.9–1.6 ms | 100% / 100% / 100% |
| 一行 JSON 16 / 64 MiB | 0 | 20 KiB | 0.003 ms | 1.7 / 2.0 ms，2.0 / 3.4 ms，2.2 / 3.4 ms | 100% / 100% / 100% |
| 一行压缩 JS 1 / 4 / 16 MiB | 0 | 20 KiB | ≤ 0.03 ms | 8.2–11.6 / 11.8–19.5 / 12.0–20.2 ms | 100% / 100% / 100% |
| 一行压缩 JS 64 MiB | 0 | 20 KiB | 0.003 ms | 7.8 / 9.8 / 10.6 ms | 不比较（整文件的树约 5 GiB） |
| `data.json`（一行 16 MiB） | 0 | 20 KiB | 0.004 ms | 2.0 / 2.2 / 2.2 ms | 100% / 100% / 100% |
| `typescript.js` / `typescript.d.ts` / `mod.rs` | 0 | 16–18 KiB | ≤ 0.02 ms | 2.4–3.4 / 6.0–16.4 / 6.5–19.2 ms | 94.5–99.7% / 29–91% / 90–92% |
| `babel.min.js` | 3 / 40 | 26 KiB | 0.05 ms | 8.0 / 17.6 / 22.3 ms | 98.2% / 57% / 84% |

- 选起点与文件大小无关，最多 0.07 ms；64 MiB 的一行 JSON 与 16 MiB 的相同。
- 合计时间主要是窗口的解析和查询。压缩 JS 的窗口里 token 密，这台机器上平均 8–12 ms、最多约 20 ms，超过 8 ms 截止时间的那部分首屏先画文本；M 系列上按 1.2–1.7 倍的速度估计，平均可以进入截止时间。
- 起点只看局部字节，真实文件里有 8–16% 的位置首屏高亮不完全一致（多数是落在多行注释或模板字符串里），由之后的整文件计算改正。

### 整个文件按窗口高亮

把整个文件切成约 64 KiB 的窗口，逐个解析、算出这一段的着色区间后立即释放语法树。两种切法：

- 启发式：窗口的终点放在下一个安全位置（同上一节的规则）。
- 按树切：解析一个约 64 KiB 的窗口后，在它自己的树里找窗口终点之前最后一个完整、没有错误的节点（从根往下，进入被窗口截断的那个节点，直到找到这样的兄弟节点），只采用到这个节点结束处为止的部分，下一个窗口从这里开始。窗口按文件顺序前进，每一段的起点都是前一段的树确认过的语句边界。

| 文件 | 窗口数 | 各窗口解析之和 / 整文件解析 | 最大窗口的解析 | 最大窗口的语法树 | 一致的字节：启发式 | 一致的字节：按树切（最差窗口） |
|---|---|---|---|---|---|---|
| 合成 TS 1 / 4 / 16 / 64 MiB | 16–1,033 | 196 / 227 ms … 12.5 / 13.5 s | 16–38 ms | 2.1 MiB | 99.98% | 100%（100%） |
| 合成 Rust 同上 | 16–1,029 | 188 / 179 ms … 14.0 / 13.7 s | 16–38 ms | 2.6 MiB | 100% | 100%（100%） |
| 合成 JSON 同上 | 17–1,027 | 60 / 78 ms … 3.8 / 4.4 s | 7–16 ms | 0.9 MiB | 100% | 100%（100%） |
| 合成压缩 JS 1 / 4 MiB | 17 / 65 | 441 / 387 ms，1.7 / 1.8 s | 45–46 ms | 5.3 MiB | 100% | 100%（100%） |
| `typescript.js` 8.7 MiB | 125 | 1.4 / 1.1 s | 36 ms | 5.3 MiB | 96.4% | 98.9%（33.7%） |
| `typescript.d.ts` 0.56 MiB | 10 | 47 / 42 ms | 8 ms | 1.7 MiB | 97.8% | 99.9%（99.3%） |
| `babel.min.js` 2.9 MiB | 51 | 730 / 588 ms | 32 ms | 4.8 MiB | 98.9% | 99.5%（83.8%） |
| `data.json` 16.4 MiB（一行） | 304 | 1.8 / 1.3 s | 16 ms | 1.7 MiB | 100% | 100%（100%） |
| `mod.rs` 3.9 MiB | 63 | 762 / 504 ms | 28 ms | 4.0 MiB | 100% | 100%（100%） |

256 KiB 的窗口（4 MiB 的合成文件）一致率同样是 99.99–100%，单个窗口的语法树 3.5–21 MiB、解析 23–189 ms：窗口越大，越容易超过 8 ms 一片的粒度，内存也随之变大，64 KiB 是两者之间合适的大小。

结论：按树切的窗口在合成文件上与整文件解析完全一致，在真实文件上 98.9–100%；总解析时间与整文件解析相同（每个字节只解析一次，加上每个窗口末尾被丢弃的一小段）；同时存在的语法树只有一个窗口的，2–5 MiB，与文件大小无关。剩下的差别集中在少数窗口（`typescript.js` 的最差窗口 34%：整个文件包在一个函数里，窗口从函数体中间开始），实现时用更大的窗口重算差别大的窗口，或接受。

### 文本存储与行索引

| 文件 | 建行索引（`memchr` 找换行） | `Rope::from_str` | Rope 的内存 | 逐行遍历 Rope | sha1dc |
|---|---|---|---|---|---|
| 1 MiB | 0.25–0.45 ms | 0.8 ms | 1.1 MiB | 1.6–1.8 ms | 0.8–0.9 ms |
| 4 MiB | 1.1–1.3 ms | 2.9–3.1 ms | 4.5 MiB | 6.4–8.0 ms | 3.5–3.6 ms |
| 16 MiB | 5.1–6.5 ms | 15–20 ms | 17.9 MiB | 27–46 ms | 14–17 ms |

- 这些都与文件大小成正比，16 MiB 以上任何一项都超过一帧，都要在后台做，UI 线程只拿结果。
- Rope 比文本本身多约 12% 的内存；阅读不需要可编辑的 Rope，不可变的 64 KiB 分块加行索引就够，编辑模式才建 Rope。
- 行索引每行 4–8 字节，64 MiB 的文件（228 万行）约 9–18 MiB；每 1024 行记一个检查点只要几 KiB，找某一行时从检查点往后扫描至多 1024 行（约 40 KiB，几微秒）。

### 档位与降级

档位的取舍：整文件解析的树最多几十 MiB，所以「整文件解析」只用于 1 MiB 以内；窗口解析与文件大小无关，所以没有「大到不能高亮」的字节上限，上限只在文本存储和计算总量上。

| 档位 | 条件 | 首屏 | 首屏之后 | 守卫与线程 | 文本 |
|---|---|---|---|---|---|
| A | ≤ 1 MiB，且没有超过 4 KiB 的行 | 首屏窗口 | 整文件解析，8 ms 一片，完成后换成整文件的区间，释放语法树 | `BusyGuard`、`Interactive`（1 MiB 约 165 ms） | 整份读入 |
| B | 1–16 MiB，或有超过 4 KiB 的行 | 首屏窗口 | 按树切的 64 KiB 窗口，从文件开头顺序计算，记下每个窗口的起点，区间只为可见附近的窗口留在 LRU 里；可见区域所在的窗口先用首屏窗口顶上 | 可见窗口和前后各一个：`BusyGuard`、`Interactive`；其余：`BackgroundGuard`、批量线程（ADR 0033 的只存内存的一类，受让路开关约束） | 整份读入（首屏先经范围读取） |
| C | > 16 MiB | 首屏窗口 | 只为可见区域前后各一个窗口算区间，随滚动按需算；窗口起点的顺序计算同档位 B 的「其余」，算到之前用启发式的安全位置 | 同档位 B | 按 64 KiB 的页经范围读取，页的 LRU ≤ 8 MiB；行索引用检查点 |
| 降级 | 二进制、不是 UTF-8，或一个 64 KiB 窗口的解析超过 128 ms 两次 | 纯文本 | 不高亮 | — | 同所在档位 |

几秒长的计算（档位 B、C 的顺序计算，16 MiB 在这台机器上约 3 s）不持有 `BusyGuard`、不占 `Interactive`：否则在它完成之前 kernel 一直不静止、交互静止的第三个条件也一直不成立，让路开关会一直打开。只有可见附近的三个窗口（实测每个 8–46 ms，合计约 50–140 ms）和档位 A 的整文件解析（≤ 1 MiB）在交互线程上。

- 长行：超过 4 KiB 的行一律按字符格数折成显示行（不测量字形），只为可见的行计算，与软换行的设置无关。4 KiB 是估计值：Core Text 排一行的耗时与行长的关系没有测过，由 macOS 上的长行排版基准校准。
- 着色区间的内存：每个 token 一个（起点、长度、捕获序号），按 8 字节计，合成 TS 每 MiB 约 23 万个捕获，约 1.8 MiB；档位 B 的 16 MiB 文件约 29 MiB，超过 8 MB 的 LRU。所以区间按窗口存放，只有可见区域附近的窗口留在 LRU 里；顺序计算时记下每个窗口的起点（每个 8 字节），滚到别处时从记下的起点重算那个窗口（约 10–20 ms），结果与顺序计算时相同。
- 1 MiB、16 MiB、128 ms 这几个数字取自上面的实测，在 M 系列上校准，4 KiB 按上一条校准；它们写在 `file_reader` 的设计文档里。

### 打开大文件时的符号抽取

`code_intel` 第 1 层（当前文件）现在对打开的文件整体抽取，上限 4 MiB，交互截止时间 1 s。按上面的数字，4 MiB 的 TS 文件解析就要 655 ms，加上抽取（ADR 0031 的一次遍历约 3.9 MB/s）超过 1 s，树 134 MiB。

做法：超过 1 MiB 的打开文件按同样的窗口抽取，结果按窗口陆续交出：

1. 可见区域所在的窗口先单独抽取一次，结果只在内存里，立即可用于同文件跳转（第一屏的符号先到）。它在 `Interactive` 上。
2. 持久的抽取按树切的窗口从文件开头顺序进行：每个窗口完成后立即作为一个单元写入 `cache`，键是（OID、语言、grammar 版本、查询版本、窗口起点），单元里记下窗口的终点，也就是下一个窗口的起点。可见窗口前后各一个在 `Interactive` 上，其余在批量层最前面、持有 `BackgroundGuard`，不延长「静止」的等待。
3. 暂停、取消或退出只丢掉在途的那个窗口：恢复或下次打开时，从缓存里最后一个窗口的终点继续，满足 ADR 0029 的第二条。窗口链覆盖到文件末尾时这个文件的 `indexed` 提示才匹配；在那之前，查询用已写入的窗口加限时搜索回答。窗口单元与普通单元在同一个命名空间、同一个配额里。
4. 查询时的 `ParsedFile`（当前文本的解析、locals）对超过 1 MiB 的文件只解析查询位置所在的窗口；窗口之外的同文件定义从窗口单元里取。

窗口抽取的局限：一个跨越整个窗口的作用域（超过 64 KiB 的类、包住整个文件的函数）里的定义，所在作用域可能不完整。

### 4 MiB 上限

打开文件的抽取上限从 4 MiB 提高到 16 MiB：窗口抽取的内存与文件大小无关，16 MiB 的抽取在这台机器上约 4–5 s 的 CPU，大部分在批量层上。超过 16 MiB 的文件（档位 C）不抽取，查询返回 `TooLarge`，与现在 4 MiB 以上的行为相同。后台的上限 1 MiB 不变：后台抽取的是整个仓库，1 MiB 以上的多是生成文件。

### 打开到文件中部

跳转目标、diff 的 hunk、保存的阅读位置都在文件中部，现在都用行号表示。行号要换算成字节偏移才能做范围读取；没有行索引时，第 N 行要从文件开头扫描：64 MiB 的文件找换行就要 37–45 ms，还要先把整个文件读进来（页缓存已热时几十毫秒）。这超过了 16 ms。

做法：

- **知道偏移的一方给出偏移。** `code_intel` 抽取时就有每个定义的字节区间，`Location` 增加定义起点的字节偏移（`byte`）；`git` 做行 diff 时两侧文本都在内存里，`Hunk` 和展示行带上两侧第一行的字节偏移（hunk 缓存的值多两个整数）；保存的阅读位置同时存行号和字节偏移，内容的 OID 不变时用偏移。
- **只有行号时用行检查点。** 如 agent 输出里的 `file:line`、OID 已经变了的旧位置。后台第一次扫描整个文件时，每 64 KiB 记下该处的行号，按 blob OID 写入 `cache`（64 MiB 的文件 1024 个数，约 4 KiB）。之后按行号定位是一次查表加至多 64 KiB 的扫描。
- 第一次打开、只给行号、又没有检查点时，先显示文件开头，扫描到那一行后再滚过去；这个情况不在 16 ms 的保证内。
- 窗口的起点按字节偏移找（第 3 节「首屏窗口」的规则只看目标附近的几 KiB），与行号无关；行号栏在后台扫描完成前按检查点推算，扫描完成后改为精确值。

所以 ADR 0034 对「打开文件到首屏高亮 < 16 ms」的保证是：目标以字节偏移给出、或这个 blob 的行检查点已在缓存里、或目标在文件开头时，任何大小的文件都成立。`app/open_file` 增加一个中部场景：从 diff 打开 4 MiB 的 `package-lock.json` 中部的一个 hunk。

### 编辑模式

编辑模式用 gpui-component 的 `InputState`（第 4 节），只对档位 A 的文件开放：≤ 1 MiB、没有超过 4 KiB 的行。

- 语法树：编辑需要增量解析，所以编辑期间保留一棵树，在上限处是 34–41 MiB（TS、Rust）。退出编辑模式时释放，空闲时不常驻，ADR 0017 的空闲内存不受影响（采样时不在编辑模式下）。
- 进入编辑时的 UI 线程工作：`Rope::from_str`（1 MiB 约 0.8 ms）和 `text_wrapper` 对全部行建换行信息。编辑模式默认不开软换行，这一步是 3.6 万行的一次遍历，同类遍历（逐行遍历 Rope）实测约 2 ms；开软换行时每行要一次文本测量，没有在 macOS 上测过，所以只对 ≤ 256 KiB 的文件允许开软换行。
- 高亮经 `InputHighlighter` 接入 Lectern 自己的实现：解析在后台、增量进行，换输入时 `Parser::reset`。
- 测量：新增 `app/enter_edit`（上限处的文件从 ⌘E 到可以输入，中位数 ≤ 100 ms，交互规范里不显示加载态的上限）和编辑模式下的 `app/scroll_frames` 场景。1 MiB 的上限是估计值，`app/enter_edit` 在 macOS 上超标时降低上限。

## 4. 渲染

Lectern 锁定 `gpui-pre =0.3.9` 与 `gpui-component =0.7.3`（[ADR 0016](../adr/0016.md)）。本节读的是这两个版本的 crate 源码：从 crates.io 下载的 `.crate` 文件，sha256 与 Cargo.lock 的 checksum 一致（gpui-component `465a3632…`、gpui-pre `34f61c1c…`、gpui-base `2e9955b6…`、gpui-pre-apple `b52f5889…`、ropey 2.0.0-beta.1 `4045a00d…`），解开到 `target/` 下的临时目录，只读、不构建。GPUI 的 macOS 平台层不能在 Linux 上构建，本节的结论都是读源码，没有运行。

### gpui-component 的代码编辑器

代码编辑器是 `InputState` 的代码模式，主体在 gpui-base 0.7.3 的 `src/input/`。

| 方面 | 做法（读源码） | 对大文件的影响 |
|---|---|---|
| 文本 | ropey 2.0.0-beta.1 的 `Rope`，叶子最多 1 KiB（`MAX_TEXT_SIZE`）；`set_value` 在 UI 线程上 `Rope::from` 整份文本 | 64 MiB 的建 Rope 本文实测 67–75 ms，16 MiB 就要 15–20 ms，在 UI 线程上超过一帧 |
| 可见行 | `calculate_visible_range` 按行高算出可见的显示行，`layout_lines` 只为可见行排版 | 行数多本身不是问题 |
| 排版 | 每帧对每个可见行 `slice_line(..).into()` 复制成 `String`，每个折行片段调用一次 `shape_line` | 一行越长，每帧的复制和排版越贵；压缩成一行的 4 MiB 文件，每帧复制 4 MiB |
| 软换行 | `text_wrapper.rs` 在设置文本、改宽度、改字体时对整个文件逐行用文本系统测量宽度，结果存进 `SumTree`；在 UI 线程上 | 与文件大小成正比；不开软换行时仍逐行建条目 |
| 高亮 | 可插拔的 `InputHighlighter`。自带实现（gpui-component `src/highlighter/`）：256 KiB 以内在 UI 线程上同步解析，2 ms 超时；更大的文件或超时后，150 ms 防抖，再在后台解析整个文件；超过 10,000 字节的行不高亮（`MAX_HIGHLIGHT_LINE_LENGTH`） | 大文件首屏没有高亮，要等防抖加整文件解析（1 MiB 的 TS 本文实测 165 ms）；解析期间整棵树常驻 |
| 高亮查询 | `styles(range)` 对可见行的字节区间跑高亮查询，在 prepaint 里、UI 线程上 | 查询本身便宜（见第 3 节），但每帧在 UI 线程上执行 |
| tree-sitter 版本 | 自带高亮要开 `tree-sitter` feature，它依赖 `tree-sitter 0.26.13` 和 gpui-component 自己选的 grammar 版本 | Lectern 锁定 0.27.1（ADR 0030），开这个 feature 会链接两份 tree-sitter 和两套 grammar；Cargo.lock 现在没有它，说明 Lectern 没开 |

另外两点：自带高亮在超时后不调用 `Parser::reset`，下一次用新文本解析时会接着上一次没做完的解析（tree-sitter 的默认行为，见第 3 节「分片解析」），这是上游的问题，Lectern 自己的实现要在换输入时 `reset`。编辑器的滚动高度是 `line_height * 显示行数`，同样受下面的 f32 精度限制。

结论：gpui-component 的编辑器适合编辑中小文件，不适合当大文件的阅读视图。Lectern 的阅读视图自己画（见「各界面的做法」），编辑模式继续用 `InputState`，只对档位 A 的文件开放（第 3 节「编辑模式」）、高亮经 `InputHighlighter` 接入 Lectern 自己的实现（[ADR 0034](../adr/0034.md)）。这与[技术调研「技术选型」](../design/tech-research.md#技术选型)「文本存储：gpui-component Editor」和[「编辑范围」](../design/tech-research.md#编辑范围第三层)「20 万行内性能稳定」不一致，见「设计文档的修改」。

### uniform_list 与 list

| 元素 | 机制（读源码） | 适合 | 限制 |
|---|---|---|---|
| `uniform_list`（gpui） | 只量第一项（或 `with_width_from_item` 指定的一项）的尺寸，按「项数 × 项高」得到内容高度，只为可见区间调用渲染闭包 | 等高的行：文件树、代码行、展示行、终端行 | 每项等高；内容高度是 `Pixels`（f32），见下文 |
| `list` + `ListState`（gpui） | 项高存在 `SumTree` 里，只量可见项和上下 `overdraw` 范围内的项；`splice` 改动一段、`remeasure_items` 让一段重新量；宽度变化时全部高度作废、按需重量；有跟随末尾的模式 | 不等高的项：对话、审阅叙事里文件头与行内评论混排 | 未量的项高度为 0 或提示值，滚动条随测量收敛；`measure_all` 在第一次布局时量全部项，要避免 |
| `v_virtual_list`（gpui-base） | 调用方给出全部项的尺寸，尺寸变化时在 UI 线程上重算前缀和；同一个 `Rc` 时不重算 | 尺寸事先知道的表格 | 尺寸数组随项数增长，10 万项可以，但尺寸要由调用方算 |
| `div` 加 `overflow_y_scroll` | 全部子元素每帧进入 taffy 布局 | 几十项以内 | 不能用于数量没有上限的集合 |

两个通用的限制：

- **f32 坐标。** `Pixels` 是 f32，有效精度 24 位。内容高度超过 2^24 = 16,777,216 像素之后，相邻的可表示值相差 2 像素以上：行高 18 pt 时约 93 万行，64 MiB 的合成 TS（228 万行）约 4100 万像素，相邻值相差 4 像素，滚动位置和行的对齐会抖动。所以超长的文件不能用「内容总高度 + 像素偏移」表示滚动位置，要按「首行序号 + 行内偏移」保存，只在可见区域里换算成像素。
- **排版缓存只跨一帧。** `LineLayoutCache` 有本帧和上一帧两张表，键是文本内容加字体区间（颜色不在键里，所以只改颜色不重新排版）；滚出视口再滚回来的行要重新排版，每次查表都对整行文本求哈希。`shape_line_by_hash` 允许调用方给出哈希（如内容 OID 加行号），命中时不必拼出文本。

### 瓶颈

| 瓶颈 | 原因 | 做法 |
|---|---|---|
| 长行 | 每帧复制整行、整行排版（Core Text 一次排整行），查缓存要哈希整行 | 超过 4 KiB 的行一律折成显示行，按字符格数折到视口宽度（不测量字形），只为可见的行计算；每个显示行单独排版 |
| 整文件高亮 | 整棵语法树占输入的 14–83 倍（第 3 节） | 按窗口解析，只保留着色区间（第 3 节） |
| 按内容键的排版缓存 | 只保留两帧，键要哈希整行 | 用 `shape_line_by_hash`，键取（内容 OID、行号、宽度）；Lectern 自己再留一份按这个键的最近行缓存，大小以可见行数的几倍为限 |
| 大 diff | 一个文件的 diff 作为一个元素时整段进入布局 | 展示行（[git 设计「展示行」](../design/git.md#展示行)）逐行作为列表项，折叠区是一行；高亮按窗口计算（见下表） |
| minimap | 要为整个文件排版或采样着色 | 不做 |
| 软换行 | 整文件逐行测量，在 UI 线程上 | 阅读视图默认不换行；长行按格数折行；需要换行时只为可见行计算，结果按（OID、行号、宽度）缓存 |
| 渲染函数里的主线程工作 | 渲染时构造全部行的 `Vec`、把 Rope 转成 `String`、跑高亮查询 | 视图拿到的快照可以按下标取行和区间；渲染只做与可见行数成正比的工作；高亮区间在后台算好 |

### 各界面的做法

| 界面 | 元素 | 要点 |
|---|---|---|
| 文件树（10 万条） | `uniform_list` | 视图持有「当前展开状态下的可见行」快照（[代码导航调研第 8 节](code-navigation.md#8-文件树浏览)）；10 万行 × 22 pt 约 220 万像素，在 f32 精度以内 |
| 代码阅读（`file_reader`） | 自绘元素：固定行高、按显示行虚拟化 | 滚动位置是（首个显示行、行内偏移）；每帧只排版可见的显示行；长行折行；高亮区间从快照取；横向滚动的宽度取已知最长行（后台扫描行索引时记下），不量全部行 |
| 统一 diff | 同一个自绘元素，行来自展示行 | `Row::Folded` 是一行；词级差异（`inline_changes`）是背景色区间，不改字体区间，不触发重新排版 |
| 双栏 diff | 同上，每行两个单元格 | 配对行共用一行；两侧各自排版；两侧的高亮各自按 blob 的窗口计算 |
| 审阅叙事（多文件、文件头、行内评论） | `list` | 每个展示行、文件头、评论框各是一项；只有评论框和文件头不等高；评论框展开时 `remeasure_items` 只量这一项 |
| 对话（不等高） | `list`，跟随末尾 | 每条消息一项，流式输出时 `remeasure_items`；超长的工具输出默认折叠，展开后改为在 Terminal 页查看 |
| 终端网格 | 自绘元素 | 每行把同样式的格子合成一段排版，按行内容的哈希用 `shape_line_by_hash`；libghostty 给出的脏行才重新排版；滚动缓冲按行数限制，在 f32 精度以内 |

这些做法都要在 macOS 上用 `#[gpui::test]`（元素只为可见行调用渲染、滚动位置的换算）和 UI 探针（`app/scroll_frames` 等帧时间基准）验证。

## 对 Lectern 的建议

决定写进 [ADR 0033](../adr/0033.md)（依赖源码、空闲时的后台工作）和 [ADR 0034](../adr/0034.md)（大文件、阅读视图、编辑模式）。电源已由 [ADR 0032](../adr/0032.md) 决定。

| 部分 | 建议 | 落在哪里 |
|---|---|---|
| 依赖源码 | 不整体索引、不监听；跳转按需解析；当前子项目的直接依赖在批量层的「依赖层」建声明闭包的索引，排在第 4 层之后、第 5 层之前；限额每包 4,000 个文件 / 16 MiB，每项目读 64 MiB | `code_intel` 的解析扩展点（TS：#19） |
| 依赖的存储 | 项目分库的命名空间 `code_intel.deps`，32 MiB，从 256 MiB 里划出（`code_intel.tags` 改为 224 MiB） | `code_intel`、`cache` |
| 依赖的键 | 内容求 blob OID；包的身份（lockfile 的 `integrity` 等）不变就不读；stat 表（含 ctime）兜底；跳转时读取核对 | `code_intel` |
| 依赖根 | 工作区内的根经 `SafeRoot::open_dir` 不跟随链接打开；工作区外只允许依赖缓存的源码子树；路径和链接不离开所在的根；只读声明和源码的扩展名 | `code_intel`；`platform` 增加 `SafeRoot::open_dir` |
| 跳转候选的分层 | 依赖里的候选排在本仓库的各层之后（[代码导航调研第 6 节](code-navigation.md#6-没有语言服务器时的定义准确率)的分层末尾加「依赖」一层）；import 解析给出的依赖目标仍是 `Bound(Import)`，可以直接跳 | `code_intel` |
| 交互静止 | 300 ms 无输入、无动效、无 `Interactive` 任务；`app` 判断 | `app`、`ui` |
| 让路 | kernel 的让路开关：第 4 层、依赖层、第 5 层和只存内存的两类在分片边界停下、保留状态，第 3 层不停；之后只在全局的保活时段（≤ 50 ms，每 500 ms 一个，一次一个 ≤ 256 KiB 的文件）里前进，合计 ≤ 一个核的 10%；默认关闭，由 `app/scroll_frames_indexing` 决定是否启用 | `kernel`、`app`、`code_intel` |
| 空闲预取 | 下一个未看文件、抽屉第一个候选、唯一的跳转目标，每次最多 4 个文件，结果只进 8 MB LRU | 高亮的领域模块（随 `file_reader` 设计）、`code_intel` 第 1 层 |
| 首屏 | 安全位置开始的窗口单独解析（≤ 16 KiB 加可见部分），8 ms 截止时间，可见行的区间先交给视图 | 高亮的领域模块 |
| 整文件高亮 | 档位 A 整文件分片解析（`Interactive`）；档位 B 按树切的 64 KiB 窗口；档位 C 只算可见附近；可见附近之外的窗口在批量线程上、持有 `BackgroundGuard`；语法树算完区间即释放 | 同上 |
| 文本 | 不可变的 64 KiB 分块加行索引；> 16 MiB 按页经范围读取；编辑模式才建 Rope | 同上，`platform` 的范围读取（#103） |
| 定位 | 跳转、hunk、保存的位置带字节偏移；只有行号时用按 OID 缓存的行检查点（每 64 KiB 一个） | `code_intel` 的 `Location`、`git` 的 hunk 与展示行、`cache` |
| 打开文件的抽取 | 超过 1 MiB 按窗口抽取，可见窗口先交出；每个窗口完成即按（OID……、窗口起点）写入 `cache`；上限 16 MiB | `code_intel` |
| 阅读视图 | 自绘固定行高列表，（首行、偏移）表示滚动位置，按（OID、行号、宽度）缓存排版，长行折行 | `file_reader`、`review_view` |
| 编辑模式 | 只对档位 A 开放；gpui-component `InputState`，自己实现 `InputHighlighter`，不开它的 `tree-sitter` feature；语法树退出编辑即释放；默认不开软换行 | `file_reader` |
| 列表 | 等高行用 `uniform_list`；对话、审阅叙事用 `list`；不对没有上限的集合用 `div` 滚动 | 各视图 crate |
| 预算 | 数字不变；`app/open_file` 加大文件、压缩文件和文件中部的场景，`app/scroll_frames` 加大文件、压缩文件和编辑模式的场景；新增 `app/scroll_frames_indexing`、`app/enter_edit` 和只记录的 `app/index_100k_interaction` | `bench` |

高亮的计算要放在领域层（不依赖 GPUI、视图只读快照，架构规则 2、4），`file_reader` 和 `review_view` 都要用它。`code_intel` 是插件 crate，视图不能直接依赖它（架构规则 7），所以建议做成一个非插件的领域库 crate（例如 `syntax`：grammar 的登记、高亮查询、窗口规则、着色区间），`code_intel` 和两个视图的领域模型都依赖它，grammar crate 只链接一份。具体由 `file_reader` 的设计文档决定。

## 与现有 ADR 的冲突

| 现有规定 | 冲突 | 处理 |
|---|---|---|
| [ADR 0029](../adr/0029.md)「已知限制」：暂停开关是全局的，只供测量使用 | 交互让路需要 `app` 在运行时停下部分后台工作 | ADR 0033 增加单独的让路开关（默认关闭），测量用的暂停开关语义不变 |
| ADR 0029 四条条件的第二条：结果按 OID 写入 `cache` | 空闲预取和档位 B、C 的整文件高亮的结果只在内存 LRU 里 | ADR 0033 把这两类列为四条之外有上限的例外；打开文件的窗口抽取改为每个窗口完成即写入 `cache`，满足第二条 |
| [ADR 0018](../adr/0018.md)「执行时间有上限」：UI 路径上的解析带 8 ms 截止时间，超时先显示无高亮文本、转到后台；同一文件连续超时则停用 grammar | UI 线程上本来就不解析（AGENTS.md）；大文件的整文件解析必然超过 8 ms，按这条会对每个大文件停用 grammar | ADR 0034 改为：首屏窗口有截止时间，后台按 8 ms 分片；只有 64 KiB 的窗口解析超过 128 ms 两次才对这个文件停用高亮。语言包进入索引前的病态输入基准不变 |
| [技术调研「技术选型」](../design/tech-research.md#技术选型)「文本存储：gpui-component Editor」 | 阅读视图不用 Editor，文本是不可变分块 | ADR 0034；技术调研按「设计文档的修改」改 |
| [技术调研「编辑范围」](../design/tech-research.md#编辑范围第三层)「基于 gpui-component 的 Editor：已有 tree-sitter 高亮……20 万行内性能稳定」 | 它的高亮要 tree-sitter 0.26.13，与 [ADR 0030](../adr/0030.md) 锁定的 0.27.1 冲突；软换行和大文件高亮在 UI 线程上做与文件大小成正比的工作 | ADR 0034：编辑模式只对档位 A 开放，自己实现 `InputHighlighter` |
| [code_intel 设计「调度、批次与取消」](../design/code_intel.md#调度批次与取消)的大小上限：文件被打开时 4 MiB | 窗口抽取不受整树内存限制 | ADR 0034 提高到 16 MiB，后台 1 MiB 不变 |
| [cache 设计「命名空间」](../design/cache.md#命名空间)：`code_intel.tags` 配额 256 MiB | 依赖的单元要单独计配额 | ADR 0033 从中划出 32 MiB 给 `code_intel.deps`，合计不变 |

电源已由 [ADR 0032](../adr/0032.md) 决定（不区分电源，「接电源」只是索引覆盖目标的测量条件），本文和两条 ADR 都没有电源相关的内容，与它不冲突。与 [ADR 0017](../adr/0017.md)（预算）和 [ADR 0018](../adr/0018.md)（安装包）的其余部分不冲突：首帧之前不做任何新增的工作；新增的常驻内存只有依赖的路径映射（TS 项目约 250 行），预取和高亮区间都在已有的 8 MB LRU 里，编辑模式的语法树退出编辑即释放；不新增依赖。

## 决定

技术问题都已在上文和两条 ADR 里决定。以下几条影响用户看到的内容；产品负责人把它们交给负责推进的 agent 决定（原话「其他你来决定」），按下面执行：

1. **⌘K 的符号搜索不包含依赖里的符号。** 依赖只在跳转和查找引用时出现，⌘K 只搜本仓库，避免 `@types/node` 这类包的几千个名字挤掉项目自己的符号。
2. **跳转候选来自依赖时，抽屉里候选的次要文字显示包名和版本**（如 `react 19.3.1`），不另加图标。呈现归 #20 的抽屉设计。
3. **降级为纯文本时不提示**，与「界面不显示索引和语言服务器的状态」一致。
4. **超过编辑上限的文件不能进入编辑**（档位 A 之外：超过 1 MiB 或有超过 4 KiB 的行）：Edit… / ⌘E 不可用，悬停说明原因，文案走 `i18n`，en 与 zh-CN 同时提供。

## 实测说明

- 机器：Linux 容器，Intel Xeon 2.1 GHz，4 个 vCPU，16 GB 内存；不是 M 系列 Mac。数字用于比较方案的量级，标了「M 系列校准」的阈值和预算由 macOS 上的 bench 确认。测量期间机器上还有别的负载，同一项的重复测量相差 10–20%，部分测量与依赖的安装同时进行，表里给的是范围。
- 版本：tree-sitter 0.27.1；tree-sitter-typescript 0.23.2、-javascript 0.25.0、-rust 0.24.2（与 Lectern 的 Cargo.lock 相同）、-json 0.24.8；ropey 2.0.0-beta.1（gpui-base 0.7.3 用的版本和 feature）；sha1dc 0.1.5（gix 用的实现）；Rust 1.97，release 构建（thin LTO）。
- 程序与脚本在 [`large-files-rendering/`](large-files-rendering/) 目录，不是工作区成员（`bench/Cargo.toml` 自带空的 `[workspace]`），`just` 的各个命令不构建它：
  - `bash docs/research/large-files-rendering/run.sh <工作目录> all [真实文件...]`：构建 `bench`，生成合成文件，依次运行 `parse`（整文件解析、三种分块输入、语法树内存）、`slice`（2 / 5 / 8 ms 分片与恢复）、`window`（首屏窗口的五种起点与一致率，选窗口不在计时内）、`first`（有界的首屏路径：40 个随机字节偏移，选起点、补括号、解析和查询都在计时内；另用 `gen-oneline` 生成 16 / 64 MiB 的一行 JSON 和压缩 JS）、`chunked` / `chunked-tree`（整文件按窗口高亮）、`query`（按字节范围的高亮查询）、`text`（行索引、Rope、sha1dc）、`contend`（普通优先级的解析线程对主线程帧工作的影响，不模拟 QoS），结果写到 `<工作目录>/results/`。本文用 `target/large-files-research` 作工作目录。
  - `bash docs/research/large-files-rendering/deps.sh <工作目录> [Cargo registry 的源码目录]`：用三个合成清单从 npm 安装（`--ignore-scripts`），用 `go mod tidy` 下载 gin、grpc、client-go 的模块闭包，用 pip 只装 wheel，下载 spring-core 的 `-sources.jar`；`deps_stats.py`（用 `python3 -I` 运行）统计文件构成和直接依赖的声明闭包，`bench` 的 `hash` 测 stat 与读文件加求 OID 的耗时（第二遍，页缓存已热）。
- 真实文件：npm 的 `typescript@5.9.3`、`@babel/standalone@7.28.4`、`@mdn/browser-compat-data@7.1.10`（`npm pack` 下载），crates.io 的 `windows@0.62.2`；都只作为数据读取，各自解开在单独的空目录里。
- 一致率：对窗口和整文件的语法树跑同一个高亮查询，每个字节取最内层的捕获（同一节点上取查询里靠前的模式），只比较非空白字节；文件中部的位置用固定种子在 5%–95% 之间取 40 个。
- 内存：glibc 的 `mallinfo2().uordblks`，测量前后 `malloc_trim`；tree-sitter 用 C 的 `malloc`，Rust 也用系统分配器，所以两者都计入。
- GPUI 与 gpui-component：只读源码（版本与校验见第 4 节）；Lectern 的 `just` 命令在 Linux 上本来就不构建依赖 GPUI 的 crate。
- 没有测的：M 系列上的任何数字；Core Text 排一行的耗时与行长的关系；`InputState` 在大文件上的实际帧时间；Go 和 Python 的直接依赖闭包（它们还没有 import 解析）。
